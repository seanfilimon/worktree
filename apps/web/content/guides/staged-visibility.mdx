A **staged snapshot** is a team-visible picture of your work-in-progress (WIP). It lets teammates see what you are working on, which files you are touching, and on which branch, before you push anything.

Staged snapshots are deliberately separate from history:

| Property | Behavior |
|---|---|
| Visibility | Stored on the server and visible to everyone who can read the tree. |
| Cardinality | At most **one** per (tree, account, branch). |
| Replacement | A newer stage from the same account on the same branch replaces the older one. |
| Lifetime | Cleared automatically when you push that branch. |
| History | Never part of branch history. Staging does not move a branch tip, create a snapshot in `wt log`, or affect merges. |

Use staged snapshots to avoid duplicate work and surprise conflicts: if `wt status --team` shows a teammate editing `src/auth/session.rs` on `main`, you know to coordinate before you start changing the same file.

## Prerequisites

- A remote configured for the worktree (`wt remote add origin http://localhost:7420 --tenant acme`) or a worktree created with `wt clone`.
- A saved credential for that server (`wt login http://localhost:7420 -u alice`).
- `tree:write` permission on the tree (developer role or higher in the owning tenant). Staging is a write action, like push and tag.

See [Multi-Tenancy](/guides/multi-tenancy) for roles and [`wt remote`](/docs/cli/remote) for remote setup.

## Staging manually with `wt stage`

```bash
wt stage [--remote R]
```

`wt stage` builds a manifest from your **working directory** (including changes you have not snapshotted), uploads any file contents the server does not already have, and records a staged snapshot for your current branch with a change summary relative to your current head. `--remote` selects the remote (default `origin`).

<Steps>
<Step>

### Make some changes

Edit files as usual. You do not need to run `wt snapshot` first.

</Step>
<Step>

### Stage them

```bash
wt stage
```

Run it again whenever you want to refresh what the team sees. Each run replaces your previous staged snapshot for this branch.

</Step>
<Step>

### Push when ready

```bash
wt snapshot -m "Add session refresh"
wt push
```

A successful push clears your staged entry for the pushed branch on the server.

</Step>
</Steps>

## Seeing your team's WIP with `wt status --team`

```bash
wt status --team
```

In addition to the usual local status, `--team` asks the server for the tree's staged snapshots and lists, for each one, the author, branch, counts of added, modified, and deleted files, the changed paths, and when it was staged. Use `--json` for machine-readable output:

```bash
wt status --team --json
```

## Automatic staging by the daemon

The background daemon can stage for you. After each auto-snapshot it uploads a staged snapshot when **all** of these hold:

- `[sync].auto_stage = true` in `.wt/config.toml` (the default),
- the remote named by `[sync].remote` (default `origin`) is configured, and
- a credential for that remote's server exists in `$WT_HOME/credentials.toml`.

```toml
[sync]
auto_stage = true
remote = "origin"
```

To turn auto-staging off for one worktree while keeping auto-snapshots:

```bash
wt config set sync.auto_stage false
```

See [Auto-Tracking Setup](/guides/auto-tracking-setup) for running the daemon.

## Reading staged snapshots over REST

```text
GET /api/v1/trees/{tenant}/{tree}/staged?branch=
```

Omit `branch` (or leave it empty) to list every branch. The response is an array of staged snapshots. Field names are exact:

<Tabs items={['bash', 'PowerShell']}>

```bash
curl -s -H "Authorization: Bearer $WT_TOKEN" \
  "http://localhost:7420/api/v1/trees/acme/app/staged?branch=main"
```

## Live updates over SSE

The server streams events at `GET /api/v1/events?tenant=&tree=` as `text/event-stream`. Two event types concern staged snapshots:

| Event | When |
|---|---|
| `snapshot.staged` | Someone staged (or replaced) a staged snapshot. |
| `staged.cleared` | A staged entry was removed, for example after its author pushed the branch. |

Each event is sent as `event: <type>` followed by a `data:` line holding the JSON event (`type`, `tenant_id`, `tree_id`, `actor`, `payload`, `at`). A heartbeat comment is sent every 15 seconds.

```bash
curl -N -H "Authorization: Bearer $WT_TOKEN" \
  "http://localhost:7420/api/v1/events?tenant=acme&tree=app"
```

See [Events](/docs/server/events) for the full event list.

## In the admin panel

Open **Trees**, select a tree, and switch to the **Staged WIP** tab on the tree detail page. It lists every staged snapshot for the tree with author, branch, change counts, and changed paths. See the [Admin Panel guide](/guides/admin-panel).

## Privacy considerations

<Callout type="warn" title="Staging uploads file contents">
  A staged snapshot is not just metadata. `wt stage` and daemon auto-staging upload the contents of your changed files to the server, and anyone who can read the tree can see the staged entry.
</Callout>

- **Visibility follows the tree.** For a `private` tree that means tenant members; for `internal`, every authenticated account on the server; for `public`, anyone, including anonymous readers.
- **Clearing is not erasure.** A push removes the staged *entry*. Do not assume file contents already uploaded are erased from the server's object store.
- **Keep secrets out of the worktree.** Secret scanning runs before every `wt snapshot`, but the safest approach is to never place credentials in tracked paths. Use [ignore patterns](/guides/ignore-patterns) for local env files.
- **Opt out where needed.** Set `sync.auto_stage` to `false` for sensitive worktrees, or pause the daemon with `wt daemon pause` while you work on something you do not want shared.
