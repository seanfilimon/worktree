This guide takes you from a source checkout to a running, backed-up W0rkTree server with the admin panel, behind a TLS reverse proxy. For every flag and endpoint, see the [Server docs](/docs/server).

The server is a single pure-Go binary. It serves gRPC (for `wt`), the REST API, server-sent events, and the static admin panel on **one port**, `:7420` by default. All state lives in one data directory.

<Callout type="info" title="Pre-1.0">
  This guide builds from source to show every moving part. Since v0.7 you can instead use the container image (`deploy/docker/Dockerfile`), Docker Compose, the Helm chart, the systemd and launchd units, or the release archives and installers; see [Deployment](/docs/server/deployment). For backups, the server now has built-in online backups ([S3 storage and backups](/docs/server/storage-backends#backups)).
</Callout>

## 1. Build

You need Go 1.25 or newer for the server and Node.js 22 or newer for the admin panel. No cgo or C toolchain is required.

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
# from the repository root
cd services/server-go
go build -o worktree-server .
cd ../..

cd apps/admin
npm install
npm run build        # output: apps/admin/dist
cd ../..
```

</Tab>
<Tab value="PowerShell">

```powershell
# from the repository root
Set-Location services\server-go
go build -o worktree-server.exe .
Set-Location ..\..

Set-Location apps\admin
npm install
npm run build        # output: apps\admin\dist
Set-Location ..\..
```

</Tab>
</Tabs>

Copy `worktree-server` and the contents of `apps/admin/dist` to wherever you deploy, for example `/opt/worktree/bin/worktree-server` and `/opt/worktree/admin/`. Details: [Server Installation](/docs/server/installation).

## 2. Choose a data directory

`--data` (env `WT_DATA`, default `./wt-data`) holds everything the server stores:

| Path | Contents |
|---|---|
| `meta.db` | Metadata in a bbolt database: accounts, tenants, trees, branches, snapshots, tags, staged entries, protections, license rules, merge requests, audit log. |
| `objects/` | Content-addressed object store: file blobs and manifests, keyed by BLAKE3 hash. |

Put it on durable storage with room to grow, readable only by the server's user. See [Storage](/docs/server/storage).

```bash
sudo useradd --system --home /var/lib/worktree worktree
sudo mkdir -p /var/lib/worktree
sudo chown worktree: /var/lib/worktree
sudo chmod 700 /var/lib/worktree
```

## 3. First start and the first admin

<Steps>
<Step>

### Start with an admin password

When `--admin-password` (env `WT_ADMIN_PASSWORD`) is set, the server makes sure a server admin account exists at startup. The username comes from `--admin-user` (env `WT_ADMIN_USER`, default `admin`). Prefer the environment variable so the password does not appear in process listings.

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
export WT_ADMIN_PASSWORD='use-a-long-random-password'
./worktree-server \
  --addr 127.0.0.1:7420 \
  --data /var/lib/worktree \
  --admin-dir /opt/worktree/admin \
  --allow-registration=false
```

</Tab>
<Tab value="PowerShell">

```powershell
$env:WT_ADMIN_PASSWORD = 'use-a-long-random-password'
.\worktree-server.exe `
  --addr 127.0.0.1:7420 `
  --data D:\worktree-data `
  --admin-dir C:\worktree\admin `
  --allow-registration=false
```

</Tab>
</Tabs>

</Step>
<Step>

### Sign in

Open `http://127.0.0.1:7420/admin/` and sign in as `admin`. From the CLI:

```bash
wt login http://127.0.0.1:7420 -u admin
wt whoami http://127.0.0.1:7420
```

The admin account is stored in `meta.db`, so it persists across restarts.

</Step>
</Steps>

Passwords are hashed with argon2id. API tokens are stored only as SHA-256 hashes. See [Security](/docs/security).

## 4. Open or closed registration

By default, anyone who can reach the server can create an account with `wt register` or `POST /api/v1/auth/register`. For a private instance, start with `--allow-registration=false` (env `WT_ALLOW_REGISTRATION=false`).

<Callout type="info">
  On a closed instance, a server admin creates accounts with `wt admin account-create USERNAME --email EMAIL` (or `POST /api/v1/admin/accounts`), or invites existing accounts with `wt invite create`. Server admins can disable accounts afterwards from the **Accounts** page of the admin panel (`PATCH /api/v1/admin/accounts/{username}` with `{"disabled": true}`).
</Callout>

## 5. Put TLS in front

The server can serve TLS itself (`--tls-cert` / `--tls-key`; see [Operations](/docs/server/operations#tls)). Alternatively, bind it to localhost (`--addr 127.0.0.1:7420`), set `--trusted-proxies` to the proxy's address, and put a reverse proxy in front that:

- terminates TLS,
- forwards gRPC to the backend over **HTTP/2 cleartext (h2c)**,
- does not buffer `text/event-stream` responses (for live events), and
- allows request bodies up to 64 MiB (the gRPC message limit).

<Callout type="info" title="Examples">
  The proxy configurations below are starting points to adapt, not files shipped with W0rkTree.
</Callout>

<Tabs items={['Caddy', 'nginx']}>
<Tab value="Caddy">

```text
wt.example.com {
    reverse_proxy h2c://127.0.0.1:7420
}
```

Caddy obtains certificates automatically and speaks h2c to the backend for every request, which covers gRPC, REST, SSE, and the admin panel.

</Tab>
<Tab value="nginx">

```text
server {
    listen 443 ssl http2;
    server_name wt.example.com;

    ssl_certificate     /etc/ssl/wt.example.com/fullchain.pem;
    ssl_certificate_key /etc/ssl/wt.example.com/privkey.pem;

    client_max_body_size 64m;

    location / {
        if ($content_type ~* "^application/grpc") {
            grpc_pass grpc://127.0.0.1:7420;
        }
        proxy_pass http://127.0.0.1:7420;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_buffering off;
        proxy_read_timeout 1h;
    }
}
```

`grpc_pass` uses HTTP/2 to the backend; REST, SSE, and `/admin/` go through `proxy_pass`. `proxy_buffering off` and the long read timeout keep `/api/v1/events` streaming.

</Tab>
</Tabs>

<Callout type="warn" title="Client connections">
  `wt` connects to `https://` remote URLs over TLS (system and bundled root certificates), so clients use the proxy's or the server's `https://` URL.
</Callout>

If you serve the admin panel from a different origin than the API, list that origin in `WT_CORS_ORIGINS`. When the panel is served by the server at `/admin/`, no CORS setup is needed. See [Deployment](/docs/server/deployment).

## 6. Run it as a service

Example systemd unit at `/etc/systemd/system/worktree-server.service`:

```text
[Unit]
Description=W0rkTree server
After=network.target

[Service]
User=worktree
Environment=WT_ADDR=127.0.0.1:7420
Environment=WT_DATA=/var/lib/worktree
Environment=WT_ADMIN_DIR=/opt/worktree/admin
Environment=WT_ALLOW_REGISTRATION=false
ExecStart=/opt/worktree/bin/worktree-server
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now worktree-server
journalctl -u worktree-server -f
```

The server shuts down gracefully on `SIGTERM`, which is what `systemctl stop` sends. Use `--log-level` to adjust verbosity (for example `debug` while troubleshooting). All flags: [Configuration](/docs/server/configuration).

## 7. Back up the data directory

Back up the whole `--data` directory: `meta.db` and `objects/` together.

- `objects/` is content-addressed and write-once, so incremental copies (for example `rsync`) work well while the server runs.
- `meta.db` is a single bbolt file that the running server holds open. For a consistent copy, stop the server first, or take a filesystem-level snapshot (LVM, ZFS, or a cloud volume snapshot).

A simple, consistent nightly backup:

```bash
sudo systemctl stop worktree-server
sudo tar -C /var/lib -czf /backups/worktree-$(date +%F).tar.gz worktree
sudo systemctl start worktree-server
```

To restore, stop the server, replace the data directory with the backup, and start it again. Test restores regularly on a spare machine.

## 8. Upgrade

<Steps>
<Step>

### Read the changelog

W0rkTree is pre-1.0. Check the [Changelog](/changelog) for breaking changes before upgrading.

</Step>
<Step>

### Build the new version

Pull the new source and rebuild the server and admin panel as in step 1.

</Step>
<Step>

### Back up, swap, restart

Stop the server, back up the data directory, replace the binary and the admin `dist` files, and start the server again.

</Step>
<Step>

### Verify

Check `/healthz` reports the new version, then sign in to the admin panel and run `wt fetch` from a client.

</Step>
</Steps>

Upgrade clients (`wt`, `worktree-bg`) by rebuilding them from the same source version.

## 9. Health checks and monitoring

| Endpoint | Auth | Returns |
|---|---|---|
| `GET /healthz` | none | `{"status":"ok","version":"...","uptime_seconds":N}` |
| `GET /metrics` | none | Prometheus text format |
| `GET /api/v1/admin/stats` | server admin | Counts of `tenants`, `accounts`, `trees`, `branches`, `snapshots`, `staged`, `objects`, and `storage_bytes` |

```bash
curl -fsS http://127.0.0.1:7420/healthz
```

Point your load balancer or uptime checker at `/healthz` and your Prometheus at `/metrics`. Watch the audit log (**Audit log** page, or `GET /api/v1/audit`) for security-relevant actions. See [Monitoring](/docs/server/monitoring).

## Checklist

- [ ] Server and admin panel built from the same source version
- [ ] Data directory on durable storage, owned by a dedicated user
- [ ] First admin created, password stored in a secret manager
- [ ] Registration policy chosen
- [ ] Server bound to localhost behind a TLS proxy with h2c to the backend
- [ ] Nightly backups of the whole data directory, with a tested restore
- [ ] `/healthz` and `/metrics` monitored
