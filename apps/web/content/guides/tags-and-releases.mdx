A **tag** is a named, fixed pointer to one snapshot, with an optional message, the tagger and a creation time. Tags belong to a tree, so each nested tree can have its own release line.

```text
wt tag [list] | [create] NAME [REV] [-m MSG] [--sign] | delete NAME | verify NAME | push NAME
```

## Creating and listing tags

```bash
wt tag create v1.0.0 -m "First stable release"   # tags HEAD
wt tag create v0.9.0 4f9c2a1e                     # tags an older snapshot
wt tag create v1.0.1 release-1.x                  # tags a branch tip
wt tag                                            # list: name, target, tagger, date, message
```

- `REV` defaults to `HEAD` and accepts any [revision](/docs/cli#revision-syntax).
- Creating a tag that already exists fails. Tags never move: to point a name somewhere else, delete it and create it again (locally only; see below).
- Each tag records its tagger and creation time; set `user.name` and `user.email` with [`wt config`](/docs/cli/repository#wt-config) so they identify you.
- A tag name works anywhere a revision does: `wt log v1.0.0`, `wt diff v1.0.0 HEAD --stat`, `wt restore docs/ --from v1.0.0`.

## Signed tags

A signed tag proves who created it: an Ed25519 signature over the tag's name, target snapshot, message, tagger and time, made with the same key you use for [snapshot signing](/docs/cli/signing).

```bash
wt identity generate laptop && wt identity register laptop   # once
wt config set signing.key laptop --global

wt tag v1.2.0 -m "Release 1.2.0" --sign     # or set signing.auto = true to sign every tag
wt tag push v1.2.0                          # shows the server's reason if it refuses the tag
wt tag verify v1.2.0                        # check the local copy against your keys
wt tag verify v1.2.0 --remote --account ada # check the server's copy against ada's registered keys
```

The server verifies the signature against the signer's registered keys when the tag is pushed (or created over REST, or by a release) and marks it **verified**, with the key owner as signer. A tag whose signature does not verify is refused. To require signatures on release tags, protect them:

```bash
wt protect tag set "v*" --no-delete --no-move --require-signed
```

Unsigned tags matching `v*` are then refused with `signature_required`. See [Signed tags](/docs/server/release-integrity#signed-tags).

## Sharing tags

Tags travel with branches:

| Command | Tags |
|---|---|
| `wt push` | Uploads every local tag of the tree that the server does not have yet. A refused tag is logged and does not fail the push. |
| `wt tag push NAME` | Uploads one tag and fails with the server's reason when it is refused. |
| `wt fetch`, `wt pull` | Downloads remote tags. |
| `wt clone` | Brings all tags of the server tree. |

```bash
wt tag create v1.1.0 -m "Search and filters"
wt push
```

Pushing a tag requires `tree:write` on the server tree, like pushing a branch. Tags are listed by `GET /api/v1/trees/{tenant}/{tree}/tags` ([REST API](/docs/server/rest-api#tags)), shown in the [admin panel](/guides/admin-panel), and published as `tag.pushed` events on the [SSE stream](/docs/server/events).

<Callout type="warn" title="Deleting tags">
`wt tag delete NAME` removes the tag from your worktree only, and the next `wt fetch` brings a pushed tag back. Deleting a server tag needs `tree:admin` (`wt trees tag-delete`), and tag protections (`wt protect tag set`) can forbid moving or deleting tags. Treat pushed tags as permanent and pick names carefully.
</Callout>

## Release archives

```text
wt archive [REV] -o FILE [--format tar.gz|zip]
```

`wt archive` writes the files of one snapshot into a `tar.gz` or `zip` file. Only the tree's files are included: no history, no `.wt/` metadata, no ignored files (they were never snapshotted), and no files of nested trees.

```bash
wt archive v1.0.0 -o my-project-1.0.0.tar.gz --format tar.gz
wt archive v1.0.0 -o my-project-1.0.0.zip --format zip
wt archive -o snapshot.tar.gz --format tar.gz        # HEAD
wt --tree frontend archive v2.3.0 -o frontend-2.3.0.zip --format zip
```

The archive is built from the snapshot, not from your working directory, so uncommitted changes never end up in a release file.

## A release workflow

<Steps>
<Step>

### Get up to date and clean

```bash
wt switch main
wt pull
wt status          # should show no changes
```

</Step>
<Step>

### Record the release

Optionally record version bumps as a snapshot first, then tag it (signed):

```bash
wt snapshot -m "Release 1.2.0"
wt tag create v1.2.0 -m "Release 1.2.0" --sign
```

If nothing changed, `wt snapshot -m "Release 1.2.0" --allow-empty` creates an explicit release marker snapshot.

</Step>
<Step>

### Publish the tag

```bash
wt push
```

If the push is rejected because `main` moved on the server, `wt pull` and push again; the tag stays on the snapshot you chose.

</Step>
<Step>

### Build the release files

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
version=1.2.0
wt archive "v$version" -o "dist/my-project-$version.tar.gz" --format tar.gz
wt archive "v$version" -o "dist/my-project-$version.zip" --format zip
sha256sum dist/my-project-$version.*
```

</Tab>
<Tab value="PowerShell">

```powershell
$version = '1.2.0'
wt archive "v$version" -o "dist\my-project-$version.tar.gz" --format tar.gz
wt archive "v$version" -o "dist\my-project-$version.zip" --format zip
Get-FileHash "dist\my-project-$version.*" -Algorithm SHA256
```

</Tab>
</Tabs>

Keep `dist/` in your ignore rules (`wt ignore add "dist/"`) so release files are never snapshotted.

</Step>
<Step>

### Publish a server release

A server release attaches notes and asset files to the tag. The server computes a SHA-256 for every uploaded asset and can generate an SPDX 2.3 SBOM of the tagged snapshot:

```bash
wt release create v1.2.0 --name "1.2.0" --notes-file CHANGELOG.md --draft --sbom
wt release upload v1.2.0 dist/my-project-1.2.0.tar.gz dist/my-project-1.2.0.zip
wt release edit v1.2.0 --publish
wt release checksums v1.2.0          # the SHA256SUMS of the assets
wt release show v1.2.0               # "verified": the tag is signed and still points at the release
```

`--sbom` attaches `sbom.spdx.json` (files with SHA-1, SHA-256 and BLAKE3 hashes and the SPDX ids of the tree's [license rules](/docs/server/licensing)); `wt release sbom v1.2.0` regenerates it later. See [Checksums](/docs/server/release-integrity#checksums) and [SBOM](/docs/server/release-integrity#sbom).

</Step>
</Steps>

### Verifying a release

Consumers download the assets and verify them in one step:

```bash
wt release download v1.2.0 --in acme/my-project -o ./downloads
wt release verify v1.2.0 --in acme/my-project -d ./downloads
```

`wt release verify` fetches the release, its `SHA256SUMS` and the server's tag record, verifies the tag signature itself (against your local keys and the signer's registered keys; `--account USER` trusts another account's keys too), checks that the tag still points at the release's snapshot, and hashes every downloaded asset. It exits `1` on an unsigned tag (unless `--allow-unsigned`), a bad signature, a moved tag, a checksum mismatch, an unlisted asset, or a missing file (unless `--ignore-missing`). See [Verifying a release](/docs/server/release-integrity#verifying-a-release).

### Maintenance releases

Branch from a tag to patch an older release:

```bash
wt branch create release-1.2 --from v1.2.0
wt switch release-1.2
# fix, then
wt snapshot -m "Fix crash on empty input"
wt tag create v1.2.1 -m "Release 1.2.1"
wt push --branch release-1.2
```

Protect release branches on the server with [branch protection](/guides/branch-protection) if changes to them should be reviewed.

### Exporting a release to Git

Consumers that need a Git tag can get one from [`wt git export`](/guides/git-interop), which converts tags along with snapshots:

```bash
wt git export ../my-project-git
git -C ../my-project-git push origin v1.2.0   # after adding a Git remote named origin
```

To keep a Git copy up to date without a working copy, a tree admin can add a server-side [Git mirror](/docs/server/mirrors) (`wt mirror add URL`); it pushes mirrored branches and tags after every push.

<Callout type="info" title="Not built yet">
`SHA256SUMS` is not signed yet: the tag signature covers the snapshot, not the asset files, so a compromised server could replace an asset together with its checksum. A detached signature over `SHA256SUMS` is on the [roadmap](/roadmap).
</Callout>
