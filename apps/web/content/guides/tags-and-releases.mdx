A **tag** is a named, fixed pointer to one snapshot, with an optional message, the tagger and a creation time. Tags belong to a tree, so each nested tree can have its own release line.

```text
wt tag [list] | create NAME [REV] [-m MSG] | delete NAME
```

## Creating and listing tags

```bash
wt tag create v1.0.0 -m "First stable release"   # tags HEAD
wt tag create v0.9.0 4f9c2a1e                     # tags an older snapshot
wt tag create v1.0.1 release-1.x                  # tags a branch tip
wt tag                                            # list: name, target, tagger, date, message
```

- `REV` defaults to `HEAD` and accepts any [revision](/docs/cli#revision-syntax).
- Creating a tag that already exists fails. Tags never move: to point a name somewhere else, delete it and create it again (locally only; see below).
- Each tag records its tagger and creation time; set `user.name` and `user.email` with [`wt config`](/docs/cli/repository#wt-config) so they identify you.
- A tag name works anywhere a revision does: `wt log v1.0.0`, `wt diff v1.0.0 HEAD --stat`, `wt restore docs/ --from v1.0.0`.

## Sharing tags

Tags travel with branches:

| Command | Tags |
|---|---|
| `wt push` | Uploads every local tag of the tree that the server does not have yet. |
| `wt fetch`, `wt pull` | Downloads remote tags. |
| `wt clone` | Brings all tags of the server tree. |

```bash
wt tag create v1.1.0 -m "Search and filters"
wt push
```

Pushing a tag requires `tree:write` on the server tree, like pushing a branch. Tags are listed by `GET /api/v1/trees/{tenant}/{tree}/tags` ([REST API](/docs/server/rest-api#tags)), shown in the [admin panel](/guides/admin-panel), and published as `tag.pushed` events on the [SSE stream](/docs/server/events).

<Callout type="warn" title="Deleting tags">
`wt tag delete NAME` removes the tag from your worktree only, and the next `wt fetch` brings a pushed tag back. Deleting a server tag needs `tree:admin` (`wt trees tag-delete`), and tag protections (`wt protect tag set`) can forbid moving or deleting tags. Treat pushed tags as permanent and pick names carefully.
</Callout>

## Release archives

```text
wt archive [REV] -o FILE [--format tar.gz|zip]
```

`wt archive` writes the files of one snapshot into a `tar.gz` or `zip` file. Only the tree's files are included: no history, no `.wt/` metadata, no ignored files (they were never snapshotted), and no files of nested trees.

```bash
wt archive v1.0.0 -o my-project-1.0.0.tar.gz --format tar.gz
wt archive v1.0.0 -o my-project-1.0.0.zip --format zip
wt archive -o snapshot.tar.gz --format tar.gz        # HEAD
wt --tree frontend archive v2.3.0 -o frontend-2.3.0.zip --format zip
```

The archive is built from the snapshot, not from your working directory, so uncommitted changes never end up in a release file.

## A release workflow

<Steps>
<Step>

### Get up to date and clean

```bash
wt switch main
wt pull
wt status          # should show no changes
```

</Step>
<Step>

### Record the release

Optionally record version bumps as a snapshot first, then tag it:

```bash
wt snapshot -m "Release 1.2.0"
wt tag create v1.2.0 -m "Release 1.2.0"
```

If nothing changed, `wt snapshot -m "Release 1.2.0" --allow-empty` creates an explicit release marker snapshot.

</Step>
<Step>

### Publish the tag

```bash
wt push
```

If the push is rejected because `main` moved on the server, `wt pull` and push again; the tag stays on the snapshot you chose.

</Step>
<Step>

### Build the release files

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
version=1.2.0
wt archive "v$version" -o "dist/my-project-$version.tar.gz" --format tar.gz
wt archive "v$version" -o "dist/my-project-$version.zip" --format zip
sha256sum dist/my-project-$version.*
```

</Tab>
<Tab value="PowerShell">

```powershell
$version = '1.2.0'
wt archive "v$version" -o "dist\my-project-$version.tar.gz" --format tar.gz
wt archive "v$version" -o "dist\my-project-$version.zip" --format zip
Get-FileHash "dist\my-project-$version.*" -Algorithm SHA256
```

</Tab>
</Tabs>

Keep `dist/` in your ignore rules (`wt ignore add "dist/"`) so release files are never snapshotted.

</Step>
</Steps>

### Maintenance releases

Branch from a tag to patch an older release:

```bash
wt branch create release-1.2 --from v1.2.0
wt switch release-1.2
# fix, then
wt snapshot -m "Fix crash on empty input"
wt tag create v1.2.1 -m "Release 1.2.1"
wt push --branch release-1.2
```

Protect release branches on the server with [branch protection](/guides/branch-protection) if changes to them should be reviewed.

### Exporting a release to Git

Consumers that need a Git tag can get one from [`wt git export`](/guides/git-interop), which converts tags along with snapshots:

```bash
wt git export ../my-project-git
git -C ../my-project-git push origin v1.2.0   # after adding a Git remote named origin
```
