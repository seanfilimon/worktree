This tutorial walks through the whole v0.2.0 workflow on one machine: local history first, then a local server, then a second clone that talks to the first one through the server. Every command shown is part of the documented [CLI surface](/docs/cli).

<Callout type="info" title="Build from source">
v0.2.0 is pre-1.0 and is installed from source only. There are no prebuilt binaries or package-manager installs yet.
</Callout>

## Part 1: local history

<Steps>
<Step>

### Install `wt`, `worktree-bg` and the server

Follow [Installation](/docs/installation). In short, from a checkout of the repository:

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
cargo install --path crates/worktree-cli
cargo install --path crates/worktree-bg
cd services/server-go && go build -o worktree-server .
```

</Tab>
<Tab value="PowerShell">

```powershell
cargo install --path crates/worktree-cli
cargo install --path crates/worktree-bg
cd services/server-go; go build -o worktree-server.exe .
```

</Tab>
</Tabs>

Check that the client is on your `PATH`:

```bash
wt --help
```

</Step>
<Step>

### Create a worktree

```bash
mkdir hello
cd hello
wt init
```

`wt init` creates `.wt/` in the current directory with a **root tree** named after the directory (here `hello`) and an empty default branch `main`. No snapshot exists yet. Use `wt init --name N --branch B` to pick a different name or default branch.

Optionally set the author recorded on your snapshots (otherwise `wt` falls back to your server username, then your OS user):

```bash
wt config set user.name "Alice Example"
wt config set user.email alice@example.com
```

</Step>
<Step>

### Add some files

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
echo "# Hello" > README.md
mkdir src
echo 'fn main() { println!("hello"); }' > src/main.rs
```

</Tab>
<Tab value="PowerShell">

```powershell
Set-Content -Encoding utf8 README.md "# Hello"
New-Item -ItemType Directory src | Out-Null
Set-Content -Encoding utf8 src\main.rs 'fn main() { println!("hello"); }'
```

</Tab>
</Tabs>

<Callout type="warn" title="Windows PowerShell 5.1">
Plain `>` redirection in Windows PowerShell 5.1 writes UTF-16 files, which `wt diff` treats as binary. Use `Set-Content -Encoding utf8` (or PowerShell 7) for text files.
</Callout>

</Step>
<Step>

### Check the status

```bash
wt status
```

Both files are listed as **added**: `wt status` compares the working directory with the head snapshot of the current branch, and there is no head yet. There is no staging area: the next snapshot captures the whole working tree.

</Step>
<Step>

### Take a snapshot

```bash
wt snapshot -m "First snapshot"
```

The snapshot records every non-ignored file of the tree and advances `main` to it. Before it is written, added and modified files are scanned for secrets (AWS keys, GitHub tokens, private keys and similar). If something is found the snapshot is refused and the findings are listed; see [`wt snapshot`](/docs/cli/snapshots#wt-snapshot).

</Step>
<Step>

### Look at the history

```bash
wt log
wt log --oneline
```

Each snapshot has a UUID id (human output shows the first 8 characters), author, time and message. Any unique id prefix of 4 or more characters works as a revision, as do `HEAD`, `HEAD~1`, branch names and tags.

</Step>
<Step>

### Work on a branch

Create a branch and switch to it in one step:

```bash
wt switch -c feature
```

This is the same as `wt branch create feature` followed by `wt switch feature`. Now change a file and snapshot it:

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
echo "A tiny W0rkTree demo." >> README.md
wt diff
wt snapshot -m "Describe the project"
```

</Tab>
<Tab value="PowerShell">

```powershell
Add-Content -Encoding utf8 README.md "A tiny W0rkTree demo."
wt diff
wt snapshot -m "Describe the project"
```

</Tab>
</Tabs>

`wt switch` refuses to leave a branch with uncommitted changes unless you pass `--force` (which discards them), so snapshot first.

</Step>
<Step>

### Merge it back

```bash
wt switch main
wt merge feature
wt log --oneline
```

`main` has not moved since `feature` was created, so the merge is a **fast-forward**: `main` simply moves to the tip of `feature`. Pass `--no-ff` to always create a two-parent merge snapshot. When both branches have changed, `wt merge` runs a three-way merge and exits with code `3` if there are conflicts; see [Merge strategies](/guides/merge-strategies).

</Step>
</Steps>

## Part 2: a server and two clones

<Steps>
<Step>

### Start a local server

Open a **second terminal** in `services/server-go` and run:

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
./worktree-server --data ./wt-data --admin-password 'change-me-now'
```

</Tab>
<Tab value="PowerShell">

```powershell
.\worktree-server.exe --data .\wt-data --admin-password 'change-me-now'
```

</Tab>
</Tabs>

The server listens on `http://localhost:7420`: gRPC (h2c), REST, Server-Sent Events and the optional admin panel all share that one port. `--data` holds `meta.db` and the `objects/` store; `--admin-password` makes sure the server admin account (`admin`) exists. Leave it running. Check it with:

```bash
curl http://localhost:7420/healthz
```

All flags are in [Server configuration](/docs/server/configuration).

</Step>
<Step>

### Create an account

Back in the first terminal (inside `hello`):

```bash
wt register http://localhost:7420 -u alice -e alice@example.com
```

You are prompted for a password. Registration creates the account plus a **personal tenant** whose slug is your username (`alice`), and saves a token in `$WT_HOME/credentials.toml` (default `~/.wt`). If the account already exists, use `wt login http://localhost:7420 -u alice` instead.

To avoid the prompt in scripts, pipe the password with `--password-stdin` or set `WT_PASSWORD`:

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
printf '%s' "$ALICE_PASSWORD" | wt register http://localhost:7420 -u alice -e alice@example.com --password-stdin
# or
WT_PASSWORD="$ALICE_PASSWORD" wt login http://localhost:7420 -u alice
```

</Tab>
<Tab value="PowerShell">

```powershell
$env:ALICE_PASSWORD | wt register http://localhost:7420 -u alice -e alice@example.com --password-stdin
# or
$env:WT_PASSWORD = $env:ALICE_PASSWORD; wt login http://localhost:7420 -u alice
```

</Tab>
</Tabs>

Confirm with `wt whoami http://localhost:7420`.

</Step>
<Step>

### Add a remote and push

```bash
wt remote add origin http://localhost:7420 --tenant alice
wt push
```

`wt push` resolves the server tree `alice/hello` (the server-side name defaults to the local tree name), **creates it if it does not exist**, uploads only the objects the server is missing, and moves the server's `main` to your tip. Tags are pushed along with the branch. The server never accepts a push that does not descend from its current tip, and there is no force push.

</Step>
<Step>

### Clone it somewhere else

Go to the parent directory and clone the tree into `other`:

```bash
cd ..
wt clone http://localhost:7420 alice/hello other
cd other
wt log --oneline
```

The clone has the same snapshot ids as the original, a remote `origin` pointing at `alice` on the server, a local branch for every remote branch, and `main` checked out. Your saved credential is per server URL, so the clone can push without logging in again.

</Step>
<Step>

### Push from the clone, pull in the original

In `other`:

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
echo "Edited from the second clone." >> README.md
wt snapshot -m "Edit from other"
wt push
```

</Tab>
<Tab value="PowerShell">

```powershell
Add-Content -Encoding utf8 README.md "Edited from the second clone."
wt snapshot -m "Edit from other"
wt push
```

</Tab>
</Tabs>

Then in `hello`:

```bash
cd ../hello
wt pull
wt log --oneline
```

`wt pull` fetches the new snapshots and fast-forwards `main`. If both sides had new snapshots, it would merge exactly like `wt merge` (and exit with code `3` on conflicts). If you try to push from `hello` before pulling, the push is rejected because the server tip moved: pull, then push again.

</Step>
<Step>

### Share work in progress

Staged snapshots let teammates see what you are working on before you push. In `other`, change a file **without** snapshotting it and stage it:

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
cd ../other
echo "// work in progress" >> src/main.rs
wt stage
```

</Tab>
<Tab value="PowerShell">

```powershell
cd ..\other
Add-Content -Encoding utf8 src\main.rs "// work in progress"
wt stage
```

</Tab>
</Tabs>

In `hello`, list the team's staged work for this tree:

```bash
cd ../hello
wt status --team
```

You see the staged entry with its author, branch, change counts and time. In a real team the entry would come from a teammate's account; here both clones belong to `alice`. The server keeps at most one staged snapshot per tree, account and branch; a newer `wt stage` replaces it, and pushing that branch clears it. Staged snapshots are never part of branch history.

</Step>
<Step>

### Let the daemon do it automatically

The background daemon takes auto-snapshots after a period of inactivity and, when a remote and a credential exist, stages them for you:

```bash
wt daemon start
wt daemon watch
wt daemon status
```

Defaults: an auto-snapshot after 30 seconds without file events (or immediately once 50 files changed), with the message `auto: N files changed`, followed by an auto-stage because `sync.auto_stage = true`. The daemon never snapshots during a merge and never pushes. Stop it with `wt daemon stop`. See [Auto-tracking setup](/guides/auto-tracking-setup).

</Step>
</Steps>

## What you have now

| Where | What |
|---|---|
| `hello/.wt/` | Local object store, snapshots, branches and reflog of the root tree `hello`. |
| `other/.wt/` | A second worktree linked to the same server tree. |
| `services/server-go/wt-data/` | The server's `meta.db` and content-addressed `objects/`. |
| `$WT_HOME` (`~/.wt`) | Your saved token (`credentials.toml`) and daemon files. |

To browse the tree in a UI, build the [admin panel](/guides/admin-panel) (`cd apps/admin && npm install && npm run build`), restart the server with `--admin-dir` pointing at `apps/admin/dist` (from `services/server-go` that is `--admin-dir ../../apps/admin/dist`), and open `http://localhost:7420/admin/`.
