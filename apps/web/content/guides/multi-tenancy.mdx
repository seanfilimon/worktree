Every tree on a W0rkTree server belongs to a **tenant**. A tenant is the unit of ownership and membership: who can see a tree, who can push to it, and who can change its settings is decided by the caller's role in the tree's tenant plus the tree's visibility.

## Tenant kinds

| Kind | `kind` value | Created by | Slug |
|---|---|---|---|
| Personal | `user` | Automatically, when an account registers | The account's username |
| Organization | `org` | `POST /api/v1/tenants` (or the admin panel) | Chosen at creation: lowercase letters, digits, and `-` |

When `alice` registers, the server creates the account plus a personal tenant with slug `alice`, with `alice` as its owner. Personal tenants are great for experiments; use an organization for anything a team shares.

Trees are addressed as `TENANT/TREE`, for example `alice/notes` or `acme/app`.

## Create an organization

<Steps>
<Step>

### Get a token

Log in with the CLI (`wt login http://localhost:7420 -u alice`), or call the REST login endpoint, which returns a session token:

```bash
curl -s -X POST http://localhost:7420/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"correct horse battery staple"}'
```

The response is `{"token": "...", "account": {...}}`. Export the token as `WT_TOKEN` for the following steps.

</Step>
<Step>

### Create the tenant

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
curl -s -X POST http://localhost:7420/api/v1/tenants \
  -H "Authorization: Bearer $WT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"slug":"acme","name":"Acme Corp"}'
```

</Tab>
<Tab value="PowerShell">

```powershell
$headers = @{ Authorization = "Bearer $env:WT_TOKEN" }
Invoke-RestMethod -Method Post -Headers $headers -ContentType "application/json" `
  -Uri "http://localhost:7420/api/v1/tenants" `
  -Body '{"slug":"acme","name":"Acme Corp"}'
```

</Tab>
</Tabs>

The server answers `201` with the new tenant. Its `kind` is `org` and the caller becomes its `owner`:

```json
{
  "id": "9a3e...",
  "slug": "acme",
  "name": "Acme Corp",
  "kind": "org",
  "plan": "free",
  "created_at": "2026-10-24T10:00:00Z"
}
```

</Step>
<Step>

### Add members

Members are set by username with `PUT`, which both adds and changes a role:

```bash
curl -s -X PUT http://localhost:7420/api/v1/tenants/acme/members/bob \
  -H "Authorization: Bearer $WT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"role":"developer"}'
```

List members with `GET /api/v1/tenants/acme/members` (each entry is `{"account": {...}, "role": "..."}`) and remove one with `DELETE /api/v1/tenants/acme/members/bob`. The person must already have an account on the server.

</Step>
</Steps>

You can do all of this in the admin panel too: **Tenants** to create an organization, then the tenant detail page to manage members. See the [Admin Panel guide](/guides/admin-panel).

## Roles

There are five built-in roles, from most to least privileged: `owner` > `admin` > `maintainer` > `developer` > `viewer`. Each role includes everything the roles below it can do.

| Role | Typical capabilities |
|---|---|
| `viewer` | Read trees, branches, snapshots, tags, staged WIP, and merge requests (`tree:read`). |
| `developer` | Everything above, plus push, stage, and tag (`tree:write`), create branches, and open merge requests. |
| `maintainer` | Everything above, plus approve and merge merge requests and delete (archive) branches. |
| `admin` | Everything above, plus create trees and administer them (`tree:admin`): branch protections, license rules, tree settings, and deleting trees. |
| `owner` | Everything above, plus tenant administration (`tenant:admin`): managing members and tenant settings. |

<Callout type="info">
  The server's IAM service is the authority on which role grants which action. See [Access Control](/docs/server/access-control) for the exact action list, including `tree:read`, `tree:write`, `tree:create`, `tree:admin`, `branch:create`, `branch:delete`, `mr:create`, `mr:approve`, `mr:merge`, `tenant:read`, `tenant:admin`, and `server:admin`.
</Callout>

**Server admins** are separate from tenant roles. An account with `is_admin` set can manage every account (`/api/v1/admin/accounts`), view server stats, and read the audit log across tenants. The first server admin is created by the server's `--admin-password` flag; see [Self-Hosting](/guides/self-hosting).

## Tree visibility

Each tree has a `visibility`:

| Visibility | Who can read |
|---|---|
| `private` | Members of the owning tenant only. |
| `internal` | Any authenticated account on the server. |
| `public` | Anyone, including anonymous clients. |

Visibility only affects **reads**. Writing always requires the right role in the owning tenant.

Create a tree explicitly with its visibility:

```bash
curl -s -X POST http://localhost:7420/api/v1/tenants/acme/trees \
  -H "Authorization: Bearer $WT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"app","description":"Main application","visibility":"private","default_branch":"main"}'
```

Change it later with `PATCH /api/v1/trees/acme/app` and a body such as `{"visibility":"internal"}`. A tree can also be created on first `wt push` if it does not exist yet and you are allowed to create trees in the tenant.

## Connect the CLI to a tenant

A remote names both the server and the tenant:

```bash
wt remote add origin http://localhost:7420 --tenant acme
wt login http://localhost:7420 -u bob
wt push
```

To get an existing tree, clone it by `TENANT/TREE`:

```bash
wt clone http://localhost:7420 acme/app
wt clone http://localhost:7420 acme/app ./acme-app
```

`wt clone` configures `[remote.origin]` with the URL and tenant for you. Reference: [`wt remote`](/docs/cli/remote#wt-remote), [`wt clone`](/docs/cli/remote#wt-clone).

## API tokens for CI and scripts

Session tokens from login last 30 days by default. For scripts, create a named **personal API token** instead, optionally with an expiry:

```bash
curl -s -X POST http://localhost:7420/api/v1/auth/tokens \
  -H "Authorization: Bearer $WT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"ci-nightly","ttl_hours":720}'
```

The response is `{"token": "...", "api_token": {...}}`. The raw `token` is shown **only once**: the server stores just its SHA-256 hash. The `api_token` object carries `id`, `account_id`, `name`, `created_at`, and, when set, `expires_at` and `last_used_at`.

- List your tokens with `GET /api/v1/auth/tokens`; revoke one with `DELETE /api/v1/auth/tokens/{id}`. The **Settings** page of the admin panel does the same.
- Send the token as `Authorization: Bearer <token>` on REST calls. The same bearer scheme is used in gRPC metadata.
- Tokens act with the full permissions of the account that created them. For CI, create a dedicated account, add it to the tenant with the smallest role that works (often `developer`, or `viewer` for read-only jobs), and create the token as that account.

For running `wt` itself in CI, log in non-interactively with a secret from your CI system:

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
printf '%s' "$CI_WT_PASSWORD" | wt login http://wt.internal:7420 -u ci-bot --password-stdin
```

</Tab>
<Tab value="PowerShell">

```powershell
$env:WT_PASSWORD = $env:CI_WT_PASSWORD
wt login http://wt.internal:7420 -u ci-bot
```

</Tab>
</Tabs>
