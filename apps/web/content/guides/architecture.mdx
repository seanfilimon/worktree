W0rkTree v0.2.0 ("v2 rebuild") is a client/server version control system. A Rust client works on a local `.wt/` repository and synchronizes with a Go server that holds the team's canonical history. This page explains the pieces, where data lives, and what happens on the wire for push, pull and stage.

## The big picture

```text
 wt (CLI, Rust) ──► worktree-sdk (Rust) ──► .wt/ on disk
      │                  │  remote (gRPC h2c + REST)
      │ ipc (JSON/TCP)   ▼
 worktree-bg (Rust) ──► worktree-server (Go, services/server-go) ──► bbolt meta + CAS objects
                              ▲ REST + SSE
                        apps/admin (React/Vite admin panel)
 worktree-git (Rust) — Git import/export over worktree-sdk
 apps/web (Next.js) — marketing + docs site
```

## Components

| Component | Language / location | Role |
|---|---|---|
| `wt` | Rust, crate `worktree-cli` | The command-line client. Parses commands and prints human or `--json` output; all real work is delegated to the SDK. |
| `worktree-sdk` | Rust, `crates/worktree-sdk` | The engine. `Repository` manages `.wt/` (snapshots, branches, tags, merges, reflog, ignore rules); `diff` and `merge` are pure algorithms; `scan` is the pre-snapshot secret scanner; `remote` implements push, fetch, pull, clone, stage and login; `ipc` defines the daemon protocol. |
| `worktree-protocol` | Rust, `crates/worktree-protocol` | Owns `proto/sync.proto` (`worktree.sync.v1.SyncService`), the Rust/Go wire contract. Rust code is generated at build time with a vendored `protoc`. |
| `worktree-bg` | Rust, crate `worktree-bg` | The background daemon. Watches worktrees, takes auto-snapshots, and stages work in progress. Controlled with `wt daemon`. |
| `worktree-server` | Go, `services/server-go` | The team server. Stores canonical history, authenticates accounts, authorizes every action, enforces branch protection and license rules, keeps staged snapshots, streams events and serves the admin panel. |
| Admin panel | React + Vite, `apps/admin` | A static single-page app served by the server at `/admin/`. Talks only to the REST API and the SSE stream. |
| `worktree-git` | Rust, `crates/worktree-git` | The Git bridge behind `wt git import` and `wt git export` (libgit2). Works through the SDK. |
| Website | Next.js, `apps/web` | This site. |

## One port

The server listens on a single address (default `:7420`) and multiplexes everything on it using cleartext HTTP/2 (h2c) and HTTP/1.1:

| Traffic | Recognised by | Used by |
|---|---|---|
| gRPC `SyncService` | `Content-Type: application/grpc*` | `wt`, `worktree-bg` (object transfer, push, pull, stage, branches, tags, ping) |
| REST `/api/v1/...` | path | `wt` (register, login), admin panel, scripts |
| SSE `/api/v1/events` | path | admin panel dashboard, tools |
| `/healthz`, `/metrics` | path | load balancers, Prometheus |
| `/admin/...` | path | browsers |

So a remote URL is just the server origin, such as `http://localhost:7420`, and one firewall rule or one reverse-proxy route covers the whole service.

<Callout type="warn" title="No built-in TLS">
The server does not terminate TLS in v0.2.0. Put it behind a reverse proxy that terminates TLS and forwards HTTP/2 cleartext (h2c) to the backend so gRPC keeps working. Built-in TLS and a QUIC transport are on the Roadmap. See [Deployment](/docs/server/deployment).
</Callout>

## Local vs. server responsibilities

| Concern | Local (`wt` + SDK + daemon) | Server |
|---|---|---|
| Snapshots | Created locally by `wt snapshot`, `wt merge`, `wt revert` and the daemon. Work fully offline. | Stores pushed snapshots; immutable once stored. |
| Branches | Local refs per tree; archived (soft-deleted), never hard-deleted. | Canonical branch tips; move only forward to descendants, with compare-and-swap. |
| Merging | All merging (fast-forward or three-way) happens locally. Conflicts are resolved locally. | Merge requests only **fast-forward** the target; the server never creates merge snapshots. |
| Secret scanning | Before every snapshot, on added and modified files. | Not repeated. |
| Ignore rules | Built-ins, `.wt/ignore`, `.wtignore`. | Not involved: ignored files are never in a snapshot. |
| Identity | Tokens in `$WT_HOME/credentials.toml`. | Accounts (argon2id password hashes), session and API tokens (stored as SHA-256), tenants, roles. |
| Policy | Reports rejections. | Enforces `tree:write`, branch protection, approvals, license rules. |
| Work in progress | `wt stage` or the daemon uploads it. | Keeps at most one staged snapshot per tree, account and branch. |
| Audit and events | Local reflog per tree. | Append-only audit log, SSE event stream. |

## Data stores

**Local, per worktree (`.wt/`).** A BLAKE3 content-addressed object store (`objects/<hh>/<62 hex>`) holding blobs (raw file bytes) and manifests (sorted file lists), snapshot records as JSON (`snapshots/<id>.json`), and per-tree state under `trees/<tree>/`: `HEAD`, branch refs, remote-tracking refs, tags, a stat-cache index, the append-only `reflog.jsonl` and merge state. Configuration is `.wt/config.toml`. The full layout is in [Local layout](/docs/protocol/local-layout).

**Local, per user (`$WT_HOME`, default `~/.wt`).** `credentials.toml` (tokens per server), and the daemon's `bg.toml`, `bg.json` and `bg.log`. See [Config model](/guides/config-model).

**Server (`--data`, default `./wt-data`).** `meta.db`, an embedded bbolt database with every record except file content (accounts, tenants, trees, branches, snapshots, tags, staged snapshots, protections, license rules, merge requests, audit log), and `objects/`, the same BLAKE3 content-addressed layout as the client. Objects are deduplicated across all trees and tenants. See [Storage](/docs/server/storage).

Objects are identical on both sides: an object's name is the BLAKE3-256 hash of its exact bytes, so the client and server agree on what the other is missing without any translation. Snapshots travel separately as records with UUID v4 ids. See [Object model](/docs/protocol/object-model).

## How a push flows

1. `wt push` asks the SDK to push the current branch of the selected tree to `origin`.
2. The SDK calls `ResolveTree` with create-if-missing, so the server tree `<tenant>/<tree>` exists.
3. It learns the server's tip for the branch, then uses `Negotiate` to find which manifests and blobs the server lacks, and streams them with `UploadObjects`.
4. It sends `Push` with the old tip it expects, the new tip and the new snapshot records.
5. The server checks `tree:write`, branch protection, license rules on changed paths, that every referenced object and parent snapshot is present, and that the new tip **descends from the current server tip**. Otherwise it rejects the push (a moved tip comes back as a conflict carrying the server tip).
6. The tip moves with compare-and-swap. The server clears the pusher's staged snapshot for that branch, publishes a `branch.pushed` event and writes a `branch.push` audit entry.
7. The client updates `refs/remotes/origin/<branch>` and pushes local tags the server does not have.

## How a pull flows

1. `wt pull` (or `wt fetch`) sends `Pull` with the client's current tip.
2. The server returns the missing snapshot records, oldest first, plus the hashes of every manifest and blob they reference.
3. The client downloads only the objects it lacks with `DownloadObjects` and updates `refs/remotes/origin/*`. `wt fetch` stops here.
4. `wt pull` then integrates `origin/<branch>`: a fast-forward plus checkout when possible, otherwise a local three-way merge (exit code `3` on conflicts).

## How staging flows

1. `wt stage`, or the daemon after an auto-snapshot when `sync.auto_stage = true`, builds a manifest from the **working directory**.
2. Missing objects are uploaded exactly as for a push.
3. A `Stage` request records the staged snapshot with the changed paths and added/modified/deleted counts relative to head.
4. The server replaces any earlier stage by the same account on the same branch and publishes an event. Teammates see it with `wt status --team` (the `ListStaged` RPC), the REST API or the admin panel.

Staged snapshots never move a branch and never appear in `wt log`. See [Staged visibility](/guides/staged-visibility).

The wire-level details of all three flows are in [Sync protocol](/docs/protocol/sync-protocol).

## The daemon

`worktree-bg` runs per user and is controlled by `wt daemon` over newline-delimited JSON on a loopback TCP port recorded in `$WT_HOME/bg.json`. For each watched worktree it debounces file events (`[auto_snapshot]` settings), takes snapshots marked auto-generated with the message `auto: N files changed`, and stages them when a remote and credential exist. It never snapshots during a merge and never pushes. See [`wt daemon`](/docs/cli/daemon) and [SDK IPC](/docs/sdk/ipc).

## Where the admin panel fits

The admin panel is a static build (`apps/admin/dist`) served by the server when started with `--admin-dir`. It has no backend of its own: it signs in through `/api/v1/auth/login`, calls the REST API with a bearer token, and subscribes to `/api/v1/events` for live activity. Merge requests, branch protections, license rules, tenants and members are managed there or through the REST API; there are no `wt` subcommands for them in v0.2.0. See [Admin panel](/guides/admin-panel).

## Why a Rust client and a Go server

- **Rust on the client** gives one native binary per platform with fast hashing and filesystem scanning, and lets the CLI, the daemon and the Git bridge share one SDK crate, so their behaviour is identical.
- **Go on the server** provides an HTTP/2 and gRPC stack that can serve gRPC, REST, SSE and static files from one listener. The server is pure Go (no cgo), so it builds with `go build` alone and cross-compiles easily, and its embedded bbolt database needs no external service.
- **A protobuf contract** (`sync.proto`) is the only coupling between the two, so each side can evolve independently as long as the contract holds.

## Not in v0.2.0

<Callout type="warn" title="Roadmap">
QUIC transport, built-in TLS, a virtual filesystem with lazy loading, chunked large-file transfer, snapshot signing, encryption at rest, OAuth/SSO and live Git mirroring are planned but not shipped. See the [roadmap](/roadmap).
</Callout>
