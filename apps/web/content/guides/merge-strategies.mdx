All merging in W0rkTree happens **locally**, in `wt merge` and `wt pull`. The server never merges content: it only accepts pushes that descend from its tip and, for merge requests, fast-forwards a target branch. This page covers the local merge and how it combines with server-side merge requests.

```text
wt merge SOURCE [-m MSG] [--no-ff] | --continue [-m MSG] | --abort
```

`SOURCE` is any [revision](/docs/cli#revision-syntax) of the current tree: a branch, `origin/<branch>`, a tag or a snapshot id prefix. The working tree must be clean before you start.

## The four outcomes

| Outcome | When | Result | Exit code |
|---|---|---|---|
| Up to date | `SOURCE` is already an ancestor of the current branch. | Nothing changes. | `0` |
| Fast-forward | The current branch tip is an ancestor of `SOURCE`. | The branch tip moves to `SOURCE` and its files are checked out. No new snapshot. | `0` |
| Merged | Both sides have new snapshots and the merge is clean. | A new **merge snapshot** with two parents (current tip first, then `SOURCE`). | `0` |
| Conflicts | Both sides changed something in incompatible ways. | The working tree holds the partial merge with conflicts to resolve. | `3` |

The reflog records `fast-forward` or `merge` accordingly.

### Fast-forward or merge snapshot

By default `wt merge` fast-forwards whenever it can. That keeps history linear but leaves no record that a branch was merged. Pass `--no-ff` to always create a merge snapshot:

```bash
wt switch main
wt merge feature/search --no-ff -m "Merge feature/search"
wt log -n 3
```

| Use | When |
|---|---|
| Default (fast-forward when possible) | Short-lived branches, personal work, pulling a teammate's changes. |
| `--no-ff` | Feature branches whose integration you want visible in history, or when you may want to `wt revert` the whole feature as one snapshot later. |

## How the three-way merge works

<Steps>
<Step>

### Find the merge base

The base is the best common ancestor of the two tips: an ancestor reachable from both that is not itself an ancestor of another common ancestor. Ties are broken by the shortest distance from the current tip, then by id. Two tips that share no history have no merge base.

</Step>
<Step>

### Merge the manifests path by path

| Situation | Result |
|---|---|
| Unchanged on both sides, or changed identically | Kept once. |
| Changed (or added, or deleted) on one side only | That side's version is taken. |
| Deleted on one side, unchanged on the other | Deleted. |
| Modified on one side, deleted on the other | `modify_delete` conflict. |
| Text changed on both sides | Line-based three-way merge (next step). |
| Added on both sides with different content | Two-way text merge; `add_add` conflict if lines overlap. |
| Binary changed on both sides | `binary` conflict; our version is kept in the working tree. |

</Step>
<Step>

### Merge text line by line

Text files changed on both sides are merged with diff3 semantics against the base: non-overlapping edits from both sides are combined, identical edits are taken once, and only overlapping edits become a `content` conflict with markers written into the file. A file is treated as binary if it contains a NUL byte in its first 8 KiB or is not valid UTF-8.

</Step>
</Steps>

The algorithm is specified in [Merge and diff](/docs/protocol/merge-and-diff).

## Conflicts

### Conflict kinds

| Kind | Cause | How to resolve |
|---|---|---|
| `content` | Overlapping line edits. | Edit the file and remove all markers. |
| `add_add` | Both sides added the path with different content. | Edit the merged file (markers appear where lines overlap). |
| `modify_delete` | One side modified, the other deleted. | Keep the file (with the content you want) or delete it. |
| `binary` | A binary file changed on both sides. | "Ours" is in the working tree; replace it with the version you want. |

### Markers

Markers are diff3-style and labelled with the branch names, so you can see the base as well as both sides:

```text
<<<<<<< main
const TIMEOUT_SECS: u64 = 30;
||||||| base
const TIMEOUT_SECS: u64 = 10;
=======
const TIMEOUT_SECS: u64 = 60;
>>>>>>> feature/retry
```

Keep the lines you want and delete every marker line (`<<<<<<<`, `|||||||`, `=======`, `>>>>>>>`).

### State on disk

While a merge is in progress:

- `.wt/trees/<tree>/MERGE_STATE.json` stores the source branch and tip, the target tip, the base, the conflicts and the merge message;
- `.wt/conflicts/<tree>.json` lists the conflicts (`path` and `kind`) for editors and scripts;
- `wt status` shows the merge and the conflicted paths;
- the daemon does not auto-snapshot that tree.

## Resolve, finish or abort

<Steps>
<Step>

### Start the merge

```bash
wt merge feature/retry
```

Exit code `3` means conflicts. Branch on the exit code in scripts, not on the message text.

</Step>
<Step>

### Resolve each conflict

```bash
wt status                 # conflicted paths
wt diff                   # what the merge produced so far
```

Edit the files, remove all markers, and keep or delete `modify_delete` paths.

</Step>
<Step>

### Finish

```bash
wt merge --continue -m "Merge feature/retry"
```

`--continue` fails while conflict markers remain. Alternatively, `wt snapshot -m MSG` completes the merge once the markers are gone; either way the result is a snapshot with **two parents**.

</Step>
</Steps>

To give up instead, restore the pre-merge state:

```bash
wt merge --abort
```

### Scripting

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
wt merge feature/retry
case $? in
  0) echo "merged" ;;
  3) wt --json status | jq -r '.merge.conflicts[].path'; exit 3 ;;
  *) exit 1 ;;
esac
```

</Tab>
<Tab value="PowerShell">

```powershell
wt merge feature/retry
switch ($LASTEXITCODE) {
  0 { 'merged' }
  3 { (wt --json status | ConvertFrom-Json).merge.conflicts | ForEach-Object path; exit 3 }
  default { exit 1 }
}
```

</Tab>
</Tabs>

## Merging during `wt pull`

`wt pull` fetches and then integrates `origin/<branch>` into the local branch exactly like `wt merge origin/<branch>`: fast-forward when possible, otherwise a merge snapshot, or exit code `3` with conflicts to resolve the same way. This is also how you recover from a rejected push: the server only accepts pushes that descend from its tip, so pull, resolve, and push again.

```bash
wt push        # rejected: the server tip moved
wt pull        # merge origin/main into main
wt push
```

There is no force push. Locally you can also replay unpushed work with [`wt rebase`](/docs/cli/history-rewriting) or copy single snapshots with `wt cherry-pick`; pushed history is never rewritten.

## Merge requests on the server

On protected branches you do not push directly; you open a **merge request** through the [REST API](/docs/server/rest-api#merge-requests) or the [admin panel](/guides/admin-panel). From the CLI, use [`wt mr`](/docs/cli/merge-requests#wt-mr).

The server merges with one of three [methods](/docs/server/merging): `fast-forward` (move the target to the source tip), `merge` (the server writes a three-way merge snapshot) or `squash` (one new snapshot with the combined changes); `wt mr merge N --method merge` picks one. When the two sides conflict the server answers `409 merge_conflict` with the paths, and you resolve locally: merge the target into the source and push:

```bash
wt pull --branch main
wt switch feature/retry
wt merge main -m "Merge main into feature/retry"
# resolve conflicts if any, then: wt merge --continue
wt push --branch feature/retry
```

The source now descends from the target, and the merge request fast-forwards. Approval requirements come from branch protection rules; see [Branch protection](/guides/branch-protection).

<Callout type="warn" title="Roadmap">
Besides approvals and fast-forwardability, branch protection can require passing CI checks, signed snapshots, linear history and no open blocking TODOs before a merge. Check a merge request with `wt mr checks`. See [Reviews, CI and merges](/docs/cli/merge-requests).
</Callout>

## Undoing a merge

History is append-only, so a merge is undone with a new snapshot. `wt revert REV` undoes a snapshot's changes relative to its **first parent**; for a merge snapshot that is the branch you merged into, so reverting the merge snapshot removes everything the merge brought in. See [Reflog and recovery](/guides/reflog-and-recovery).
