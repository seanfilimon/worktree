A worktree always has one **root tree**, created by `wt init` and named after the directory. You can register sub-directories as **nested trees**: independently versioned sub-projects that live in the same working directory but have their own history. Think of them as the W0rkTree answer to Git submodules, without a second repository to clone.

## What each tree has

| Per tree | Shared by the worktree |
|---|---|
| Branches and the current branch (`HEAD`) | `.wt/config.toml`: author, auto-snapshot and sync settings, remotes |
| Snapshots and history | The object store `.wt/objects/` (identical content is stored once) |
| Tags | Ignore rules |
| Reflog (`.wt/trees/<tree>/reflog.jsonl`) | The daemon watch (one per worktree) |
| Remote-tracking refs and a server tree `<tenant>/<tree>` | |

A tree's snapshots **exclude the paths of trees nested inside it**. The root tree never records files under `apps/frontend/` once `apps/frontend` is its own tree, so each history contains only its own files.

## Managing trees

```text
wt tree list | add NAME PATH | remove NAME
```

<Steps>
<Step>

### Add a tree

```bash
wt tree add frontend apps/frontend
wt tree add api services/api
wt tree list
```

`PATH` is relative to the worktree root and is created if missing. `wt tree add` writes the marker `PATH/.wt-tree/config.toml` and registers the tree under `.wt/trees/NAME/`. The new tree starts with an empty default branch.

</Step>
<Step>

### Take its first snapshot

```bash
wt --tree frontend snapshot -m "Initial frontend"
wt --tree api snapshot -m "Initial API"
```

</Step>
<Step>

### Snapshot the parent

Files that now belong to the nested trees disappear from the root tree's view, so the root tree's next snapshot no longer contains them:

```bash
wt status
wt snapshot -m "Move frontend and api into their own trees"
```

</Step>
</Steps>

`wt tree remove NAME` unregisters a nested tree and keeps its files on disk. The root tree cannot be removed. Adding a tree whose name already exists fails.

## Selecting a tree

Tree-scoped commands (`status`, `snapshot`, `log`, `diff`, `branch`, `switch`, `merge`, `tag`, `reflog`, `revert`, `restore`, `archive`, `push`, `fetch`, `pull`, `stage`, `git export`) act on:

1. the tree named by the global flag `--tree <name>`, if given;
2. otherwise the **deepest** tree whose directory contains the current directory (or the `-C` path);
3. otherwise the root tree.

```bash
cd apps/frontend
wt status                       # frontend
wt log --oneline                # frontend history
cd ../..
wt status                       # root tree
wt --tree api log -n 5          # api, from anywhere
wt -C apps/frontend switch -c redesign
```

In scripts, always pass `--tree` so the result does not depend on the current directory.

## Branches are per tree

Each tree has its own branch namespace and its own `HEAD`. Switching branches in one tree only rewrites that tree's files; nested-tree directories are never touched by a parent's `wt switch`, `wt restore` or merge.

```bash
wt --tree frontend switch -c redesign   # frontend on "redesign"
wt --tree api branch                    # api still on "main"
wt branch                               # root tree still on "main"
```

The same branch name in two trees means two unrelated branches. Revisions such as `main~2` or a tag name resolve within the selected tree.

## Trees on the server

Each tree is pushed to its own server tree. With `[remote.origin]` set to tenant `acme`:

| Local tree | Server tree |
|---|---|
| `my-app` (root) | `acme/my-app` |
| `frontend` | `acme/frontend` |
| `api` | `acme/api` |

```bash
wt push                       # root tree
wt --tree frontend push
wt --tree api push --branch main
```

The first push of each tree creates its server tree. Access control, visibility, branch protection and license rules are configured per server tree, so a nested tree can, for example, be `public` while the root tree stays `private`. See [Multi-tenancy](/guides/multi-tenancy) and [Access control](/docs/server/access-control).

<Callout type="info" title="Cloning">
`wt clone URL TENANT/TREE` links the new worktree's root tree to one server tree. Nested trees are separate server trees and are not brought along: clone each one separately where you need it (for example `wt clone URL acme/frontend`). Reassembling a multi-tree worktree from the server is not automated in v0.2.0.
</Callout>

## When to use nested trees

- Components with **different release cadences** (a library and the app that uses it), each with its own tags.
- Components with **different access** needs: separate server trees can have different visibility and members.
- Large monorepos where teams want `wt log` and `wt status` to show only their area.

If everything always ships together, a single tree with directories is simpler.

## Not in v0.2.0

<Callout type="warn" title="Roadmap">
Switching several trees together and reassembling a multi-tree worktree from the server are planned but not shipped. Trees can already be coordinated on the server: snapshot dependencies create TODOs in other trees (`wt snapshot --depend`, `wt deps graph`), and merge requests of several trees can be linked so they merge together (`wt mr link`). See [Dependencies, TODOs and releases](/docs/cli/dependencies) and the [roadmap](/roadmap).
</Callout>
