W0rkTree talks to Git through a local bridge, the `worktree-git` crate (libgit2), exposed as two commands:

```text
wt git import GIT_PATH [DEST]
wt git export GIT_PATH [--rev REV]
```

Both work on Git repositories **on disk**. Neither talks to a Git hosting server; use `git clone` and `git push` for that. The full reference is [`wt git`](/docs/cli/git#wt-git).

## `wt git import`

Creates a **new** worktree at `DEST` from the Git repository at `GIT_PATH`. The worktree and its root tree are named after `DEST`.

| Git | Becomes |
|---|---|
| Every local branch | A branch of the root tree, with its full commit graph as snapshots. |
| Commit parents | Snapshot parents. Merge commits become two-parent snapshots. |
| Author, timestamp, message | Snapshot author, `created_at`, message. |
| Lightweight and annotated tags | Tags (annotated tag messages are kept). |
| `.gitignore` | `.wt/ignore` (same syntax). |
| File contents | Blobs re-hashed with BLAKE3 into `.wt/objects/`. |

After the import one branch is checked out in `DEST`, and the working tree is clean.

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
wt git import ~/src/app ./app
wt -C ./app log -n 5 --oneline
wt -C ./app branch
```

</Tab>
<Tab value="PowerShell">

```powershell
wt git import C:\src\app .\app
wt -C .\app log -n 5 --oneline
wt -C .\app branch
```

</Tab>
</Tabs>

Import always creates a new worktree; it does not merge Git history into an existing one. Re-running it into a fresh directory produces fresh snapshot ids.

## `wt git export`

Writes snapshots into the Git repository at `GIT_PATH` (created if it does not exist) as Git commits with the same parents, author, timestamp and message.

| Option | Effect |
|---|---|
| (none) | Export all branches of the tree. |
| `--rev REV` | Export only `REV` (any [revision](/docs/cli#revision-syntax): branch, tag, `HEAD~N`, id prefix). |
| `--tree <name>` (global) | Export a nested tree instead of the root tree. |

```bash
wt git export ../app-git
wt git export ../app-git --rev main
wt --tree frontend git export ../frontend-git
```

### Incremental and deterministic

The mapping from snapshot id to Git commit SHA is stored in `.wt/git-map.json`. On the next export, snapshots that are already mapped are skipped and only new ones are written, and the same snapshot always produces the same commit. That makes it safe to export repeatedly into the same Git repository, for example after every push, and to push the result to a Git host with normal fast-forward pushes.

<Callout type="info">
`.wt/git-map.json` is local to the worktree that ran the export (`.wt/` is never synchronized). Run repeated exports from the same worktree, or the mapping starts over.
</Callout>

## Workflows

### One-time migration

Import, verify, push to a W0rkTree server, and retire the Git repository. The full checklist is in [Migrating from Git](/guides/migration).

```bash
wt git import ~/src/app ./app
cd app
wt remote add origin https://wt.example.com --tenant acme
wt push --branch main
```

### Publishing to Git-only consumers

Some tools (CI systems, package managers, code search) only read Git. Keep a Git repository next to the worktree and export into it whenever you want them to see new history:

<Steps>
<Step>

### Create the export target once

```bash
wt git export ../app-git
git -C ../app-git remote add origin git@git.example.com:acme/app.git
```

</Step>
<Step>

### Export and push after each release or merge

```bash
wt pull
wt git export ../app-git --rev main
git -C ../app-git push origin main --follow-tags
```

</Step>
</Steps>

Because export is incremental, each run only writes the snapshots added since the last one.

### Exporting for CI

To build a revision in a Git-based CI system, export just that revision into a scratch repository:

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
wt git export /tmp/app-ci --rev v1.2.0
git -C /tmp/app-ci log -1
```

</Tab>
<Tab value="PowerShell">

```powershell
$dest = Join-Path $env:TEMP 'app-ci'
wt git export $dest --rev v1.2.0
git -C $dest log -1
```

</Tab>
</Tabs>

If the CI system only needs files, not history, [`wt archive`](/docs/cli/snapshots#wt-archive) is simpler: `wt archive v1.2.0 -o app.tar.gz --format tar.gz`.

## Limitations

- **One-shot commands, not a mirror.** Nothing runs in the background; Git and W0rkTree only meet when you run `wt git import` or `wt git export`.
- **Import goes one way into a new worktree.** New Git commits made after an import cannot be pulled into the existing worktree. Pick a cut-over point.
- **Local branches only.** Remote-tracking branches are not imported.
- **Root tree only on import.** Submodules are not converted into nested trees.
- **No LFS, hooks, config, stashes, index or Git reflog.** `.gitattributes` filters are not applied, so LFS files arrive as pointer files.
- **No signatures.** Commit and tag signatures are not imported, and exported commits are unsigned.
- **Different ids.** Snapshots use UUIDs and BLAKE3 object hashes; Git uses SHA-1. Correlate with `.wt/git-map.json`.

A live Git mirror mode that keeps a Git remote continuously in sync with a W0rkTree branch is planned but **not** part of v0.2.0. See the [roadmap](/roadmap).
</Callout>
