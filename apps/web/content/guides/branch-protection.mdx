Branch protection rules live on the server and apply to every push, from every client. A typical setup forbids direct pushes to `main` and `release/*`, so changes land only through **merge requests** that collect approvals first.

Even without protection, history on the server is safe: snapshots are immutable and a push must descend from the current server tip. There is no force push. Protection adds *who* and *how* on top of that.

## Protection rule fields

A rule (`BranchProtection`) matches branches by a glob `pattern`, for example `main` or `release/*`.

| Field | Type | Meaning |
|---|---|---|
| `pattern` | string | Branch-name glob. `release/*` matches `release/1.0` and `release/2.3`. |
| `no_direct_push` | bool | Matching branches change only through merge requests. Direct pushes are rejected. |
| `required_approvals` | int | Approvals a merge request needs before it can be merged into a matching branch. |
| `allowed_pushers` | string array | Usernames allowed to push to matching branches. Empty means role-based only: anyone with `tree:write` on the tree. |
| `no_delete` | bool | Matching branches cannot be deleted (archived). |

Managing protections requires `tree:admin` on the tree (tenant `admin` or `owner`).

## Protect `main` and `release/*`

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
curl -s -X PUT http://localhost:7420/api/v1/trees/acme/app/protections \
  -H "Authorization: Bearer $WT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"pattern":"main","no_direct_push":true,"required_approvals":1,"allowed_pushers":[],"no_delete":true}'

curl -s -X PUT http://localhost:7420/api/v1/trees/acme/app/protections \
  -H "Authorization: Bearer $WT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"pattern":"release/*","no_direct_push":true,"required_approvals":2,"allowed_pushers":[],"no_delete":true}'
```

</Tab>
<Tab value="PowerShell">

```powershell
$headers = @{ Authorization = "Bearer $env:WT_TOKEN" }
$uri = "http://localhost:7420/api/v1/trees/acme/app/protections"

Invoke-RestMethod -Method Put -Headers $headers -ContentType "application/json" -Uri $uri `
  -Body '{"pattern":"main","no_direct_push":true,"required_approvals":1,"allowed_pushers":[],"no_delete":true}'

Invoke-RestMethod -Method Put -Headers $headers -ContentType "application/json" -Uri $uri `
  -Body '{"pattern":"release/*","no_direct_push":true,"required_approvals":2,"allowed_pushers":[],"no_delete":true}'
```

</Tab>

`PUT` creates or replaces the rule for that pattern and returns it. The response also includes `tree_id`.

Other operations:

```text
GET    /api/v1/trees/{tenant}/{tree}/protections            list rules
DELETE /api/v1/trees/{tenant}/{tree}/protections?pattern=   remove the rule for one pattern
```

URL-encode the pattern when deleting, for example `?pattern=release%2F%2A`. Branches covered by a rule report `"protected": true` in `GET /api/v1/trees/{tenant}/{tree}/branches`.

In the admin panel: **Trees**, select the tree, then the **Protections** tab. See the [Admin Panel guide](/guides/admin-panel).

## The merge request workflow

With `no_direct_push` on `main`, work happens on a feature branch and lands through a merge request (MR). Merge requests are managed with [`wt mr`](/docs/cli/merge-requests#wt-mr), the REST API and the admin panel.

<Steps>
<Step>

### Push a feature branch

```bash
wt branch create feature/login
wt switch feature/login
# ...edit...
wt snapshot -m "Add login form"
wt push
```

</Step>
<Step>

### Open the merge request

```bash
curl -s -X POST http://localhost:7420/api/v1/trees/acme/app/merge-requests \
  -H "Authorization: Bearer $WT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"Add login form","description":"Implements the login page.","source_branch":"feature/login","target_branch":"main"}'
```

The server responds `201` with the MR. Numbers are per tree and start at 1:

```json
{
  "id": "e7b1...",
  "tree_id": "b1d7...",
  "number": 4,
  "title": "Add login form",
  "description": "Implements the login page.",
  "source_branch": "feature/login",
  "target_branch": "main",
  "author_id": "c42f...",
  "author": "bob",
  "state": "open",
  "approvals": [],
  "created_at": "2026-10-24T11:00:00Z",
  "updated_at": "2026-10-24T11:00:00Z"
}
```

</Step>
<Step>

### Review and approve

Reviewers inspect the source branch (in the admin panel, or locally with `wt fetch` and `wt diff main origin/feature/login`) and approve:

```bash
curl -s -X POST http://localhost:7420/api/v1/trees/acme/app/merge-requests/4/approve \
  -H "Authorization: Bearer $WT_TOKEN"
```

Each approval is added to `approvals` as `{"account_id", "username", "at"}`.

</Step>
<Step>

### Merge

```bash
curl -s -X POST http://localhost:7420/api/v1/trees/acme/app/merge-requests/4/merge \
  -H "Authorization: Bearer $WT_TOKEN"
```

The server **fast-forwards** the target branch to the source branch's tip. On success `state` becomes `merged` and `merged_at` and `merged_snapshot` are set.

</Step>
</Steps>

Other MR endpoints: `GET .../merge-requests?state=open|merged|closed` to list, `GET .../merge-requests/{n}` to read one, and `POST .../merge-requests/{n}/close` to close without merging. SSE subscribers receive `mr.opened`, `mr.approved`, `mr.merged`, and `mr.closed` events.

### When the target branch moved

A server-side merge only fast-forwards. If someone else merged into `main` after you pushed, `main`'s tip is no longer an ancestor of your branch and the merge fails with `409 conflict`. Bring `main` into your branch locally, push, and retry:

```bash
wt switch feature/login
wt fetch
wt merge origin/main          # resolve conflicts if any, then: wt merge --continue
wt push
```

Then call `POST .../merge-requests/4/merge` again. See [Merge Strategies](/guides/merge-strategies) for resolving conflicts.

### Not enough approvals

If the MR has fewer approvals than the target branch's protection rule requires (`required_approvals`), the merge is refused as `review_required`, reporting how many approvals are required and how many the MR currently has.

## Push rejections

When the server refuses a push, `wt push` exits with code 1 and prints the reason. The rejection kinds are:

| Kind | Cause | What to do |
|---|---|---|
| `branch_protection` | A rule forbids this push, for example `no_direct_push` on `main`, or you are not in `allowed_pushers`. The rule is named. | Push to a feature branch and open a merge request. |
| `access_denied` | Your account lacks `tree:write` on the tree. | Ask a tenant owner for a role with write access. |
| `review_required` | The change needs approvals that it does not have. | Collect approvals on the merge request. |
| `license_violation` | A changed path is covered by a license rule that does not allow your tenant to modify it. The path and license are named. | See [License Compliance](/guides/license-compliance). |
| `conflict_detected` | The branch tip on the server moved since your last pull. | `wt pull`, resolve any conflicts, then push again. |

<Callout type="warn" title="Roadmap">
  The server does not run CI itself, but CI systems can report check results (`wt ci report`), and a rule with `require_ci_pass` (`wt protect set ... --require-ci --check NAME`) blocks merges until the required checks succeed on the source tip. See [Reviews, CI and merges](/docs/cli/merge-requests).
</Callout>
