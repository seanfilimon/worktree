W0rkTree never rewrites history. Undoing something always means **adding** to history, and anything that was ever snapshotted stays reachable. This page shows how to find earlier states and get back to them.

## The append-only model

| Thing | Guarantee |
|---|---|
| Snapshots | Immutable. `wt rebase` and `wt cherry-pick` create *new* snapshots and move the branch (the old ones stay reachable from the reflog until `wt gc` prunes them); there is no `amend` or `reset`. |
| Undo | `wt revert` creates a **new** snapshot that undoes an earlier one. |
| Branches | Never hard-deleted. `wt branch archive` hides a branch; `wt branch restore` brings it back with all its history. |
| Reflog | Every ref-moving action is appended to `.wt/trees/<tree>/reflog.jsonl`. Entries are never removed. |
| Server | Snapshots are immutable, pushes must descend from the server tip, there is no force push, and the audit log is append-only. |

The one thing that can be lost is work that was **never snapshotted**: uncommitted edits discarded by `wt restore` or `wt switch --force`. Running the [daemon](/guides/auto-tracking-setup) closes most of that gap, because it snapshots your work automatically after 30 seconds of inactivity.

## `wt reflog`

```text
wt reflog [-n N]
```

Shows the selected tree's reflog, newest first. Each entry has a time, tree, branch, action, the **old** and **new** snapshot ids, and a message.

| Action | Recorded by |
|---|---|
| `init` | `wt init` |
| `snapshot`, `auto-snapshot` | `wt snapshot`, the daemon |
| `switch` | `wt switch` |
| `branch.create`, `branch.archive` | `wt branch create`, `wt branch archive` |
| `merge`, `fast-forward` | `wt merge`, `wt pull` |
| `revert` | `wt revert` |
| `restore` | `wt restore` |
| `pull`, `push` | `wt pull`, `wt push` |
| `tag.create`, `tag.delete` | `wt tag create`, `wt tag delete` |

```bash
wt reflog -n 20
wt --tree frontend reflog
```

Any id from the reflog (or a unique prefix of at least 4 characters) is a valid revision for `wt show`, `wt log`, `wt diff`, `wt restore --from`, `wt branch create --from` and `wt tag create`.

## Recovery recipes

### Discard uncommitted changes

```bash
wt restore src/app.rs     # one file back to HEAD
wt restore                # the whole tree back to HEAD
```

`wt restore` overwrites working files with their content at a revision (default `HEAD`) and deletes files that do not exist there. It creates no snapshot and moves no branch. Uncommitted changes in those paths are gone afterwards, so snapshot first if in doubt.

### Bring back a file from an earlier snapshot

```bash
wt log --oneline -n 20                   # find the snapshot
wt restore config/app.toml --from 4f9c2a1e
wt diff
wt snapshot -m "Restore config/app.toml from 4f9c2a1e"
```

`--from` accepts any revision: `HEAD~3`, `main~1`, `origin/main`, a tag such as `v1.0.0`.

### Undo a snapshot

```bash
wt revert HEAD            # undo the last snapshot
wt revert 4f9c2a1e        # undo an older one
```

The revert is a normal snapshot that undoes the target's changes relative to its first parent. Both the original and the revert stay in history.

### Undo something that was already pushed

The server's history can only grow, so the fix is the same: revert locally and push the revert.

```bash
wt revert 4f9c2a1e
wt push
```

### Recover after a bad merge

If the merge **is still in progress** (it stopped with conflicts), abandon it:

```bash
wt merge --abort
```

If the merge **completed** (fast-forward or merge snapshot), choose one of:

- **Revert it.** For a merge snapshot, `wt revert <merge-id>` undoes everything the merge brought in relative to the first parent (the branch you merged into). This is the right choice once the merge has been pushed.
- **Restore the old content.** Find the pre-merge tip in the reflog (the `old` id of the `merge` or `fast-forward` entry), then restore the whole tree from it and snapshot:

  ```bash
  wt reflog -n 5
  wt restore --from 7d2e91b0
  wt snapshot -m "Back out the merge of feature/x"
  ```

- **Continue from the old state on a new branch.** Branch tips never move backwards, but you can start a branch at the pre-merge snapshot:

  ```bash
  wt branch create main-before-merge --from 7d2e91b0
  wt switch main-before-merge
  ```

### Find work that seems lost

Every snapshot that was ever taken is still in `.wt/`. Look in the reflog for the `new` ids of `snapshot`, `auto-snapshot` and `switch` entries, inspect them, and put a branch on the one you want:

```bash
wt reflog -n 50
wt show 9a0c33f1 --stat
wt branch create rescue --from 9a0c33f1
```

### Restore an archived branch

```bash
wt branch -a                       # archived branches are listed too
wt branch restore feature/old-spike
wt switch feature/old-spike
```

An archived name cannot be reused for a new branch until it is restored. The current branch and the default branch cannot be archived.

### Recreate a deleted tag

`wt tag delete` removes a tag **locally** only. Find the snapshot it pointed to (in `wt log`, or the `tag.delete` reflog entry) and tag it again:

```bash
wt tag create v1.2.0 3b8f02aa -m "Release 1.2.0"
```

If the tag had been pushed, the server still has it and `wt fetch` downloads it again; a tree admin can delete it on the server with `wt trees tag-delete` (unless a tag protection forbids it).

## What the server guarantees

| Guarantee | Detail |
|---|---|
| Immutable snapshots | A stored snapshot never changes; re-sending the same id with different content is rejected. |
| No lost pushes | A push must descend from the current server tip, and tips move by compare-and-swap, so concurrent pushes cannot overwrite each other. |
| No force push | There is no way to move a server branch backwards or to an unrelated snapshot. |
| Branch deletion | Only explicit server deletion (`wt trees branch-delete`, `branch:delete`), which protection rules can forbid with `no_delete`. See [Branch protection](/docs/server/branch-protection). |
| Audit trail | Security-relevant actions (pushes, membership changes, protection changes and others) are appended to an append-only audit log. See [Monitoring](/docs/server/monitoring#audit-log). |
| Verified objects | Every uploaded object is checked against its BLAKE3 hash. |

<Callout type="warn" title="Limits of the guarantees">
- **Deleting a server tree** (`DELETE /api/v1/trees/{tenant}/{tree}`, requires `tree:admin`) removes its metadata. Only a backup of the data directory brings it back. See [Storage](/docs/server/storage#backup).
- **Local history is local.** Snapshots you have not pushed live only in your `.wt/`. Deleting `.wt/` deletes them. Push regularly.
- Server garbage collection deletes objects that are no longer reachable from any branch, tag, staged snapshot, merge request or release after a grace period (default 30 days). See [Garbage collection](/docs/server/operations#garbage-collection).
</Callout>
