W0rkTree ships three programs and a static web application: `wt` (the CLI) and `worktree-bg` (the background daemon) for developer machines, `worktree-server` (the Go server) and the admin panel it serves. There are three ways to get them:

| Way | What you get | Section |
|---|---|---|
| Installers (`scripts/install.sh`, `scripts/install.ps1`) | `wt`, `worktree-bg` (and optionally `worktree-server`) from a release archive, SHA-256 verified | [Installers](#installers) |
| Container images (`deploy/docker/Dockerfile`, `deploy/docker/Dockerfile.cli`) | The server with the admin panel and `git`; static CLI binaries | [Container images](#container-images) |
| Source | Everything, built with Cargo, Go and Node | [Build from source](#build-from-source) |

## Installers

`scripts/install.sh` (Linux, macOS, Git Bash) and `scripts/install.ps1` (Windows PowerShell 5.1 or newer, PowerShell 7 on any OS) pick the release archive for your OS and architecture, verify its SHA-256 against the release's `SHA256SUMS`, and install `wt` and `worktree-bg` into `~/.local/bin` (Windows: `%LOCALAPPDATA%\Programs\worktree\bin`). Nothing is installed when the checksum does not match.

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
bash scripts/install.sh --version v0.8.0
bash scripts/install.sh --version v0.8.0 --dir /usr/local/bin --with-server
bash scripts/install.sh --base-url https://mirror.example.com/worktree/v0.8.0
```

</Tab>
<Tab value="PowerShell">

```powershell
.\scripts\install.ps1 -Version v0.8.0 -AddToPath
.\scripts\install.ps1 -Version v0.8.0 -WithServer -AddToPath
.\scripts\install.ps1 -BaseUrl \\fileserver\worktree\v0.8.0
```

</Tab>
</Tabs>

By default the installers download from the project's GitHub releases. A `--base-url` (`-BaseUrl`) can instead name an internal mirror, a `file://` URL or a plain directory, for example the `dist/` directory written by `scripts/release.sh`, which builds the same archives (`worktree-<version>-<target>.tar.gz` or `.zip` with `wt`, `worktree-bg` and `worktree-server`, the admin panel archive and `SHA256SUMS`) on your machine. `--from-source` (`-FromSource`) builds with Cargo instead of downloading. All options are listed in [Deployment](/docs/server/deployment#installing-the-clients).

<Callout type="info" title="Release availability">
  Release archives and images are produced by `scripts/release.sh` and the release workflow for each `v<version>` tag. If no release has been published for the version you need, build the archives locally (`bash scripts/release.sh`, then `install.sh --base-url ./dist`) or build from source. Package-manager installs (Homebrew, winget, crates.io) are on the [roadmap](/roadmap).
</Callout>

## Container images

The server image bundles the server, the admin panel (served at `/admin/`) and `git` (for [Git mirrors](/docs/server/mirrors)); it runs as a non-root user with its data in the `/data` volume:

```bash
docker build -f deploy/docker/Dockerfile -t worktree-server .
docker run -d --name worktree -p 7420:7420 -v wt-data:/data \
  -e WT_ADMIN_PASSWORD='change-me-now' worktree-server
curl http://localhost:7420/healthz
```

`deploy/docker/Dockerfile.cli` builds statically linked `wt` and `worktree-bg` for CI jobs and Linux hosts. `deploy/docker-compose.yml` runs the server with optional MinIO (S3) and Mailpit (SMTP) profiles, and `deploy/helm/worktree` is a Helm chart. See [Deployment](/docs/server/deployment) and the operator guide [`docs/deploy.md`](https://github.com/seanfilimon/worktree/blob/main/docs/deploy.md).

## Build from source

The repository contains everything: the Rust workspace (`wt`, `worktree-bg`, the SDK, the protocol crate, the Git bridge), the Go server in `services/server-go`, and the admin panel in `apps/admin`.

### Prerequisites

| Toolchain | Version | Needed for |
|---|---|---|
| Rust | stable (edition 2021) | `wt`, `worktree-bg`, and all Rust crates. `protoc` is vendored by the build, so you do not need to install Protocol Buffers. |
| Go | 1.25 or newer | `worktree-server`. Pure Go, no cgo: no C compiler required. |
| Node.js | 22 or newer | Only for building the admin panel (`apps/admin`). |

Install Rust with [rustup](https://rustup.rs) and Go from [go.dev](https://go.dev/dl/). Check the versions:

```bash
rustc --version
cargo --version
go version
node --version   # only if you build the admin panel
```

### Build and install

<Steps>
<Step>

### Clone the repository

```bash
git clone https://github.com/seanfilimon/worktree.git
cd worktree
```

All following commands run from the repository root unless they `cd` elsewhere.

</Step>
<Step>

### Build the Rust workspace

```bash
cargo build --workspace --release
```

This builds every crate in the workspace. Release binaries land in `target/release/` (`wt` and `worktree-bg`, with `.exe` on Windows).

</Step>
<Step>

### Install `wt` and `worktree-bg`

```bash
cargo install --path crates/worktree-cli
cargo install --path crates/worktree-bg
```

Both binaries go into Cargo's bin directory (`~/.cargo/bin`, or `%USERPROFILE%\.cargo\bin` on Windows), which rustup adds to your `PATH`. Install `worktree-bg` next to `wt`: [`wt daemon start`](/docs/cli/daemon#wt-daemon) launches it for you, so you rarely run it directly.

</Step>
<Step>

### Build the server

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
cd services/server-go
go build -o worktree-server .
```

</Tab>
<Tab value="PowerShell">

```powershell
cd services\server-go
go build -o worktree-server.exe .
```

</Tab>
</Tabs>

The result is a single self-contained binary. See [Server installation](/docs/server/installation) for first-run options and [Configuration](/docs/server/configuration) for every flag.

</Step>
<Step>

### Build the admin panel (optional)

```bash
cd apps/admin
npm install
npm run build
```

The build writes static files to `apps/admin/dist`. Serve them from the server with `--admin-dir apps/admin/dist`; the panel is then available at `/admin/` on the server port. See [Admin panel](/guides/admin-panel).

</Step>
</Steps>

## Verify the install

Check that the CLI is on your `PATH`:

```bash
wt --help
```

Start a local server with an admin account and check its health endpoint:

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
cd services/server-go
./worktree-server --admin-password 'change-me-now' --admin-dir ../../apps/admin/dist
# in another terminal
curl http://localhost:7420/healthz
```

</Tab>
<Tab value="PowerShell">

```powershell
cd services\server-go
.\worktree-server.exe --admin-password 'change-me-now' --admin-dir ..\..\apps\admin\dist
# in another terminal
curl.exe http://localhost:7420/healthz
```

</Tab>
</Tabs>

`/healthz` returns JSON of the form `{"status":"ok","version":"...","uptime_seconds":N,"checks":{"meta":"ok","objects":"ok"}}` (HTTP `503` with `"status":"degraded"` when a storage probe fails). Omit `--admin-dir` if you did not build the admin panel. Data is written to `./wt-data` by default.

Then try a worktree end to end:

```bash
wt init demo && cd demo
echo "hello" > README.md
wt snapshot -m "First snapshot"
wt log --oneline
wt daemon start
wt daemon status
```

Continue with the [Quick start](/guides/quick-start) to push to the server.

## Windows notes

Windows is a first-class platform; W0rkTree is developed on it.

- **Shell.** All commands work in PowerShell. Where shell syntax differs (environment variables, paths, quoting), the docs show a PowerShell variant. Use `curl.exe` rather than the `curl` alias of older Windows PowerShell versions.
- **PATH.** `install.ps1` installs into `%LOCALAPPDATA%\Programs\worktree\bin` (`-AddToPath` adds it to your user `PATH`); `cargo install` places `wt.exe` and `worktree-bg.exe` in `%USERPROFILE%\.cargo\bin`. If `wt` is not found, add the directory to your user `PATH` and open a new terminal.
- **Per-user state.** `$WT_HOME` defaults to `%USERPROFILE%\.wt` and holds `credentials.toml`, the user `config.toml`, signing keys in `keys\`, and the daemon files `bg.json`, `bg.toml` and `bg.log`. Override it with an environment variable:

```powershell
$env:WT_HOME = "$env:USERPROFILE\.wt-test"
wt daemon status
```

- **Passwords in scripts.** Use `--password-stdin` or `$env:WT_PASSWORD` rather than typing passwords into prompts in automation. See [`wt login`](/docs/cli/remote#wt-login).

## Run the test suites

From the repository root:

```bash
cargo build --workspace && cargo test --workspace
cd services/server-go && go build ./... && go vet ./... && go test ./...
cd apps/admin && npm run build && npm test
cd apps/web && npm run build
bash scripts/e2e.sh        # starts the Go server and drives wt end to end
```

Run each `cd` line from the repository root. On Windows, run `scripts/e2e.sh` from Git Bash (or another POSIX shell).

<Callout type="info" title="Isolate per-user state in tests">
  Tests and the end-to-end script must not touch your real credentials. Point `WT_HOME` at a temporary directory before running anything that logs in or starts the daemon.
</Callout>

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
export WT_HOME="$(mktemp -d)"
cargo test --workspace
```

</Tab>
<Tab value="PowerShell">

```powershell
$env:WT_HOME = Join-Path $env:TEMP "wt-home-test"
cargo test --workspace
```

</Tab>
</Tabs>
