`wt` is the W0rkTree command-line client (crate `worktree-cli`). It works on a local `.wt/` repository through the Rust SDK, talks to a W0rkTree server over gRPC (h2c) and REST on a single port, and controls the background daemon `worktree-bg` over newline-delimited JSON on a loopback (`127.0.0.1`) TCP port.

This reference covers **v0.2.0 ("v2 rebuild")**. Every command, subcommand, flag and positional listed here is the complete surface; there are no hidden or extra flags.

<Callout type="info" title="Install from source">
v0.2.0 is pre-1.0 and is built from source only: `cargo install --path crates/worktree-cli` (and `cargo install --path crates/worktree-bg` for the daemon). See [Installation](/docs/installation).
</Callout>

## Synopsis

```text
wt [--json] [-C <path>] [--tree <name>] [--no-color] <command> [args...]
```

## Global flags

Global flags are accepted by every command.

| Flag | Description |
|---|---|
| `--json` | Write machine-readable JSON to stdout instead of human-formatted text. |
| `-C <path>` | Run as if `wt` had been started in `<path>`. The worktree is found by walking up from this directory to the nearest `.wt/`. |
| `--tree <name>` | Operate on the named tree instead of the tree inferred from the current directory. |
| `--no-color` | Disable ANSI colors in human output. |

### Which tree a command acts on

A worktree contains one root tree (created by `wt init`) and optionally nested trees (directories with a `.wt-tree/` marker, see [`wt tree`](/docs/cli/repository#wt-tree)). Tree-scoped commands such as `wt status`, `wt snapshot`, `wt log` or `wt push` act on:

1. the tree named by `--tree <name>`, if given; otherwise
2. the deepest tree whose directory contains the current directory (or the `-C` path); falling back to
3. the root tree.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | Success. |
| `1` | Error (for example: not a worktree, dirty working tree, push rejected, secrets detected, not logged in). |
| `2` | Usage error: unknown command or flag, missing or invalid argument. |
| `3` | Merge conflicts: `wt merge` or `wt pull` stopped with conflicts that need resolving. |

## Environment variables

| Variable | Description |
|---|---|
| `WT_HOME` | Per-user state directory. Default `~/.wt` (on Windows, `%USERPROFILE%\.wt`). Holds `credentials.toml`, `bg.json`, `bg.toml`, `bg.log`. |
| `WT_PASSWORD` | Password used by `wt login` and `wt register` instead of an interactive prompt. |

Files in `$WT_HOME`:

| File | Contents |
|---|---|
| `credentials.toml` | Saved login tokens, keyed by server URL (written by `wt login` / `wt register`, removed by `wt logout`). |
| `bg.json` | `pid`, `port` and `version` of the running daemon; written on daemon start, removed on clean shutdown. |
| `bg.toml` | `watched = [...]`, the worktree roots the daemon watches. |
| `bg.log` | Daemon log. |

<Callout type="warn" title="Tests and CI">
Set `WT_HOME` to a temporary directory in tests and CI so runs never read or overwrite your real credentials or daemon state.
</Callout>

## Revision syntax

Wherever a command takes `REV` (`wt log`, `wt show`, `wt diff`, `wt revert`, `wt restore --from`, `wt branch create --from`, `wt tag create`, `wt archive`, `wt merge`), the following forms are accepted. Revisions resolve within the selected tree.

| Form | Resolves to |
|---|---|
| `HEAD` | Head snapshot of the current branch. |
| `HEAD~N` | The `N`th first-parent ancestor of `HEAD`. |
| `<branch>` | Tip of a local branch. |
| `<branch>~N` | The `N`th first-parent ancestor of a branch tip. |
| `origin/<branch>` | Last known tip of a remote branch (from `refs/remotes/origin/<branch>`, updated by `wt fetch`, `wt pull`, `wt push`). |
| `<tag>` | The snapshot a tag points to. |
| `<id-prefix>` | A snapshot id (UUID) or a unique prefix of at least 4 characters. An ambiguous prefix is an error. |

Snapshot ids are UUID v4 strings; human output usually shows the first 8 characters.

### Not in the CLI

Merge requests, branch protections, license rules, tenants, members and API tokens have **no `wt` subcommands in v0.2.0**. Manage them with the [REST API](/docs/server/rest-api) or the [admin panel](/guides/admin-panel).

<Callout type="warn" title="Roadmap">
`wt` subcommands for merge requests, tenants, access and licenses are planned but not shipped. See the [roadmap](/roadmap).
</Callout>

## Scripting with `--json`

- `--json` puts the command's result on stdout as JSON. Field names follow the SDK data types (for example `wt status --json` mirrors `StatusReport`: `tree`, `branch`, `head`, `changes` with `path` and `kind` of `added`, `modified` or `deleted`, and `merge`). See [SDK repository](/docs/sdk/repository).
- Branch on the **exit code**, not on message text: `0` success, `1` error, `2` usage, `3` conflicts.
- Never type passwords into scripts interactively. Use `--password-stdin` or `WT_PASSWORD`.
- Use `-C <path>` instead of changing directories, and `--tree <name>` instead of relying on the current directory.
- Pass `--no-color` when capturing human output.

```bash
# Fail a CI step when the working tree is dirty
changes=$(wt -C ./repo status --json | jq '.changes | length')
if [ "$changes" -ne 0 ]; then echo "uncommitted changes"; exit 1; fi

# Handle merge conflicts explicitly
wt merge feature/login
case $? in
  0) echo "merged" ;;
  3) echo "conflicts; see .wt/conflicts/" ;;
  *) echo "merge failed"; exit 1 ;;
esac
```

```powershell
$status = wt -C .\repo status --json | ConvertFrom-Json
if ($status.changes.Count -ne 0) { Write-Error "uncommitted changes"; exit 1 }

wt merge feature/login
if ($LASTEXITCODE -eq 3) { Write-Host "conflicts; see .wt\conflicts\" }
```

<Callout type="info">
JSON output is pre-1.0. Field names track the SDK types and may change between minor versions.
</Callout>
