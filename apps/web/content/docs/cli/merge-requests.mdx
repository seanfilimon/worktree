These commands talk to the server's REST API. They accept `--server URL` (or `WT_SERVER`; default: the worktree's `origin` remote, else the only saved login) and `--json`. A `TREE` argument is written `tenant/tree`; inside a worktree it defaults to the origin tenant plus the current tree's remote name. Every flag is listed in the [full CLI reference](https://github.com/seanfilimon/worktree/blob/main/docs/cli-reference.md#wt-mr).

## Workflow

<Steps>
<Step>

### Push the source branch

```bash
wt switch -c feature/refunds
wt snapshot -m "Add refund endpoint"
wt push --branch feature/refunds
```

</Step>
<Step>

### Open the merge request

```bash
wt mr create --source feature/refunds --target main --title "Add refund endpoint"
wt mr create --source feature/refunds --target main --title "Add refund endpoint" --draft --reviewer team:payments
wt mr ready 4                         # a draft becomes mergeable; owners are asked for review
```

Needs `mr:create` (developer). Source and target are branches of the same tree, or since v0.8 the source is a branch of a [fork](/docs/server/forks): `wt mr create acme/web --from bob/web:feature --target main --title "..."` (needs `mr:create` on the upstream, or `tree:fork` on it plus `tree:write` on the fork). Opening a non-draft merge request (and every later push to its source) requests reviews from the [path owners](/docs/server/review-workflow#path-owners) of the changed paths.

</Step>
<Step>

### Review

```bash
wt mr show 4 --diff
wt mr owners 4                        # owners per changed path and whether they approved
wt mr comment 4 -m "Validate the amount" --path src/refund.rs --line 42
wt mr suggest 4 --path src/refund.rs --lines 42-43 -m "    validate(amount)?;" -b "Validate first"
wt mr review 4 --request-changes -m "Amount is not validated"
# the author applies the suggestion (a new snapshot on the source branch), or pushes a fix
wt mr apply-suggestion 4 17
wt mr review 4 --approve
```

</Step>
<Step>

### Check and merge

```bash
wt mr checks 4
wt mr merge 4                         # fast-forward if possible, else a merge snapshot
wt mr merge 4 --method squash -m "Add refund endpoint (!4)"
wt mr merge 4 --rebase --delete-branch   # v0.8: replay onto main, then delete the source branch
```

</Step>
</Steps>

### Review rules

- **Approvals belong to a source tip.** An approval records the source branch tip at the time it was given. When the author pushes again, the approval becomes **stale** and no longer counts; the reviewer must approve again.
- **Change requests block.** A `--request-changes` review from someone with `mr:approve` blocks the merge until that same reviewer approves the current tip.
- **Authors cannot approve** (or request changes on) their own merge request.
- `--approve` and `--request-changes` need `mr:approve` (maintainer); `--comment` and `wt mr comment` need only `tree:read`.
- **Drafts cannot be merged.** A draft has a `draft` blocker and `wt mr merge` answers `409 draft` until `wt mr ready N` (author or `mr:merge`).
- **Owner approval.** With `--require-owner-approval` on the target's protection, every changed path that has owners needs an approval of the current source tip from one of them (`owners` blocker). See [Owner approval](/docs/server/review-workflow#owner-approval).

### Review requests, owners and suggestions

- `wt mr reviewers N [TREE]` lists requested reviewers; `wt mr reviewers N [TREE] add WHO...` requests reviews and `remove WHO...` withdraws them (author or `mr:approve`). `WHO` is `user:NAME`, `team:SLUG`, `NAME`, `@NAME` or `@TENANT/SLUG`; the author cannot be requested. Each new request publishes `mr.review_requested` and lands in the reviewers' [inbox](/docs/server/notifications#wt-inbox).
- `wt mr owners N [TREE]` shows the owners of every changed path (from `wt owners set` or the tree's `OWNERS` file), whether each path is approved, and which are still missing. Manage owner rules with [`wt owners show|set`](/docs/server/review-workflow#path-owners).
- `wt mr suggest N [TREE] --path P --lines A[-B] (--file F | -m TEXT) [-b BODY]` posts a comment that replaces lines `A..B` (1-based, inclusive) of `P` as of the source tip; an empty replacement deletes them. `--file -` reads stdin.
- `wt mr apply-suggestion N COMMENT_ID [TREE] [-m MSG]` writes a snapshot on the source branch on the server, authored by you (needs `tree:write` and a direct push allowed by the source's protection). It answers `409 suggestion_outdated` when the source tip changed those lines, `409 conflict` when it was already applied or the tip already contains the change, and `409 quota_exceeded` when the new objects exceed the tenant's storage quota. See [Suggested changes](/docs/server/review-workflow#suggested-changes).

### Merge methods

The server merges with one of four methods (see [Server-side merges](/docs/server/merging)):

| `--method` | Result |
|---|---|
| `fast-forward` | The target moves to the source tip; no new snapshot. |
| `merge` | A merge snapshot with parents `[target tip, source tip]`. |
| `squash` | One snapshot on the target with all the source's changes. |
| `rebase` (v0.8; also `--rebase`) | The source snapshots are replayed onto the target tip as new snapshots (linear history; the source must be linear). See [Rebase merges](/docs/server/conflict-resolution#rebase-merges). |

Without `--method` the server fast-forwards when it can and otherwise writes a merge snapshot, whichever branch protection allows first (`wt protect set --merge-methods` restricts the methods; `--require-linear` forbids `merge`, `--require-signed` forbids `merge`, `squash` and `rebase`). `-m` sets the message of a merge or squash snapshot. `--delete-branch` (v0.8) deletes the source branch after the merge; it needs `branch:delete` and is checked before merging. `wt mr mergeability 4` shows the possible methods, the merge base and any conflicts before you try.

The server never writes conflict markers into the target: a merge with conflicts is refused (`409 merge_conflict` listing the paths, exit code `3`). Since v0.8 you can resolve the conflicts on the server, in the browser (**Resolve conflicts** on the merge request page) or from the CLI, which writes a merge-resolution snapshot on the source branch ([Conflict resolution](/docs/server/conflict-resolution)):

```bash
wt mr conflicts 4 --write        # write the diff3 previews into the local tree; edit them
wt mr resolve 4                  # or: wt mr resolve 4 --take theirs assets/logo.png
wt mr merge 4
```

Or bring the target into the source locally, resolve, push and merge again:

```bash
wt pull --branch main
wt switch feature/refunds
wt merge main -m "Merge main into feature/refunds"
wt push --branch feature/refunds
```

A refused merge reports why, in this order of precedence: a draft answers `409 draft`; a linked group answers `409 linked_group`; missing approvals answer `403 review_required`; change requests, missing owner approvals, CI, blocking TODOs and linear-history violations answer `409 merge_blocked` listing every blocker; a method protection refuses answers `409 merge_method_not_allowed`; conflicts answer `409 merge_conflict`; a fast-forward on diverged branches answers `409 conflict`; a merge or squash snapshot whose new objects would exceed the tenant's storage quota answers `409 quota_exceeded`. Run `wt mr checks` first to see all blockers at once; refusals hint at `wt mr ready`, `wt mr owners` and the storage quota where relevant. See [`wt merge`](/docs/cli/branches#wt-merge).

## `wt mr`

```text
wt mr <list|show|create|ready|reviewers|owners|suggest|apply-suggestion|approve|merge|conflicts|resolve|mergeability|close|review|comment|comments|checks|link|merge-group|groups>
```

| Command | Usage | Notes |
|---|---|---|
| `list` | `wt mr list [--state <open\|merged\|closed\|all>] [TREE]` | Default `open`. Drafts are marked. |
| `show` | `wt mr show [--diff] <NUMBER> [TREE]` | `--diff` adds the changes (JSON: `{"merge_request", "diff"}`). Shows draft state and reviewers. |
| `create` | `wt mr create --source <B> --target <B> --title <T> [--description <D>] [--draft] [--reviewer <WHO>]... [TREE]` | `--draft`: not mergeable until `ready`; owners are requested only then. |
| `ready` | `wt mr ready <NUMBER> [TREE]` | Mark a draft ready for review (`mr.ready`). |
| `reviewers` | `wt mr reviewers <NUMBER> [TREE] [add\|remove <WHO>...]` | List, request or withdraw review requests. |
| `owners` | `wt mr owners <NUMBER> [TREE]` | Owners and approval state per changed path. |
| `suggest` | `wt mr suggest --path <PATH> --lines <A-B> <--file <F>\|-m <TEXT>> [-b <TEXT>] <NUMBER> [TREE]` | Suggested change as a comment. |
| `apply-suggestion` | `wt mr apply-suggestion [-m <MSG>] <NUMBER> <COMMENT_ID> [TREE]` | Comment ids are shown by `wt mr comments`. |
| `approve` | `wt mr approve <NUMBER> [TREE]` | Same as `review --approve`. |
| `review` | `wt mr review <--approve\|--request-changes\|--comment> [-m <TEXT>] <NUMBER> [TREE]` | `--comment` needs `-m`. |
| `comment` | `wt mr comment --message <TEXT> [--path <PATH>] [--line <N>] <NUMBER> [TREE]` | `--line` refers to a line of `--path`. |
| `comments` | `wt mr comments <NUMBER> [TREE]` | Includes suggestions and whether they were applied. |
| `checks` | `wt mr checks <NUMBER> [TREE]` | Merge readiness, below. |
| `merge` | `wt mr merge [--method <fast-forward\|merge\|squash>] [-m <MSG>] <NUMBER> [TREE]` | Needs `mr:merge`. Conflicts exit with code `3`. |
| `mergeability` | `wt mr mergeability <NUMBER> [TREE]` | Possible methods, default, merge base, conflicts. |
| `close` | `wt mr close <NUMBER> [TREE]` | Close without merging. |
| `link` | `wt mr link [--tenant <SLUG>] <NAME> <TREE#N> <TREE#N>...` | Linked group, below. |
| `merge-group` | `wt mr merge-group [--tenant <SLUG>] [--method <METHOD>] <ID>` | One method for every member (default: each member's default). |
| `groups` | `wt mr groups [--tenant <SLUG>]` | |

### `wt mr checks`

Shows whether the merge request can be merged now and what blocks it. With `--json`:

```json
{
  "mergeable": false,
  "blockers": [
    {"kind": "approvals", "message": "1 of 2 required approvals on the current source tip"},
    {"kind": "ci", "message": "required CI checks have not passed: ci/test is pending"}
  ],
  "approvals": {"required": 2, "current": 1, "stale": 1, "changes_requested": []},
  "ci": {"state": "pending", "required": ["ci/build", "ci/test"], "missing": []},
  "todos": {"blocking_open": 0}
}
```

Blocker kinds: `state` (not open), `draft`, `source` (source branch missing or empty), `linked_group`, `approvals`, `changes_requested`, `owners` (owned paths without an owner approval, with `require_owner_approval`; the JSON adds `"owners": {"required", "missing"}`), `ci`, `todos`, `conflicts` (the three-way merge has conflicts), `merge_method` (no allowed method can merge), and, when no other allowed method can merge, `linear` (the source brings merge snapshots) and `diverged` (the target is not an ancestor of the source). The JSON also lists the possible `methods` and the `conflicts`. Messages above are illustrative.

### Linked merges across trees

Merge requests in different trees (or tenants) can be linked into a group that merges all or nothing:

```bash
wt mr link oauth acme/frontend#4 acme/backend#9
wt mr groups
wt mr merge-group <id>
```

- Creating a group needs `mr:merge` on every member tree. A merge request belongs to at most one open group.
- `merge-group` merges only when every member is mergeable; `--method` applies one method to every member. Merge and squash snapshots of every member are written first, then the tips move in order with compare-and-swap and are rolled back if one fails; the server publishes `group.merged`.
- Merging a member alone with `wt mr merge` answers `409` with code `linked_group`.

## `wt ci`

CI systems report check results per snapshot; branch protection can require them.

```text
wt ci report --snapshot <ID> --context <NAME> --state <STATE> [--description <TEXT>] [--url <URL>] [TREE]
wt ci status [--snapshot <ID> | --branch <B>] [TREE]
```

- `--state` is `pending`, `success`, `failure` or `error`. `--snapshot` also accepts a branch or tag, resolved to its snapshot. `--url` must be `http` or `https`.
- A newer report for the same snapshot and context replaces the older one. Each report publishes the event `ci.status`.
- The combined state is `failure` if any check is `failure` or `error`, else `pending` if any is `pending`, else `success` (empty when nothing was reported).
- Reporting needs `ci:report` (developer and above, or a scoped key).

A CI job typically uses a service-account key limited to `ci:report`:

```bash
# once, as a tenant admin
wt sa create acme ci --role developer --description "CI pipeline"
wt sa key-create acme ci --name github-actions --scope ci:report

# in the job: WT_TOKEN replaces saved logins, WT_SERVER picks the server
export WT_SERVER=https://wt.example.com WT_TOKEN="$WT_CI_KEY"
wt ci report acme/payments --snapshot "$SNAPSHOT_ID" --context ci/test \
  --state success --url "$JOB_URL" --description "212 tests passed"
```

Without `WT_TOKEN`, `wt` uses the credential saved by [`wt login`](/docs/cli/remote#wt-login) in `$WT_HOME/credentials.toml`. The key is also a plain bearer token for the REST API (`POST /api/v1/trees/{tenant}/{tree}/ci/status`). See [`wt sa`](/docs/cli/iam#wt-sa).

## `wt protect`

Branch and tag protection rules of a server tree. Rules are enforced on the server for everyone, server admins included.

```text
wt protect list [TREE]
wt protect set [OPTIONS] [TREE] <PATTERN>
wt protect remove [--yes] [TREE] <PATTERN>
wt protect tag list|set|remove ...
```

`wt protect set` creates **or replaces** the rule for a pattern: flags you leave out are off. Pass every flag the rule should keep.

| Flag | Rule field | Effect |
|---|---|---|
| `--no-direct-push` | `no_direct_push` | Changes reach matching branches only through merge requests. |
| `--approvals <N>` | `required_approvals` | Current approvals needed to merge (default `0`). |
| `--pusher <U>` | `allowed_pushers` | Accounts allowed to push (repeatable; default: anyone with write access). |
| `--no-delete` | `no_delete` | Matching branches cannot be deleted. |
| `--require-ci` | `require_ci_pass` | Merges need passing CI on the source tip: every `--check`, or every reported check when none is named. |
| `--check <NAME>` | `required_checks` | A CI context that must succeed (repeatable; implies `--require-ci`). |
| `--require-signed` | `require_signed` | Every pushed snapshot must carry a verified signature. See [Snapshot signing](/docs/cli/signing). |
| `--require-linear` | `require_linear` | No merge snapshots, in direct pushes or merged sources. |
| `--block-on-todos` | `block_on_todos` | Open blocking TODOs that target the source branch block merging. See [Dependencies](/docs/cli/dependencies#blocking-merges-on-todos). |
| `--require-owner-approval` | `require_owner_approval` | Every changed path needs an approval (of the current source tip) from one of its owners. See [Owner approval](/docs/server/review-workflow#owner-approval). |
| `--merge-methods <METHODS>` | `merge_methods` | Merge methods allowed into matching branches, comma-separated (`fast-forward`, `merge`, `squash`; default: all). See [Server-side merges](/docs/server/merging#restricting-methods-with-protection). |

```bash
wt protect set main --no-direct-push --approvals 2 --no-delete --check ci/build --check ci/test --require-signed --require-owner-approval
wt protect set "release/*" --no-direct-push --approvals 1 --require-linear
wt protect set develop --no-direct-push --merge-methods squash,fast-forward
wt protect list
```

Patterns are branch names or `path.Match` globs (`release/*`). All matching rules combine into their most restrictive form. Rule semantics: [Branch protection](/docs/server/branch-protection).

### Tag protection

```text
wt protect tag set [--no-delete] [--no-move] [--tagger <U>]... [--require-signed] [TREE] <PATTERN>
wt protect tag list [TREE]
wt protect tag remove [--yes] [TREE] <PATTERN>
```

```bash
wt protect tag set "v*" --no-delete --no-move --tagger release-bot --require-signed
```

`--no-move` stops matching tags from being replaced, `--no-delete` stops deletion, and `--tagger` limits who may create, move or delete them (default: anyone with `tree:write`). `--require-signed` refuses matching tags without a verified signature on push, REST create and release creation (`signature_required`); create them with `wt tag NAME --sign`. See [Signed-tag protection](/docs/server/release-integrity#signed-tag-protection).

See the [Server specification, section 9](https://github.com/seanfilimon/worktree/blob/main/crates/worktree-protocol/specs/server/Server.md#9-merge-requests-reviews-and-ci) for the full merge, review and CI rules.
