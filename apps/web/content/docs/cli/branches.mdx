Branches and tags belong to a tree: each tree (root or nested) has its own set. Commands act on the selected tree (`--tree <name>` or the tree containing the current directory). `REV` accepts the [revision syntax](/docs/cli#revision-syntax).

## `wt branch`

```text
wt branch [list] [-a] | create NAME [--from REV] | archive NAME | restore NAME
```

| Subcommand | Description |
|---|---|
| `list` (default) | List branches sorted by name, marking the current one. Archived branches are hidden. |
| `create NAME` | Create branch `NAME` pointing at the current head. Does not switch to it. |
| `archive NAME` | Soft-delete a branch: hide it from listings. Its snapshots stay reachable. |
| `restore NAME` | Un-archive a branch. |

| Flag | Applies to | Description |
|---|---|---|
| `-a` | `list` | Include archived branches. |
| `--from REV` | `create` | Start the new branch at `REV` instead of the current head. |

```bash
wt branch
wt branch -a
wt branch create feature/login
wt branch create hotfix --from v1.0.0
wt branch archive feature/old-spike
wt branch restore feature/old-spike
```

**Notes**

- Branches are **never hard-deleted**. Archiving keeps all history; an archived name cannot be reused for a new branch until it is restored.
- The current branch and the tree's default branch cannot be archived.
- Listings include the last known upstream tip (`origin/<branch>`) when one has been fetched.
- Creating a branch that already exists fails. `wt branch create` and `wt branch archive` append `branch.create` and `branch.archive` reflog entries.

## `wt switch`

```text
wt switch NAME [-c] [--force]
```

Make `NAME` the current branch and rewrite the tree's working directory to that branch's head: files are updated, tracked files absent from the target are removed. Ignored paths and nested-tree directories are never touched.

| Argument / flag | Description |
|---|---|
| `NAME` | Branch to switch to. |
| `-c` | Create `NAME` at the current head first, then switch to it. |
| `--force` | Switch even if there are uncommitted changes, **discarding** them. |

```bash
wt switch main
wt switch -c feature/search
wt switch main --force
```

**Notes**

- With uncommitted changes and no `--force`, `wt switch` refuses with "working tree has uncommitted changes (N files); snapshot them or use --force". Snapshot your work (or let the daemon do it) before switching.
- Appends a `switch` entry to the reflog.

## `wt merge`

```text
wt merge SOURCE [-m MSG] [--no-ff] | --continue [-m MSG] | --abort
```

Merge `SOURCE` (a branch or any revision, for example `origin/main`) into the current branch using a three-way merge against their best common ancestor.

| Argument / flag | Description |
|---|---|
| `SOURCE` | Branch or revision to merge into the current branch. |
| `-m MSG` | Message for the merge snapshot (with `SOURCE` or with `--continue`). |
| `--no-ff` | Always create a merge snapshot, even when a fast-forward is possible. |
| `--continue` | Finish a conflicted merge after resolving all conflicts. |
| `--abort` | Abandon a conflicted merge and restore the pre-merge state. |

### Outcomes

| Outcome | What happens | Exit code |
|---|---|---|
| Up to date | `SOURCE` is already contained in the current branch. Nothing changes. | `0` |
| Fast-forward | The current branch is an ancestor of `SOURCE`: the branch tip moves to `SOURCE` and files are checked out. Skipped with `--no-ff`. | `0` |
| Merged | A new snapshot with two parents (current tip, `SOURCE`) is created. | `0` |
| Conflicts | The working directory holds the partial merge; conflicts must be resolved. | `3` |

The working tree must be clean before merging; otherwise `wt merge` fails.

### How paths are merged

- Changed on one side only: that side's version is taken (including deletions).
- Identical changes on both sides: taken once.
- Text changed on both sides: line-based three-way merge (diff3 semantics). Non-overlapping edits are combined.

Conflict kinds:

| Kind | Cause | Working tree |
|---|---|---|
| `content` | Both sides changed overlapping lines. | Conflict markers written into the file. |
| `modify_delete` | One side modified the file, the other deleted it. | Resolve by keeping or deleting the file. |
| `add_add` | Both sides added the path with different content. | Merged two-way; markers written if lines overlap. |
| `binary` | A binary file changed on both sides. | Our version is kept. |

### Conflict markers

Markers are diff3-style, labelled with the branch names:

```text
<<<<<<< main
let timeout = 30;
||||||| base
let timeout = 10;
=======
let timeout = 60;
>>>>>>> feature/login
```

During a conflicted merge, `.wt/trees/<tree>/MERGE_STATE.json` stores the merge state (source branch and tip, target tip, base, conflicts, message) and `.wt/conflicts/<tree>.json` holds a machine-readable list of conflicts (each with `path` and `kind`) for editors and scripts. `wt status` shows the merge in progress.

### Resolving

```bash
wt merge feature/login
# exit code 3: edit the conflicted files and remove all markers
wt status
wt merge --continue -m "Merge feature/login"
```

```bash
# Or give up and return to the pre-merge state
wt merge --abort
```

**Notes**

- `--continue` fails while any conflict markers remain. `wt snapshot -m MSG` also completes the merge once markers are gone.
- Commands that cannot run during a pending merge fail with "a merge is in progress; resolve conflicts and run `wt merge --continue` or `wt merge --abort`", and the daemon does not auto-snapshot.
- Strategies and examples: [Merge strategies](/guides/merge-strategies), algorithm details: [Merge and diff](/docs/protocol/merge-and-diff).
- Server-side merge requests are managed via the [REST API](/docs/server/rest-api) and the [admin panel](/guides/admin-panel); there is no `wt` command for them.

## `wt tag`

```text
wt tag [list] | create NAME [REV] [-m MSG] | delete NAME
```

Tags are named, fixed pointers to a snapshot, used for releases.

| Subcommand | Description |
|---|---|
| `list` (default) | List tags: name, target snapshot, tagger, date, message. |
| `create NAME [REV]` | Tag `REV` (default `HEAD`) as `NAME`. |
| `delete NAME` | Delete the local tag `NAME`. |

| Flag | Applies to | Description |
|---|---|---|
| `-m MSG` | `create` | Tag message (annotation). |

```bash
wt tag
wt tag create v1.0.0 -m "First stable release"
wt tag create v0.9.0 4f9c2a1e
wt tag delete v1.0.0-rc1
```

**Notes**

- `wt push` uploads local tags the server does not have; `wt fetch` and `wt pull` download remote tags.
- `wt tag delete` removes the tag locally only. There is no command to delete a tag on the server.
- Creating a tag that already exists fails. Reflog entries: `tag.create`, `tag.delete`.
- See [Tags and releases](/guides/tags-and-releases).

<Callout type="info">
A tag name can be used anywhere a revision is accepted, for example `wt diff v1.0.0 HEAD`.
</Callout>
