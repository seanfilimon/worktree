---
title: Branches
description: Create, switch, archive and restore branches, merge them with three-way merges and resolve conflicts, and manage tags.
---


Branches and tags belong to a tree: each tree (root or nested) has its own set. Commands act on the selected tree (`--tree <name>` or the tree containing the current directory). `REV` accepts the [revision syntax](/docs/cli#revision-syntax). Server-side branches and tags of any tree can also be managed with [`wt trees`](/docs/cli/administration#wt-trees).

## `wt branch`

```text
Usage: wt branch [OPTIONS]
       wt branch <COMMAND>
```

| Subcommand | Description |
|---|---|
| `list` (default) | List branches sorted by name, marking the current one. Archived branches are hidden. |
| `create <NAME>` | Create branch `NAME` pointing at the current head. Does not switch to it. |
| `archive <NAME>` | Soft-delete a branch: hide it from listings. Its snapshots stay reachable. |
| `restore <NAME>` | Un-archive a branch. |

| Flag | Applies to | Description |
|---|---|---|
| `-a, --all` | `list` | Include archived branches. |
| `--from <REV>` | `create` | Start the new branch at `REV` instead of the current head. |

```bash
wt branch
wt branch -a
wt branch create feature/login
wt branch create hotfix --from v1.0.0
wt branch archive feature/old-spike
wt branch restore feature/old-spike
```

**Notes**

- Local branches are **never hard-deleted**. Archiving keeps all history; an archived name cannot be reused for a new branch until it is restored.
- The current branch and the tree's default branch cannot be archived.
- Listings include the last known upstream tip (`origin/<branch>`) when one has been fetched.
- Branch names may contain `/`; components must not start with `.` or `-` or end with `.lock`, and names may not contain whitespace, `~ ^ : ? * [ \`, `..` or `@{`. `HEAD` is reserved.
- Deleting a branch **on the server** is a separate, hard operation: [`wt trees branch-delete`](/docs/cli/administration#wt-trees), subject to `no_delete` protection.

## `wt switch`

```text
Usage: wt switch [OPTIONS] <NAME>
```

Make `NAME` the current branch and rewrite the tree's working directory to that branch's head: files are updated, tracked files absent from the target are removed. Untracked and ignored files and nested-tree directories are never touched.

| Argument / flag | Description |
|---|---|
| `NAME` | Branch to switch to. |
| `-c, --create` | Create `NAME` at the current head first, then switch to it. |
| `--force` | Switch even if there are uncommitted changes, **discarding** them. |

```bash
wt switch main
wt switch -c feature/search
wt switch main --force
```

**Notes**

- With uncommitted changes and no `--force`, `wt switch` refuses ("working tree has uncommitted changes (N files)"). When both branches point at the same snapshot, uncommitted changes are carried over untouched.
- With `auto_snapshot.on_branch_switch = "snapshot"` and the daemon watching the worktree, `wt switch` first asks the daemon to auto-snapshot the tree, so the switch can proceed. With `stash`, it stashes the changes as `auto-stash on <branch>` and restores them when you switch back to that branch (see [Auto-stash](/docs/cli/history-rewriting#auto-stash-on-branch-switch)). See [`on_branch_switch`](/docs/cli/configuration#branch-switches-with-uncommitted-changes).
- To set changes aside by hand, use [`wt stash`](/docs/cli/history-rewriting#wt-stash).
- Switching is refused while a merge is in progress. Appends a `switch` entry to the reflog.

## `wt merge`

```text
Usage: wt merge [OPTIONS] <SOURCE|--continue|--abort>
       wt merge <COMMAND>
```

Merge `SOURCE` (a branch or any revision, for example `origin/main`) into the current branch using a three-way merge against their best common ancestor.

| Argument / flag | Description |
|---|---|
| `SOURCE` | Branch or revision to merge into the current branch. |
| `-m, --message <MSG>` | Message for the merge snapshot (with `SOURCE` or with `--continue`). |
| `--no-ff` | Always create a merge snapshot, even when a fast-forward is possible. |
| `-s, --strategy <STRATEGY>` | How conflicting changes are resolved: `manual` (default) writes conflict markers and stops; `ours` / `theirs` resolve every conflicting hunk and file in favour of that side while still combining non-conflicting changes. |
| `--continue` | Finish a conflicted merge after resolving all conflicts. |
| `--abort` | Abandon a conflicted merge and restore the pre-merge state (same as `wt merge abort`). |

| Subcommand | Description |
|---|---|
| `resolve [PATH]... --ours\|--theirs\|--file <FILE>` | Resolve conflicted paths. `--ours` / `--theirs` take that side for conflicting hunks of a text file (non-conflicting changes from the other side are kept) and that side's version of binary or modify/delete conflicts; `--file F` uses the contents of `F`. `--all` resolves every unresolved conflict (with `--ours` or `--theirs`). |
| `abort` | Abandon the merge in progress and restore the pre-merge state. |
| `status` | Show the merge in progress and the state of each conflict. |

### Outcomes

| Outcome | What happens | Exit code |
|---|---|---|
| Up to date | `SOURCE` is already contained in the current branch. Nothing changes. | `0` |
| Fast-forward | The current branch is an ancestor of `SOURCE`: the branch tip moves to `SOURCE` and files are checked out. Skipped with `--no-ff`. | `0` |
| Merged | A new snapshot with two parents (current tip, `SOURCE`) is created. | `0` |
| Conflicts | The working directory holds the partial merge; conflicts must be resolved. | `3` |

The working tree must be clean before merging; otherwise `wt merge` fails. In a shallow clone, a merge whose base lies beyond the shallow boundary fails with a hint to run `wt fetch --deepen N`.

### How paths are merged

- Changed on one side only: that side's version is taken (including deletions).
- Identical changes on both sides: taken once.
- Text changed on both sides: line-based three-way merge (diff3 semantics). Non-overlapping edits are combined.

Conflict kinds:

| Kind | Cause | Working tree |
|---|---|---|
| `content` | Both sides changed overlapping lines. | Conflict markers written into the file. |
| `modify_delete` | One side modified the file, the other deleted it. | Resolve by keeping or deleting the file. |
| `add_add` | Both sides added the path with different content. | Merged two-way; markers written if lines overlap. |
| `binary` | A binary file changed on both sides. | Our version is kept until resolved. |

### Conflict markers

Markers are diff3-style and labelled with the side, the branch and a short snapshot id:

```text
<<<<<<< ours (main 1a2b3c4d)
let timeout = 30;
||||||| base (0f0f0f0f)
let timeout = 10;
=======
let timeout = 60;
>>>>>>> theirs (feature/login 5e6f7a8b)
```

During a conflicted merge, `.wt/trees/<tree>/MERGE_STATE.json` stores the merge state (source branch and tip, target tip, base, conflicts, resolved paths, message) and `.wt/conflicts/<tree>.json` holds a machine-readable list of conflicts for editors and scripts. Each entry has `path`, `kind` and `hunks` (`ours_start`, `ours_len`, `theirs_start`, `theirs_len` per conflicting region):

```json
[{"path":"src/auth/login.rs","kind":"content",
  "hunks":[{"ours_start":45,"ours_len":2,"theirs_start":45,"theirs_len":3}]},
 {"path":"assets/logo.png","kind":"binary","hunks":[]}]
```

### Resolving

```bash
wt merge feature/login
# exit code 3
wt merge status
wt merge resolve src/config.rs --theirs
wt merge resolve assets/logo.png --ours
# edit the remaining files and remove all markers
wt merge --continue -m "Merge feature/login"
```

```bash
# Take one side for everything that conflicts
wt merge feature/login --strategy theirs
wt merge resolve --all --ours

# Or give up and return to the pre-merge state
wt merge abort
```

**Notes**

- `--continue` fails (exit code `3`) while conflict markers remain in paths that were not resolved with `wt merge resolve`. `wt snapshot -m MSG` also completes the merge once markers are gone.
- Commands that cannot run during a pending merge fail with "a merge is in progress", and the daemon does not auto-snapshot the tree.
- Merges never cross trees. Strategies and examples: [Merge strategies](/guides/merge-strategies); algorithm details: [Merge and diff](/docs/protocol/merge-and-diff).
- The same conflict commands (`wt merge status`, `wt merge resolve`) resolve a stopped [`wt cherry-pick` or `wt rebase`](/docs/cli/history-rewriting#conflicts); finish those with their own `--continue`.
- Merge requests are merged on the server by fast-forward, merge snapshot or squash, with the same merge rules but without conflict markers: a conflicting request must be merged locally first. Open, review and merge them with [`wt mr`](/docs/cli/merge-requests#wt-mr); see [Server-side merges](/docs/server/merging).

## `wt tag`

```text
Usage: wt tag [OPTIONS] [NAME] [REV]
       wt tag <COMMAND>
```

Tags are named, fixed pointers to a snapshot, used for releases. `wt tag NAME [REV]` is short for `wt tag create NAME [REV]`.

| Subcommand | Description |
|---|---|
| `list` (default) | List tags: name, target snapshot, tagger, date, message, signature. |
| `create <NAME> [REV]` | Tag `REV` (default `HEAD`) as `NAME`. |
| `delete <NAME>` | Delete the local tag `NAME`. |
| `verify <NAME>` | Verify the tag's signature against your local keys (and, with `--account USER`, that account's registered keys). With `--remote [--from R]`, verify the server's copy instead of the local one. Exits `1` unless the signature is good. |
| `push <NAME>` | Push one tag to the server (`--remote R`, default `[sync] remote`) and fail with the server's reason when it is refused, for example an unsigned tag under a `require_signed` tag protection. |

| Flag | Applies to | Description |
|---|---|---|
| `-m, --message <MSG>` | `create` | Tag message (makes an annotated tag). |
| `--sign` | `create` | Sign the tag with your Ed25519 signing key (`[signing] key`, else `default`). `[signing] auto = true` signs every tag. |

```bash
wt tag
wt tag create v1.0.0 -m "First stable release"
wt tag v1.1.0 -m "Second release" --sign
wt tag create v0.9.0 4f9c2a1e
wt tag verify v1.1.0
wt tag verify v1.1.0 --remote --account ada
wt tag push v1.1.0
wt tag delete v1.0.0-rc1
```

**Notes**

- `wt push` uploads local tags whose target the server knows (refusals are logged, not fatal); `wt fetch` and `wt pull` download server tags. Tags are immutable on the server: pushing an existing name is refused.
- A signed tag carries an Ed25519 signature over its canonical record (name, target, message, tagger, time), made with the same keys as [snapshot signing](/docs/cli/signing). The signature travels with the tag on push, fetch and clone; the server verifies it against the signer's registered keys and marks the tag **verified**, or refuses a tag whose signature does not verify. The key is loaded before the tag is written, so a missing key leaves no unsigned tag behind. See [Signed tags](/docs/server/release-integrity#signed-tags).
- `wt tag delete` removes the tag locally only and is not propagated. Delete a server tag with [`wt trees tag-delete`](/docs/cli/administration#wt-trees) (needs `tree:admin`); the next `wt fetch` otherwise brings a pushed tag back.
- Servers can protect tags (who may create them, whether they can be moved or deleted, and whether they must be signed) with [`wt protect tag`](/docs/cli/merge-requests#wt-protect).
- Releases are built on tags: see [`wt release`](/docs/cli/dependencies#wt-release) and [Tags and releases](/guides/tags-and-releases).

<Callout type="info">
A tag name can be used anywhere a revision is accepted, for example `wt diff v1.0.0 HEAD`.
</Callout>
