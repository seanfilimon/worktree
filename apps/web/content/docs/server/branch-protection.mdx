Branch protection rules restrict how branches matching a pattern may change; tag protection rules do the same for tags. Merge requests are the path for changing a branch that does not accept direct pushes. Everything here is enforced on the server, for everyone, server admins included; there is no bypass permission.

Manage rules with [`wt protect`](/docs/cli/merge-requests#wt-protect), merge requests with [`wt mr`](/docs/cli/merge-requests#wt-mr) and CI results with [`wt ci`](/docs/cli/merge-requests#wt-ci), or use the [REST API](/docs/server/rest-api#protections) and the admin panel. Rule changes need `tree:admin`.

## Protection rules

A rule belongs to one tree and is keyed by its `pattern`.

| Field | Type | `wt protect set` flag | Meaning |
|---|---|---|---|
| `pattern` | string | `PATTERN` | Branch name glob, Go `path.Match` semantics: `*` matches any run except `/`, `?` one character, `[...]` a class. |
| `no_direct_push` | bool | `--no-direct-push` | Reject every direct push; the branch moves only when a merge request is merged. |
| `required_approvals` | int | `--approvals N` | Current approvals a merge request needs. `0` means none. |
| `allowed_pushers` | string array | `--pusher U` (repeatable) | Usernames allowed to push. Empty: anyone with `tree:write`. |
| `no_delete` | bool | `--no-delete` | Matching branches cannot be deleted. |
| `require_ci_pass` | bool | `--require-ci` | Merges need passing CI on the source tip. |
| `required_checks` | string array | `--check NAME` (repeatable, implies `--require-ci`) | CI contexts that must be `success`. Empty with `require_ci_pass`: every reported check must succeed. |
| `require_signed` | bool | `--require-signed` | Every pushed snapshot must carry a verified signature. See [signing](/docs/cli/signing). Also forbids the `merge` and `squash` methods, because the server cannot sign the snapshots it writes. |
| `require_linear` | bool | `--require-linear` | No merge snapshots: direct pushes must be linear, the `merge` method is forbidden, and fast-forwarded sources must not contain merges. |
| `block_on_todos` | bool | `--block-on-todos` | Open blocking TODOs that target the source branch block merging. See [TODOs](/docs/cli/dependencies#wt-todo). |
| `require_owner_approval` | bool | `--require-owner-approval` | Every owned changed path needs an approval of the current source tip from one of its [path owners](/docs/server/review-workflow#owner-approval). |
| `merge_methods` | string array | `--merge-methods a,b` | Merge methods allowed for merge requests into matching branches (`fast-forward`, `merge`, `squash`). Empty: all. Lists of several matching rules intersect. See [Server-side merges](/docs/server/merging). |

Every rule whose pattern matches a branch applies to it; matching rules combine into their most restrictive form. Branch listings report `protected: true` for branches that at least one rule matches.

### Pattern examples

| Pattern | Matches | Does not match |
|---|---|---|
| `main` | `main` | `main2`, `feature/main` |
| `release/*` | `release/1.0`, `release/2026-10` | `release/1.0/hotfix`, `release` |
| `*` | every branch without a `/` | `feature/x` |
| `hotfix-?` | `hotfix-1`, `hotfix-a` | `hotfix-10` |

### Creating a rule

```bash
wt protect set acme/payments main --no-direct-push --approvals 2 --no-delete --check ci/build --check ci/test --require-signed
wt protect set acme/payments 'release/*' --no-direct-push --approvals 1 --require-linear --block-on-todos
wt protect list acme/payments
wt protect remove acme/payments 'release/*'
```

`wt protect set` creates or replaces the whole rule: flags you leave out are off. Inside a worktree the tree argument can be omitted. Over REST:

```bash
curl -s -X PUT http://localhost:7420/api/v1/trees/acme/payments/protections \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"pattern":"main","no_direct_push":true,"required_approvals":2,"allowed_pushers":[],"no_delete":true,"require_ci_pass":true,"required_checks":["ci/build"],"merge_methods":["squash","fast-forward"]}'
```

`DELETE .../protections?pattern=main` removes a rule. See the [branch protection guide](/guides/branch-protection) for recommended setups.

## Tag protection

Pushing an existing tag name is refused; only a `tree:admin` can replace a tag, with REST `POST {tree}/tags` and `"force": true`, or delete one. Tag protection rules restrict who may create tags and whether they may be deleted or replaced:

| Field | `wt protect tag set` flag | Meaning |
|---|---|---|
| `pattern` | `PATTERN` | Tag name glob, for example `v*`. |
| `no_delete` | `--no-delete` | Matching tags cannot be deleted. |
| `no_move` | `--no-move` | Matching tags cannot be replaced (moved to another snapshot). |
| `allowed_taggers` | `--tagger U` (repeatable) | Accounts allowed to create, move or delete matching tags. Empty: anyone with `tree:write`. |
| `require_signed` | `--require-signed` | Matching tags must carry a verified signature (`wt tag NAME --sign`), also tags created by a release. See [Release integrity](/docs/server/release-integrity#signed-tag-protection). |

```bash
wt protect tag set acme/payments 'v*' --no-delete --no-move --tagger release-bot --require-signed
wt protect tag list acme/payments
```

REST: `GET|PUT|DELETE {tree}/tag-protections` (`DELETE` takes `?pattern=`). Rules apply to `PushTag` from `wt push` and to REST tag creation and deletion.

## How pushes are checked

On every push the server checks `tree:write` and `branch:push` (policies can deny one branch), then branch protection, then snapshot records, objects, fast-forward, license rules and the push checks (see the [push flow](/docs/server#what-happens-on-a-push)). Protection rejects the push when a matching rule:

- has `no_direct_push`; or
- has a non-empty `allowed_pushers` that does not contain the pusher; or
- has `require_linear` and the push contains a merge snapshot; or
- has `require_signed` and a new snapshot has no verified signature (an invalid signature is rejected on any branch).

A rejected push changes nothing and `wt push` exits with an error naming the rule. Deleting a branch (`wt trees branch-delete`, REST `DELETE {tree}/branches/{name}`) is refused for the default branch and for branches with `no_delete`. Locally, `wt branch archive` only soft-deletes. See [`wt branch`](/docs/cli/branches#wt-branch).

## Merge requests

A merge request asks the server to bring `source_branch` into `target_branch`, within one tree.

| State | Meaning |
|---|---|
| `open` | Created and awaiting reviews or merge. |
| `merged` | The target was fast-forwarded, merged or squashed. `merged_at`, `merged_snapshot` and `merge_method` are set. |
| `closed` | Closed without merging. |

Numbers are per tree and start at 1.

<Steps>
<Step>

### Push the source branch and open

```bash
wt switch -c feature/refunds
wt snapshot -m "Add refund endpoint"
wt push --branch feature/refunds
wt mr create --source feature/refunds --target main --title "Add refund endpoint"
```

Requires `mr:create`. Publishes `mr.opened`.

</Step>
<Step>

### Review

```bash
wt mr show 4 --diff
wt mr comment 4 -m "Handle partial refunds" --path src/refund.rs --line 42
wt mr review 4 --request-changes -m "Needs a test"
wt mr review 4 --approve
```

An approval (`mr:approve`; authors cannot approve their own merge request) records the source tip it approved. **Approvals go stale** when the source branch moves and must be renewed. A `--request-changes` review from someone with `mr:approve` blocks merging until that reviewer approves the current tip. `--comment` reviews need only `tree:read`.

</Step>
<Step>

### Report CI

CI systems report results per snapshot and context, using a token with `ci:report` (for example a service-account key scoped to `ci:report`):

```bash
wt ci report --snapshot feature/refunds --context ci/build --state success --url https://ci.example.com/runs/812 acme/payments
wt ci status --branch feature/refunds acme/payments
```

The combined state is `failure` if any check failed or errored, else `pending` if any is pending, else `success`. A newer report for the same snapshot and context replaces the old one.

</Step>
<Step>

### Check and merge

```bash
wt mr checks 4
wt mr merge 4                    # or --method fast-forward|merge|squash
```

`wt mr checks` (`GET .../merge-requests/{n}/checks`) shows `mergeable` and the blockers:

```json
{
  "mergeable": false,
  "blockers": [
    {"kind": "approvals", "message": "1 of 2 required approvals (1 stale)"},
    {"kind": "ci", "message": "required CI checks have not passed: missing ci/test"}
  ],
  "approvals": {"required": 2, "current": 1, "stale": 1},
  "ci": {"state": "pending", "required": ["ci/build", "ci/test"], "missing": ["ci/test"]},
  "todos": {"blocking_open": 0}
}
```

Blocker kinds are `state`, `draft`, `source`, `linked_group`, `approvals`, `owners` (with `require_owner_approval`), `changes_requested`, `ci`, `todos`, `conflicts`, `merge_method`, and, when no other allowed method can merge, `linear` and `diverged` (the target is not an ancestor of the source). The response also lists the possible `methods` and any `conflicts`. The messages above are illustrative.

A merge (`mr:merge`) enforces the same checks (required approvals, change requests, `require_ci_pass`, `block_on_todos`), then merges with the requested method, or by default fast-forwards when it can and otherwise writes a merge snapshot (the first method protection allows). The target moves with compare-and-swap. A refused merge answers `409 draft` for a [draft](/docs/server/review-workflow#draft-merge-requests), `409 linked_group` for a linked-group member, `403 review_required` for missing approvals, `409 merge_blocked` (listing the blockers) for change requests, missing owner approvals, CI, blocking TODOs or non-linear history, `409 quota_exceeded` when the merge snapshot would exceed the tenant's storage quota, `409 merge_method_not_allowed`, `409 merge_conflict` with the conflicting paths, or `409 conflict` for a fast-forward on diverged branches. Success publishes `mr.merged` and `branch.pushed`. Methods, conflicts and mergeability: [Server-side merges](/docs/server/merging).

</Step>
</Steps>

Close an open merge request without merging with `wt mr close 4`, which publishes `mr.closed`.

### Linked merge requests

Changes that span trees can be merged together. Group merge requests of several trees, then merge them all or none:

```bash
wt mr link oauth acme/frontend#4 acme/backend#9
wt mr groups
wt mr merge-group <ID>
```

Creating a group needs `mr:merge` on every member tree. Every member must be mergeable; `wt mr merge-group --method M` uses one method for all of them. Tips move in order and are rolled back on failure, and `group.merged` is published. Merging one member alone answers `409 linked_group`.

### Resolving a merge conflict

A diverged target is merged on the server with `merge` or `squash` as long as the three-way merge is clean. The server never writes conflict markers: when there are conflicts (`409 merge_conflict`), or when protection allows only fast-forwards, bring the target into the source locally and push:

```bash
wt pull --branch main
wt switch feature/refunds
wt merge main -m "Merge main into feature/refunds"
# resolve any conflicts, then: wt merge --continue
wt push --branch feature/refunds
```

The source tip now descends from the target, so the merge request can fast-forward. Pushing the source makes existing approvals stale, so reviewers approve again. With `require_linear`, the merged source must not contain merge snapshots: merge with `--method squash`, or keep unpushed work linear with [`wt rebase`](/docs/cli/history-rewriting#wt-rebase) before the first push (pushed snapshots cannot be rewritten). See [`wt merge`](/docs/cli/branches#wt-merge) and the [merge strategies guide](/guides/merge-strategies).

<Callout type="info">
  Rebase merges on the server, resolving conflicts in the browser, automatic source-branch deletion and force pushes are not built (see the [roadmap](/roadmap)). The wire protocol defines a `ci_checks_failed` push rejection, but CI gates apply to merges, not pushes.
</Callout>
