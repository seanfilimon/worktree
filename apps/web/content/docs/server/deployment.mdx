This page covers running the server for a team. For a narrative walkthrough, see the [self-hosting guide](/guides/self-hosting); for day-to-day knobs, see [Operations](/docs/server/operations).

## Production checklist

- [ ] Build the binary (and the admin panel) from a tagged source checkout, or build the container image. See [Installation](/docs/server/installation).
- [ ] Run as a dedicated, unprivileged user with its own data directory (`--data`).
- [ ] Encrypt traffic: either built-in TLS (`--tls-cert`/`--tls-key`), or listen on loopback (`--addr 127.0.0.1:7420`) behind a TLS-terminating proxy and set `--trusted-proxies`. Never serve cleartext on a public address (the server warns when you do).
- [ ] Set the admin password through `WT_ADMIN_PASSWORD` from a file readable only by the service user, not on the command line.
- [ ] Disable self-service registration (`--allow-registration=false`) unless you want open sign-up; create accounts with `wt admin account-create` or invitations.
- [ ] Set `--public-url` if you configure SSO.
- [ ] Decide retention: `--staged-retention` (default 7 days), `--audit-retention` (default keep forever), `--gc-grace` (default 30 days).
- [ ] Review `--rate-limit` (default 1,200 requests per minute per principal) and default quotas (`--default-max-trees`, `--default-max-storage`).
- [ ] Restrict `/metrics` to your monitoring network.
- [ ] Add browser origins that call the API from elsewhere to `--cors-origins`.
- [ ] Schedule backups of the data directory and test a restore. See [Storage](/docs/server/storage#backup).
- [ ] Monitor `/healthz`, disk space and the audit log. See [Monitoring](/docs/server/monitoring).

## Reverse proxy and TLS

You have two options.

### Option 1: built-in TLS

The server terminates TLS on its own port; HTTPS and gRPC share it through ALPN `h2`:

```bash
worktree-server \
  --addr :443 \
  --tls-cert /etc/worktree/tls/fullchain.pem \
  --tls-key /etc/worktree/tls/privkey.pem \
  --public-url https://wt.example.com
```

Add `--tls-client-ca /etc/worktree/tls/clients-ca.pem` to require client certificates (mTLS). The server reads the certificate at startup: restart it after renewing (for example from your ACME client's deploy hook). Clients use the `https://` URL directly:

```bash
wt remote add origin https://wt.example.com --tenant acme
wt login https://wt.example.com -u ada
```

### Option 2: a TLS-terminating reverse proxy

Run the server on loopback and let the proxy handle certificates. The proxy must:

1. terminate TLS for clients;
2. forward gRPC (`Content-Type: application/grpc`, path prefix `/worktree.sync.v1.SyncService/`) to the backend over **HTTP/2 cleartext** (h2c), because gRPC needs HTTP/2 end to end;
3. pass REST and `/admin/` requests through (HTTP/1.1 or h2c both work);
4. not buffer the SSE stream at `/api/v1/events`, and allow long-lived responses (heartbeat every 15 seconds) and long-lived gRPC streams (`WatchBranches`, used by the daemon);
5. allow request bodies of at least 64 MiB (gRPC messages and release assets);
6. set `X-Forwarded-For`, and the server must list the proxy in `--trusted-proxies` so audit records, policy IP conditions and per-IP rate limits see the real client:

```bash
worktree-server --addr 127.0.0.1:7420 --trusted-proxies 127.0.0.1 --public-url https://wt.example.com
```

#### Caddy

Caddy obtains certificates automatically and can speak h2c to the backend for all traffic:

```text
wt.example.com {
	@metrics_external {
		path /metrics
		not remote_ip 10.0.0.0/8 192.168.0.0/16
	}
	respond @metrics_external 403

	reverse_proxy h2c://127.0.0.1:7420 {
		flush_interval -1
	}
}
```

The `h2c://` scheme makes Caddy speak cleartext HTTP/2 to the backend for every request, so gRPC, REST, SSE and the admin panel share one upstream. `flush_interval -1` flushes responses immediately, which keeps the event stream live. Caddy sets `X-Forwarded-For` by default.

#### nginx

nginx forwards gRPC with `grpc_pass` (HTTP/2 to the backend) and everything else with `proxy_pass`. The `http2 on;` directive needs nginx 1.25.1 or newer; on older versions write `listen 443 ssl http2;`.

```text
upstream worktree {
    server 127.0.0.1:7420;
}

server {
    listen 443 ssl;
    http2 on;
    server_name wt.example.com;

    ssl_certificate     /etc/ssl/wt.example.com/fullchain.pem;
    ssl_certificate_key /etc/ssl/wt.example.com/privkey.pem;

    client_max_body_size 64m;

    # gRPC sync service (wt, worktree-bg)
    location /worktree.sync.v1.SyncService/ {
        grpc_pass grpc://worktree;
        grpc_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        grpc_read_timeout 1h;
        grpc_send_timeout 1h;
    }

    # Server-Sent Events
    location /api/v1/events {
        proxy_pass http://worktree;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 1h;
    }

    location = /metrics {
        allow 10.0.0.0/8;
        deny all;
        proxy_pass http://worktree;
    }

    # REST API, /healthz, admin panel
    location / {
        proxy_pass http://worktree;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

<Callout type="info" title="Client URLs">
  Remote URLs are the public `https://` origin of the proxy or of the server. `wt` and the daemon speak gRPC over TLS for `https://` remotes and h2c for `http://` remotes. See [Security](/docs/security).
</Callout>

## Running as a service

### systemd (Linux)

<Steps>
<Step>

### Create a user and directories

```bash
sudo useradd --system --home /var/lib/worktree --shell /usr/sbin/nologin worktree
sudo install -d -o worktree -g worktree -m 0750 /var/lib/worktree /var/lib/worktree/data
sudo install -m 0755 worktree-server /usr/local/bin/worktree-server
sudo cp -r apps/admin/dist /opt/worktree-admin
```

</Step>
<Step>

### Store secrets in an environment file

```bash
sudo install -d -m 0750 /etc/worktree
sudo install -m 0600 /dev/null /etc/worktree/server.env
sudoedit /etc/worktree/server.env
```

```text
WT_ADMIN_USER=admin
WT_ADMIN_PASSWORD=use-a-long-random-secret
WT_PUBLIC_URL=https://wt.example.com
WT_TRUSTED_PROXIES=127.0.0.1
WT_LOG_FORMAT=json
```

</Step>
<Step>

### Install the unit

`/etc/systemd/system/worktree-server.service`:

```text
[Unit]
Description=W0rkTree server
After=network-online.target
Wants=network-online.target

[Service]
User=worktree
Group=worktree
WorkingDirectory=/var/lib/worktree
EnvironmentFile=/etc/worktree/server.env
ExecStart=/usr/local/bin/worktree-server \
  --addr 127.0.0.1:7420 \
  --data /var/lib/worktree/data \
  --admin-dir /opt/worktree-admin \
  --allow-registration=false
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/worktree
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now worktree-server
curl -s http://127.0.0.1:7420/healthz
```

</Step>
</Steps>

`systemctl stop` sends `SIGTERM`: the server stops accepting work, drains connections within `--shutdown-timeout` (default 15 s), audits `server.stop` and exits.

### Windows

`worktree-server.exe` runs as an ordinary console program; it does not register itself with the Windows Service Control Manager. To run it as a service, use a service wrapper such as NSSM or WinSW, or a Task Scheduler task that runs at startup. Configure the same flags, and set `WT_ADMIN_PASSWORD` in the wrapper's environment settings rather than on the command line.

## Containers

The repository root has a `Dockerfile.server` that builds the admin panel and a static Go binary and packages both in an Alpine image. No image is published; build it yourself:

```bash
docker build -f Dockerfile.server -t worktree-server .
docker run -d --name worktree -p 7420:7420 -v wt-data:/data \
  -e WT_ADMIN_PASSWORD='use-a-long-random-secret' -e WT_ALLOW_REGISTRATION=false \
  worktree-server
```

The image runs as the unprivileged user `worktree` (uid 10001), stores data in the `/data` volume, serves the bundled admin panel from `/app/admin` (`WT_ADDR=:7420`, `WT_DATA=/data`, `WT_ADMIN_DIR=/app/admin`) and declares a `HEALTHCHECK` on `/healthz`. Pass any other setting as a `WT_*` environment variable, for example `WT_TLS_CERT` and `WT_TLS_KEY` with the certificate files mounted into the container. Build arguments `VERSION` and `COMMIT` set the reported version.

For a local stack, `docker-compose.yml` runs the server (port 7420, with the admin panel) and this documentation site (port 3000):

```bash
WT_ADMIN_PASSWORD=change-me docker compose up --build
```

Keep the data volume on persistent storage and run a single container per data directory: bbolt allows only one process to open `meta.db`.

## Upgrading

1. Back up the data directory.
2. Build the new version and replace the binary (and the admin panel build), or rebuild the image.
3. Restart the service and check `/healthz` for the new `version`.

The server refuses to open a `meta.db` written by a newer schema, so keep the backup until the new version has run cleanly. The project is pre-1.0: read the [changelog](/changelog) before upgrading.
