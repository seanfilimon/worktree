title: Secret Scanning and License Audit
description: Since v0.8 the server scans every push for secrets with the same rules as the client, records findings, blocks pushes in block mode and keeps an allowlist; the license audit checks a snapshot against the tree's license rules and the SPDX License List.
---


Secrets (API keys, tokens, private keys, passwords) are caught twice:

1. **On the client, before every snapshot.** `wt` refuses the snapshot by default (see [Secret scanning](/docs/cli/configuration#secret-scanning)). `wt snapshot --no-scan` and `[secret_scanning] block_on_match = false` let content through locally.
2. **On the server, on every push** (v0.8). The server records what it finds and, in a tree's `block` mode, rejects the push. The client's `--no-scan` has no effect here.

Both sides run the **same rule set** from one JSON file (`crates/worktree-protocol/src/scan_rules.json`, embedded byte-identical by the Go server) and produce the same findings, redacted excerpts and fingerprints for the same bytes. Tree administrators manage the server side per tree: the mode, exclusions, an allowlist of known false positives, and the findings. The [Secret scanning specification](https://github.com/seanfilimon/worktree/blob/main/crates/worktree-protocol/specs/security/SecretScanning.md) is normative.

## Rules

Built-in rules, in priority order: `private-key`, `aws-access-key`, `aws-secret-key`, `github-fine-grained-token`, `github-token`, `gitlab-token`, `slack-webhook`, `slack-token`, `stripe-secret-key`, `google-api-key`, `npm-token`, `anthropic-api-key`, `openai-api-key`, `jwt` and two `generic-secret` rules (quoted and `.env`/YAML-style assignments to password, secret, token, api_key and credential variables).

- Rules run only on files containing one of their keywords; values must pass entropy, letter-and-digit and placeholder filters (`example`, `xxx`, `changeme`, `your`, `${`, `{{`, ...).
- Binary files (a NUL byte in the first 8000 bytes) are skipped. A line containing `wt:allow-secret` is never reported, on the client or the server.
- Excerpts never contain the secret: values of 12 or more characters keep their first and last four (`AKIA****Y3U6`), shorter ones become `****`.

A finding's **fingerprint** identifies the secret wherever it appears: `hex(BLAKE3("wt-secret-v1" NUL rule NUL value))[0..24]`. It is a truncated hash (96 bits): it does not reveal high-entropy secrets, but only tree members see it.

## Modes

```bash
wt compliance settings                                     # show the current tree's settings
wt compliance settings --mode block                        # reject pushes with secrets
wt compliance settings --exclude 'testdata/**' --exclude 'docs/examples/**'
wt compliance settings --max-file-bytes 2097152
```

| Mode | Push with findings |
|---|---|
| `off` | Not scanned |
| `warn` (default) | Accepted; findings stored (`action: warned`), event and audit |
| `block` | Rejected (`action: blocked`), unless the pusher holds `branch:bypass_protection` on the tree (owners), in which case it is accepted (`action: bypassed`) |

A blocked push is answered as `access_denied` with up to ten findings and the way out:

```text
access denied: secret scanning blocked the push: 1 possible secret(s)
  src/app.rs:2 [github-token] const T: &str = "ghp_****2Zx9"; (fingerprint fd07e02d5902c12c017b886a)
remove the secret from every new snapshot and push again; a false positive can be allowed by a tree admin with `wt compliance allow FINGERPRINT --reason ...`
```

Remove the secret from **every new snapshot**, not just the tip, for example with [`wt undo`](/docs/cli/force-push-and-undo#undo-and-redo) or [`wt rebase`](/docs/cli/history-rewriting#wt-rebase), and push again. Rotate the secret anyway: it has left your machine.

### What is scanned

For a push, the server scans, for each new snapshot, the files that differ from its first parent (so a secret added and removed again within one push is still found, attributed to the snapshot that introduced it). With more than 256 new snapshots (imports) only what the new tip adds relative to the old tip is scanned; a branch created at an already stored snapshot scans nothing.

Skipped: chunked files (over 8 MiB), files larger than the tree's `max_file_bytes` (default 1 MiB, at most 16 MiB), paths matching an `exclude` glob (license-rule glob syntax), and, once 64 MiB have been collected, the rest of the push (the event carries `truncated`). In `warn` mode a scanner failure is logged and the push proceeds; in `block` mode it fails the push (fail closed). Server-side merges and conflict resolutions are not scanned.

## The allowlist

```bash
wt compliance allow 683e63ab39e025dc3e6ea642 --reason "AWS documentation example key"
wt compliance allow --list
wt compliance disallow 683e63ab39e025dc3e6ea642 --yes
```

The allowlist names fingerprints of known false positives with a required reason (at most 500 bytes; at most 1000 entries per tree). Allowlisted secrets produce no findings and never block, in any mode and for anyone. Adding an entry resolves the open findings with that fingerprint as `false_positive`.

## Findings

```bash
wt compliance findings                       # open findings of the current tree
wt compliance findings --status all --tree acme/web
wt compliance resolve 9f2c51e07d3a4b18 --as revoked --note "rotated 2026-10-26"
wt compliance resolve 9f2c51e07d3a4b18 --reopen
```

There is one finding per (fingerprint, path) and tree. A later push containing the same secret at the same path updates it (`count`, `last_seen_at`, `line`, `excerpt`, `branch`, `snapshot_id`, `action`, `pushed_by`); a resolved finding is reopened when the secret lands again. Resolutions are `revoked`, `false-positive`, `test-data` and `wont-fix` (stored as `false_positive`, `test_data`, `wont_fix`) with an optional note. Resolving does not let a secret through a blocked push; the allowlist does.

```json
{
  "id": "9f2c51e07d3a4b18", "path": "config/aws.env", "line": 2,
  "rule": "aws-access-key", "excerpt": "AWS_ACCESS_KEY_ID=AKIA****Y3U6",
  "fingerprint": "683e63ab39e025dc3e6ea642", "branch": "main", "snapshot_id": "…",
  "status": "open", "action": "warned", "count": 1, "pushed_by": "bob",
  "first_seen_at": "…", "last_seen_at": "…"
}
```

## On-demand scans

```bash
wt compliance scan                       # the current tree's working files (local); exit 1 on findings
wt compliance scan src/config            # one file or directory
wt compliance scan --server --ref main   # a snapshot on the server, with the tree's exclusions and size cap
```

The local scan covers the working files of the current tree (ignored paths, nested trees and `.wt/` skipped; files over 8 MiB skipped), even when automatic scanning is disabled, and applies the tree's `[secret_scanning]` configuration (exclude globs, extra patterns). `--server` calls `POST {tree}/compliance/scan` (`tree:admin`), which scans every file of a branch, tag or snapshot and flags allowlisted matches; nothing is stored. Both print every finding with its fingerprint and exit `1` when a match is not allowlisted. `--server` shares the global `--server URL` flag: bare, it scans on the default server.

## License audit

```bash
wt license audit                    # the current tree's default branch
wt license audit acme/web --ref release/2.0
wt license audit --strict           # exit 1 on an invalid rule or an exposed proprietary path
```

`wt license audit` (`GET {tree}/compliance/licenses`, `tree:admin`) audits a snapshot against the tree's [license rules](/docs/server/licensing):

- **Files per license**: every file resolved against the live general rules (most specific glob wins), counted per SPDX expression with the globs that assign it and whether it is proprietary.
- **Unlicensed paths**: files no general rule matches.
- **Exposed proprietary paths**: files whose governing license is proprietary but which a non-member can read, through a grant on the general rule or a grantee rule that permits reading.
- **Rule checks**: every rule (expired ones flagged) with the number of files it governs and a **strict SPDX check**: the expression must parse, every identifier must be on the SPDX License List in its canonical case and not deprecated (`GPL-2.0`, `GPL-2.0+`, `LGPL-2.1`... are deprecated: use the `-only` / `-or-later` forms), and exceptions after `WITH` must be listed exceptions. `LicenseRef-...`, `DocumentRef-...:LicenseRef-...` and W0rkTree's `Proprietary` keyword are accepted.

The SPDX License List (version 3.25) is embedded in the server. Path lists are capped at 1000 entries (`truncated`); counts are exact. Server administrators get a server-wide summary at `GET /api/v1/admin/compliance` and on the admin panel's **Compliance** page: per tree the mode, open, resolved and blocked findings, allowlist size, license rules and rules failing the strict check, plus the 20 most recent open findings.

## Admin panel

- Tree tab **Compliance**: scanning mode, excluded paths and size cap (tree admins edit, others read); findings filtered open / resolved / all with location, redacted excerpt, last push action, fingerprint and time; resolve, allowlist and reopen dialogs; the allowlist; the license audit of the default branch.
- Page **Compliance** (server admins): totals, modes, the per-tree table and the latest open findings.

## Events and audit

- Event **`secret.detected`** for every push with findings (any mode): `{tree, branch, new_tip, mode, action, count, allowed, truncated, findings: [{id, path, line, rule, excerpt, fingerprint}]}` (at most 20 findings). Subscribe with [webhooks](/docs/server/webhooks) or the [event stream](/docs/server/events).
- Audit `secret.detected`; a blocked push is also audited as `branch.push_rejected` with reason `secret_detected`. REST changes are audited as `compliance.settings`, `compliance.finding.resolve`, `compliance.finding.reopen`, `compliance.allow.add` and `compliance.allow.remove`.

## REST API

All under `/api/v1/trees/{tenant}/{tree}`.

| Method and path | Permission | Notes |
|---|---|---|
| `GET compliance/settings` | `tree:read` | Defaults when never set |
| `PUT compliance/settings` | `tree:admin` | `{mode?, exclude?, max_file_bytes?}` |
| `GET compliance/findings` | `tree:write` | `?status=open` (default) `\|resolved\|all`, `limit` at most 1000 |
| `POST compliance/findings/{id}/resolve` | `tree:admin` | `{resolution, note?}` or `{reopen: true}` |
| `GET compliance/allowlist` | `tree:write` | |
| `POST compliance/allowlist` | `tree:admin` | `{fingerprint, reason}` → `201` |
| `DELETE compliance/allowlist?fingerprint=` | `tree:admin` | `204` |
| `POST compliance/scan` | `tree:admin` | `{ref?}` |
| `GET compliance/licenses` | `tree:admin` | `?ref=` |
| `GET /api/v1/admin/compliance` | `server:admin` | Server-wide summary |

Without the scan component the routes answer `501`.

## Performance

On the reference machine (Go benchmarks, one core per file) the scanner reads about 135-175 MB/s of source and prose and about 190 MB/s through the whole push check (manifests, blob reads, scan, store); the worst case (a keyword and a long value on every line) drops to about 4 MB/s and is bounded by the 1 MiB default file cap, the 64 MiB push budget and eight parallel workers.
