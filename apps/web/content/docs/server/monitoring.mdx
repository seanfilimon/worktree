## Health check

`GET /healthz` needs no authentication and has no `/api/v1` prefix.

```bash
curl -s http://localhost:7420/healthz
```

```json
{"status":"ok","version":"0.2.0","uptime_seconds":86400}
```

| Field | Meaning |
|---|---|
| `status` | `ok` when the server is serving requests. |
| `version` | Server version string. |
| `uptime_seconds` | Seconds since the process started. |

Use it for load balancer health checks, container liveness probes, and uptime monitors. For a gRPC-level check, `wt` clients call the `Ping` RPC, which is allowed anonymously.

## Prometheus metrics

`GET /metrics` returns server metrics in the Prometheus text exposition format, without authentication, for scraping by Prometheus or any compatible collector.

```yaml
scrape_configs:
  - job_name: worktree
    metrics_path: /metrics
    static_configs:
      - targets: ['wt.internal.example.com:7420']
```

<Callout type="info">
  Metric names are not a stable contract in v0.2.0. Inspect `/metrics` on your build before writing alerts or dashboards. Because `/metrics` is unauthenticated, do not expose it publicly; restrict it at your reverse proxy (see [Deployment](/docs/server/deployment)).
</Callout>

## Logs

The server writes structured log messages (Go `log/slog`) to the console. Set the verbosity with `--log-level` (`debug`, `info`, `warn`, `error`). Under systemd, read them with `journalctl -u worktree-server`. Recording an audit event never fails the request that caused it; if an audit event cannot be persisted, the error is logged instead.

## Admin statistics

Server admins can read aggregate counts from `GET /api/v1/admin/stats`, which the admin panel's dashboard displays:

```json
{
  "tenants": 4,
  "accounts": 12,
  "trees": 9,
  "branches": 31,
  "snapshots": 2048,
  "staged": 5,
  "objects": 18734,
  "storage_bytes": 734003200
}
```

`objects` and `storage_bytes` describe the object store (`objects/`); `meta.db` is not included in `storage_bytes`.

For live activity, subscribe to the [event stream](/docs/server/events).

## Audit log

Security-relevant actions are appended to an append-only audit log stored in `meta.db`. Query it with `GET /api/v1/audit` (tenant admins for their tenant, server admins for everything) or on the admin panel's Audit log page.

```bash
curl -s "http://localhost:7420/api/v1/audit?tenant=acme&action=branch.push&limit=20" \
  -H "Authorization: Bearer $TOKEN"
```

Each entry has `id`, `tenant_id`, `actor_id`, `actor` (a username, `anonymous`, or `system`), `action`, `resource_type`, `resource_id`, optional `details` and `remote_addr`, and `at`. Results are newest first, and `limit` defaults to 100. See the [REST API](/docs/server/rest-api#audit) for the full shape.

Actions use `resource.verb` names. Examples:

| Action | Recorded when |
|---|---|
| `auth.login` | An account logs in. |
| `tree.create` | A tree is created. |
| `branch.push` | A push moves a branch tip. |

Filter with `action=` using the exact name. Other actions follow the same naming pattern for registration, tokens, membership changes, protections, license rules, merge requests, and admin changes.

## What to alert on

- `/healthz` failing or timing out.
- Free disk space on the volume holding the data directory. `objects/` only grows in v0.2.0.
- Unexpected `auth.login` activity or unfamiliar `actor` values in the audit log.
- Backup jobs that did not complete (see [Storage](/docs/server/storage#backup)).
