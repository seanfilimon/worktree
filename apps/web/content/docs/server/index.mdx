title: W0rkTree Server
description: The Go server that stores canonical history, enforces access, protection and license rules, and serves gRPC, REST, SSE and the admin panel on a single port.
---


The W0rkTree server (`worktree-server`, source in `services/server-go`) is the shared remote that `wt` clients push to and pull from. It is a single pure-Go binary (no cgo) that keeps all metadata in an embedded bbolt database and all file content in a BLAKE3 content-addressed object store, on local disk or in an [S3-compatible bucket](/docs/server/storage-backends). There are no external dependencies to run it; `git` is needed only for [Git mirrors](/docs/server/mirrors) and an SMTP server only for [notification email](/docs/server/notifications#email).

<Callout type="info" title="Server vs. daemon">
  The server is the remote authority for a team. It is not the local background daemon `worktree-bg`, which watches your working copy, takes auto-snapshots, stages work in progress and fetches remote branches. See [`wt daemon`](/docs/cli/daemon).
</Callout>

## What the server does

- **Stores canonical history.** Snapshots are immutable once pushed. A push must descend from the current server tip (there is no force push), and branch tips move with compare-and-swap.
- **Hosts tenants and trees.** Every account gets a personal tenant; organizations are org tenants. Trees are `private`, `internal` or `public`.
- **Authenticates and authorizes.** argon2id passwords, scoped bearer tokens, sessions, TOTP two-factor authentication, OpenID Connect SSO, invitations. Built-in and custom roles, teams, per-tree grants and allow/deny policies. See [Access control](/docs/server/access-control).
- **Enforces rules on every push and read.** Per-branch and per-path policies, [branch and tag protection](/docs/server/branch-protection), [license rules](/docs/server/licensing), tenant quotas and snapshot signature verification.
- **Runs code review.** Merge requests with reviews, stale-approval tracking, comments, CI status checks, merge readiness, [server-side fast-forward, merge and squash merges](/docs/server/merging) and linked groups that merge across trees atomically; [path owners, review requests, drafts and suggested changes](/docs/server/review-workflow).
- **Searches and explains code.** [Code search](/docs/server/code-search) of contents and symbol definitions on any branch, with a persistent index, and [blame](/docs/cli/blame#server-api) per file.
- **Notifies people and other systems.** A per-account [inbox with watch levels and email](/docs/server/notifications), signed, retried [webhooks](/docs/server/webhooks) for every event, and an [OpenAPI description](/docs/server/openapi) of the REST API.
- **Mirrors to Git.** [Push mirrors](/docs/server/mirrors) keep a Git copy of a tree on GitHub, GitLab or your own Git server.
- **Tracks cross-tree work and releases.** Snapshot dependencies become TODOs in the target tree; releases with downloadable assets hang off tags, with [signed tags, checksums and SBOMs](/docs/server/release-integrity).
- **Shares work in progress.** Staged snapshots from `wt stage` or the daemon are visible to the team without entering branch history.
- **Streams and records activity.** Server-Sent Events, a gRPC `WatchBranches` stream, and an append-only audit log with NDJSON export.
- **Maintains itself.** Garbage collection with a grace period, compressed object storage, an integrity check (`wt admin fsck`), online and scheduled [backups](/docs/server/storage-backends#backups), staged and audit retention, rate limiting, health probes, Prometheus metrics and optional profiling. See [Operations](/docs/server/operations) and [Performance](/docs/server/performance).

## Single-port architecture

Everything is served from one listener (default `:7420`). In cleartext the port speaks HTTP/1.1 and HTTP/2 with prior knowledge (h2c); with `--tls-cert`/`--tls-key` the same port serves HTTPS and gRPC over TLS (ALPN `h2`). Requests are routed by protocol, content type and path:

| Traffic | How it is recognised | Purpose |
|---|---|---|
| gRPC (`worktree.sync.v1.SyncService`, `grpc.health.v1.Health`) | HTTP/2 with `Content-Type: application/grpc*` | Object transfer, push, pull, stage, tags, branch watching, access config. Used by `wt` and `worktree-bg`. |
| REST | `/api/v1/...` (JSON) | Accounts, IAM, tenants, trees, history, reviews, CI, releases, TODOs, admin. |
| SSE | `GET /api/v1/events` (`text/event-stream`) | Live event stream. |
| Health and metrics | `GET /healthz`, `GET /metrics` | Probes and Prometheus metrics (no `/api/v1` prefix). |
| Admin panel | `GET /admin/...` | Static build of `apps/admin` when `--admin-dir` is set; `/` and `/admin` redirect to `/admin/`. |

A remote URL is just the server origin:

```bash
wt remote add origin http://localhost:7420 --tenant acme
wt remote add company https://wt.example.com --tenant acme
```

The server logs a warning when it listens in cleartext on a non-loopback address. See [TLS](/docs/server/operations#tls) and [Deployment](/docs/server/deployment).

The gRPC service is defined in `crates/worktree-protocol/proto/sync.proto`. Its 16 RPCs are `Ping`, `ResolveTree`, `ListBranches`, `ListTags`, `PushTag`, `Negotiate`, `UploadObjects`, `DownloadObjects`, `Push`, `Pull`, `Stage`, `ListStaged`, `Unstage`, `WatchBranches`, `SyncAccessConfig` and `GetAccessConfig`. Messages are limited to 64 MiB in both directions. See [Sync protocol](/docs/protocol/sync-protocol) and the [Server specification](https://github.com/seanfilimon/worktree/blob/main/crates/worktree-protocol/specs/server/Server.md).

## Internal packages

The server is organised as small packages under `services/server-go/internal`, wired together through the shared contracts in `internal/domain`.

| Package | Role |
|---|---|
| `config`, `server` | Flags and `WT_*` variables; the single listener, TLS, interceptors, background tickers, graceful shutdown. |
| `syncsvc` | The gRPC `SyncService`. |
| `httpapi` | REST `/api/v1`, SSE, `/healthz`, `/metrics`, static admin panel. |
| `meta`, `objstore`, `content` | bbolt metadata and document collections; BLAKE3 object store; reading (chunked) file content. |
| `iam`, `authz`, `sso` | Authentication (accounts, tokens, sessions, MFA, invitations, resets); authorization (roles, teams, grants, policies, simulator); OIDC SSO. |
| `review`, `merge3`, `ci` | Branch protection, merge requests, reviews, linked groups and server-side merges; the three-way merge engine; CI check status. |
| `webhooks`, `codesearch`, `blame`, `policyhist` | Webhook delivery; the code search index; server blame; policy version history. |
| `notify`, `mirror`, `backup` | Notifications and email; Git push mirrors; backups and restore. |
| `license`, `pathacl`, `signing`, `limits` | License rules; path-level write denies; Ed25519 signature verification; quotas and rate limiting. |
| `staged`, `events`, `audit` | Staged snapshots and overlap detection; event bus; audit log. |
| `todo`, `release`, `gc`, `accesscfg` | Dependencies to TODOs; releases and assets; garbage collection and retention; declarative access documents. |

## What happens on a push

1. The client resolves the tree (creating it if allowed), learns the server tip with `ListBranches`, and refuses locally if the server tip is not an ancestor of the local tip.
2. It negotiates which objects the server lacks (manifests, blobs, chunk lists and chunks) and uploads them, then sends `Push` with the new snapshots, oldest first.
3. The server checks, in order: request shape; `tree:write` and `branch:push` (per-branch policies); branch protection (`no_direct_push`, `allowed_pushers`, `require_linear`); snapshot records and ancestry; that every referenced object is stored; fast-forward from the current tip; license rules on the changed paths; then the push checks (path-level write denies, tenant quotas, signatures and `require_signed`).
4. The snapshots are stored and the tip moves by compare-and-swap. The pusher's staged snapshot for that branch is cleared, `branch.pushed` is published and `branch.push` is audited. Rejections are audited as `branch.push_rejected`.

If the server tip moved, the push is rejected with a conflict carrying the server tip: run `wt pull`, resolve, and push again. See [`wt push`](/docs/cli/remote#wt-push).
