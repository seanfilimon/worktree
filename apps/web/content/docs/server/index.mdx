The W0rkTree server (`worktree-server`, source in `services/server-go`) is the shared remote that `wt` clients push to and pull from. It is a single, pure-Go binary (no cgo) that keeps all metadata in an embedded bbolt database and all file content in a BLAKE3 content-addressed object store on local disk.

<Callout type="info" title="Server vs. daemon">
  The server is the remote authority for a team. It is not the local background daemon `worktree-bg`, which watches your working copy, takes auto-snapshots, and uploads staged snapshots. See [`wt daemon`](/docs/cli/daemon) for the daemon.
</Callout>

## What the server does

- **Stores canonical history.** Snapshots are immutable once written. A push must descend from the current server tip of the branch (there is no force push), and branch tips move with a compare-and-swap so concurrent pushes cannot overwrite each other.
- **Hosts tenants and trees.** Every account gets a personal tenant; organizations are created as org tenants. Trees live inside a tenant and have a visibility of `private`, `internal`, or `public`.
- **Authenticates and authorizes.** Passwords are hashed with argon2id, tokens are bearer tokens accepted on both gRPC metadata and REST. Membership roles (`owner`, `admin`, `maintainer`, `developer`, `viewer`) decide what each caller may do.
- **Enforces policy on push.** Branch protection rules, merge request approvals, and per-path license rules are checked before a push is accepted.
- **Shares work in progress.** Staged snapshots uploaded by `wt stage` or the daemon are visible to the team (`wt status --team`) without becoming part of branch history.
- **Streams activity.** Pushes, stages, tags, tree creation, and merge request changes are published as Server-Sent Events.
- **Records an audit log.** Security-relevant actions are appended to an append-only audit log.

## Single-port architecture

Everything is served from one listener (default `:7420`). The server speaks cleartext HTTP/2 (h2c) and HTTP/1.1 on that port and routes each request by content type and path:

| Traffic | How it is recognised | Purpose |
|---|---|---|
| gRPC (`worktree.sync.v1.SyncService`) | `Content-Type: application/grpc*` over HTTP/2 | Object transfer, push, pull, stage, branches, tags, ping. Used by `wt` and `worktree-bg`. |
| REST | `/api/v1/...` (JSON) | Accounts, tenants, trees, history browsing, protections, licenses, merge requests, audit, admin. |
| SSE | `GET /api/v1/events` (`text/event-stream`) | Live event stream for dashboards and tools. |
| Health and metrics | `GET /healthz`, `GET /metrics` | Liveness and Prometheus metrics (no `/api/v1` prefix). |
| Admin panel | `GET /admin/...` | Static build of `apps/admin`, served when `--admin-dir` is set; unknown paths fall back to `index.html`. |

A remote URL is therefore just the server origin, for example `http://localhost:7420`:

```bash
wt remote add origin http://localhost:7420 --tenant acme
```

<Callout type="warn" title="No built-in TLS">
  The server does not terminate TLS. In production put it behind a reverse proxy that terminates TLS and forwards HTTP/2 cleartext (h2c) to the backend so gRPC keeps working. Built-in TLS is on the Roadmap. See [Deployment](/docs/server/deployment).
</Callout>

The gRPC service is the Rust-to-Go contract defined in `crates/worktree-protocol/proto/sync.proto`. Its RPCs are `Ping`, `ResolveTree`, `ListBranches`, `Negotiate`, `UploadObjects`, `DownloadObjects`, `Push`, `Pull`, `Stage`, `ListStaged`, `PushTag`, `ListTags`, and `SyncAccessConfig`. The message size limit is 64 MiB in both directions. The push and pull flows are described in [Sync protocol](/docs/protocol/sync-protocol).

## Internal packages

The server is organised as small packages under `services/server-go/internal`, wired together through the shared contracts in `internal/domain` (data types and service interfaces).

| Package | Role |
|---|---|
| `domain` | Shared data model (tenants, accounts, trees, branches, snapshots, merge requests, audit events, license rules) and the service interfaces every other package implements or consumes. |
| `objstore` | Content-addressed object store on disk: `objects/<2-hex>/<62-hex>`, keyed by BLAKE3-256. Writes are verified against the hash and are idempotent. |
| `meta` | Metadata store (`meta.db`, bbolt) for every record except object bytes, plus snapshot ancestry walking (ancestor checks, logs, missing-snapshot computation). |
| `iam` | Registration, login, token issuance and verification, and role-based authorization. Provides the gRPC interceptors and HTTP middleware that attach the caller to each request, and creates the server admin account at startup. |
| `events` | In-process publish/subscribe bus. Publishing never blocks; slow subscribers drop events. |
| `staged` | Team-visible staged snapshots: at most one per tree, account, and branch; replaced by a newer stage and cleared when that account pushes the branch. |
| `audit` | Append-only audit log of security-relevant actions, queryable by tenant and action. |
| `license` | Per-path SPDX license rules, checked on push (changed paths) and on reads. |
| `review` | Branch protection checks on direct pushes and the merge request lifecycle (open, approve, merge, close). |
| `syncsvc` | Implementation of the gRPC `SyncService`: negotiation, object upload and download, push validation, pull, staging, tags. |
| `httpapi` | REST API, SSE event stream, `/healthz`, `/metrics`, and static serving of the admin panel. |
| `config`, `server` | Flag and environment parsing, and the h2c listener that multiplexes gRPC and HTTP on one port with graceful shutdown. |

## What happens on a push

1. The client resolves the tree (creating it if allowed), learns the remote branch tip, and asks the server which objects it is missing.
2. It uploads the missing manifests and blobs, then sends the push with the old tip, the new tip, and the new snapshots.
3. The server checks, in order: `tree:write` permission, branch protection, license rules on the changed paths, that every referenced object and parent snapshot is present, and that the new tip descends from the current server tip.
4. The branch tip is updated atomically. The pusher's staged snapshot for that branch is cleared, a `branch.pushed` event is published, and a `branch.push` audit entry is written.

If the server tip moved, the push is rejected with a conflict that carries the server tip; run `wt pull`, resolve, and push again. See [`wt push`](/docs/cli/remote#wt-push).
