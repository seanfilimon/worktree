## Overview

The production remote server is being implemented in Go under `server-go/`. The Rust
`worktree-server` crate remains the local bgprocess/prototype server for filesystem watching and
local demo flows. The remote server boundary is intentionally separate: it verifies uploaded
objects, stores authoritative metadata, gates operations through IAM, and never watches a developer
working directory.

Current implemented remote-server slices include authenticated REST staged upload/list, authenticated
gRPC staged upload/list, BLAKE3 object verification, canonical staged idempotency, file or Postgres
staged metadata storage, audit recording, request metrics, embedded migrations, and Docker Compose
with Postgres.

## Runtime Model

The local Rust prototype uses `tokio` for localhost demo endpoints and watcher tasks. The Go remote
server uses standard HTTP/gRPC servers:

- **HTTP listener** — health, readiness, metrics, and REST staged endpoints on `WT_SERVER_HTTP_ADDR`
- **gRPC listener** — `SyncService` on `WT_SERVER_GRPC_ADDR`, default `127.0.0.1:9877`
- **Storage layer** — local BLAKE3 object store plus file or Postgres staged metadata store
- **Auth path** — shared bearer-token principal extraction for REST and gRPC
- **Audit path** — shared REST/gRPC audit recorder with token ID and auth method context
- **IAM seam** — shared default-deny `Authorizer` interface for staged create/list decisions

## Data Flow

### Local Operations

```
Working Directory → Filesystem Watcher → Event Engine → Snapshot Builder → Object Store → Branch Pointers
```

All local operations are **lock-free for reads** and use **per-tree write locks** for mutations.

### Sync Operations

```
Object Store (local) → Delta Calculator → Compression → Wire Protocol → Server (remote) → Object Store (remote)
```

The sync protocol is **incremental** — only objects the remote doesn't have are transferred.

The implemented staged slice currently uploads added/modified object bytes for one snapshot. Go
rejects unsafe paths, verifies declared BLAKE3 hash and size, authenticates the bearer principal,
authorizes staged create/list, and stores the staged snapshot record idempotently. Have/want
negotiation and branch push/pull are still planned.
