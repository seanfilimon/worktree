Every request to the server, over gRPC or REST, is made anonymously or as an authenticated principal (an account or a service account), and every operation is checked as one **action** (such as `tree:write` or `mr:merge`) on a resource (a tenant, tree, branch or path). Everything below is available from the [`wt` CLI](/docs/cli/iam), the [REST API](/docs/server/rest-api) and the admin panel. The full model is in the [IAM](https://github.com/seanfilimon/worktree/blob/main/crates/worktree-protocol/specs/iam/IAM.md) and [Tenant Model](https://github.com/seanfilimon/worktree/blob/main/crates/worktree-protocol/specs/iam/TenantModel.md) specifications.

## How a decision is made

1. A disabled account or service account is denied.
2. Token scopes: a scoped token may only perform actions its scopes cover. This binds server admins too.
3. A server admin is allowed (policies are not consulted).
4. Tenant status: a `suspended` tenant denies every write, a `deactivated` tenant denies everything.
5. Roles are collected: the tenant membership role, the service account's own role, direct tree grants, team grants and tenant grants on the tree. Tree visibility adds `tree:read`.
6. Enabled policies of the tenant are applied: a matching **deny** overrides every allow; a matching **allow** grants the action even without a role.
7. Otherwise the request is denied (`implicit_deny`).

`branch:push` is evaluated as `tree:write` plus a deny pass over the branch, so a policy can block pushes to one branch. Ask the server to explain any decision:

```bash
wt iam simulate --principal user:bob --action branch:push --tenant acme --tree acme/web --branch main
wt iam effective --tenant acme --principal user:bob
```

The simulator lists every contributing reason (`tenant_role`, `team_role`, `tree_grant`, `custom_role`, `service_account`, `visibility`, `token_scope`, `policy`, `tenant_suspended`, `owner_protected`, ...). The admin panel has the same as the **Access simulator** page.

## Accounts

An account has a unique `username` (`^[a-z0-9][a-z0-9-]{1,38}$`, some names are reserved), an `email` (not verified), a `display_name`, and the flags `is_admin` (server admin) and `disabled`. Passwords are hashed with argon2id.

Accounts are created by:

- self-service registration (`wt register`, `POST /api/v1/auth/register`) when `--allow-registration` is on (the default);
- a server admin, regardless of that setting: `wt admin account-create USERNAME --email EMAIL [--admin] [--password-stdin]` or `POST /api/v1/admin/accounts`;
- the server at startup for the account named by `--admin-user`, when `--admin-password` is set;
- the first SSO login, when SSO `auto_create` is on.

A server admin disables an account with `wt admin account-set USERNAME --disabled true` (`PATCH /api/v1/admin/accounts/{username}`); it takes effect on the next request because the account is re-read every time. Accounts are not deleted. Admins also set passwords (`wt admin password`, which revokes the account's tokens) and issue one-time reset codes (`wt admin reset-code`, redeemed with `wt password-reset`).

## Tenants

A tenant owns trees.

| Kind | Created by | Slug |
|---|---|---|
| `user` (personal) | Automatically on registration; the account is its `owner`. | The username. |
| `org` | `wt tenant create SLUG [--name N]` or `POST /api/v1/tenants`; the caller becomes `owner`. | Lowercase `[a-z0-9-]`, unique. |

- `plan` (`free`, `pro`, `enterprise`) is a label set by a server admin (`wt tenant plan`); it does not change limits.
- `status` is `active`, `suspended` (read-only: writes are denied with reason `tenant_suspended`; nothing is revoked) or `deactivated` (all access denied). Server admins set it with `wt tenant suspend|resume|deactivate TENANT [--reason TEXT]`. See [Operations](/docs/server/operations#tenant-status).
- Limits (trees, storage, branches per tree, members, requests per minute) are server defaults plus per-tenant overrides. See [Quotas](/docs/server/operations#quotas).

Remotes name the tenant explicitly (`wt remote add origin http://localhost:7420 --tenant acme`) and clones use `TENANT/TREE`. See the [multi-tenancy guide](/guides/multi-tenancy).

## Tenants and members

Members are managed with [`wt tenant`](/docs/cli/administration#wt-tenant) or `GET`, `PUT` and `DELETE` on `/api/v1/tenants/{tenant}/members/{username}` (needs `tenant:admin`):

```bash
wt tenant add-member acme bob --role developer
wt tenant set-role acme bob maintainer
wt tenant members acme
wt tenant remove-member acme bob
```

Invitations let people join without an admin knowing their username in advance:

```bash
wt invite create acme --email carol@example.com --role viewer --team backend   # prints a one-time wti_ code
wt invite accept wti_...                                                       # run as carol
```

Invitations last 7 days by default, are single use and, when they name an email or username, can only be accepted by that account. Only owners can grant or revoke `owner`, and a tenant always keeps at least one owner (`409 last_owner`).

## Built-in roles

The five built-in roles form a strict hierarchy, `owner ⊃ admin ⊃ maintainer ⊃ developer ⊃ viewer`:

| Action | viewer | developer | maintainer | admin | owner |
|---|:-:|:-:|:-:|:-:|:-:|
| `tenant:read`, `tree:read` | yes | yes | yes | yes | yes |
| `tree:write`, `branch:create`, `branch:push`, `mr:create`, `release:create`, `ci:report` | | yes | yes | yes | yes |
| `branch:delete`, `mr:approve`, `mr:merge`, `tree:create`, `iam:read`, `release:delete` | | | yes | yes | yes |
| `tree:admin`, `tenant:admin`, `iam:admin` | | | | yes | yes |
| `server:admin` | | | | | |

| Action | Covers |
|---|---|
| `tree:read` | Browse, clone, pull, download; staged snapshots, protections, licenses, merge requests. |
| `tree:write` | Push, stage, create tags. |
| `tree:create` | Create trees, by REST or by a first push. |
| `tree:admin` | Tree settings, branch and tag protection, license rules, tag deletion, tree deletion. |
| `mr:merge` | Merge and close merge requests (also linked groups). |
| `release:create`, `release:delete` | Create and edit releases and assets; delete them. |
| `ci:report` | Report CI check results. |
| `iam:read`, `iam:admin` | View or manage teams, roles, policies, grants, service accounts and invitations. |
| `server:admin` | `/api/v1/admin/*` and server-wide audit queries; server admins only. |

`owner` grants the same actions as `admin`; owners additionally assign the owner role, are protected by the lockout guard and may force edits of config-managed objects. List the catalog with `wt iam actions`.

## Custom roles

```bash
wt role create acme reviewer --permission tree:read --permission mr:create --permission mr:approve
wt tenant set-role acme carol reviewer
```

Permissions are catalog actions or `<area>:*` (never `*` or `server:*`). A custom role is assigned exactly like a built-in one: membership, grants, service accounts, invitations. Deleting a role that is still assigned answers `409`.

## Teams

Teams group tenant members. A team has no tenant-wide role; its access comes from tree grants and from policy statements that name `team:<slug>`. Team maintainers (`--maintainer`) may manage the team's membership without `iam:admin`.

```bash
wt team create acme backend --name "Backend"
wt team add acme backend bob
wt team show acme backend
```

## Tree grants

A grant gives a subject a role on one tree, and can lift access above the tenant role (it never lowers it; use a policy deny for that):

```bash
wt grant set acme/api --team backend --role developer
wt grant set acme/api --user dave --role maintainer
wt grant set acme/api --sa ci --role developer
wt grant set acme/api --tenant partner --role viewer      # every member of tenant "partner"
wt grant list acme/api
```

Grants cover tree-scoped actions only (`tree:*` except `tree:create`, `branch:*`, `mr:*`, `release:*`, `ci:report`). A grant to another tenant's users or to a whole tenant (`subject_type: "tenant"`) is how cross-tenant collaboration works. REST: `GET|PUT|DELETE /api/v1/trees/{tenant}/{tree}/grants`.

## Tree visibility

| Visibility | Who can read (`tree:read`) |
|---|---|
| `private` (default) | Tenant members per role, and grantees. |
| `internal` | Additionally any signed-in principal on the server. |
| `public` | Additionally anyone, including anonymous requests. |

Visibility widens read access only; a policy deny still overrides it. Anonymous gRPC calls are limited to `Ping` and reads of public trees. Change it with `wt trees update acme/web --visibility internal` (`tree:admin`).

## Policies

A policy is a named list of allow and deny statements for one tenant:

```json
{
  "name": "protect-main",
  "enabled": true,
  "statements": [
    {
      "sid": "no-contractor-pushes-to-main",
      "effect": "deny",
      "actions": ["branch:push"],
      "resources": ["wt:branch/acme/*/main"],
      "principals": ["team:contractors", "tenant:partner"],
      "conditions": { "require_mfa": true, "ip_ranges": ["10.0.0.0/8"] }
    }
  ]
}
```

| Field | Values |
|---|---|
| `resources` | `*`, `wt:tenant/<t>`, `wt:tree/<t>/<tree>`, `wt:branch/<t>/<tree>/<branch>`, `wt:path/<t>/<tree>/<path>`. `*` matches within a segment, a `**` segment any depth. A statement on a resource also covers its descendants. |
| `principals` | `*`, `authenticated`, `anonymous`, `user:<name>`, `team:<slug>`, `role:<role>`, `sa:<name>`, `sa:<tenant>/<name>`, `tenant:<slug>`. Names may contain `*`. |
| `conditions` | All set conditions must hold: `ip_ranges`, `require_mfa`, `not_before`/`not_after`, `time_window` (`days`, `start`, `end`, `timezone`). Undecidable conditions fail closed. |

```bash
wt policy validate acme --file protect-main.json
wt policy create acme --file protect-main.json
wt policy simulate acme --file protect-main.json --principal user:bob --action branch:push --tree web --branch main
wt policy disable acme <ID>
```

- **Deny overrides allow**, including allows from roles, grants and visibility.
- **Path rules**: `tree:read` denies on `wt:path/...` stub those files on pull and answer `403 path_denied` on REST reads; `tree:write` denies reject pushes that touch them.
- **Lockout guard**: deny statements never take `iam:*` or `tenant:admin` away from a tenant owner.
- The client IP for `ip_ranges` is the socket peer, or the `X-Forwarded-For` client when the peer is a [trusted proxy](/docs/server/operations#trusted-proxies). SSO sessions count as MFA when the identity provider asserts a second factor in the `amr` claim.

Policies can also be kept as TOML files and applied with `wt access apply`; see [Declarative access](/docs/server/declarative-access).

## Tokens

All authentication uses bearer tokens (`wt_...`), sent as `authorization: Bearer <token>` in gRPC metadata or `Authorization: Bearer <token>` on REST. The server stores only their SHA-256 hash, so a token is shown once.

| Kind | Obtained from | Lifetime |
|---|---|---|
| `session` | `wt login`, `POST /api/v1/auth/login` (plus `/auth/login/mfa`), SSO | 30 days |
| `api` | `wt token create NAME [--ttl-hours N] [--scope S]...`, `POST /api/v1/auth/tokens` | `ttl_hours`, or no expiry |
| `service` | `wt sa key-create TENANT NAME [--ttl-hours N] [--scope S]...` | `ttl_hours`, or no expiry |

- **Scopes** are action patterns (`tree:read`, `tree:*`, `ci:report`, `*`); a scoped token can do at most what its scopes cover, and only what the identity is allowed anyway.
- **Sessions** record `last_ip`, `user_agent` and `mfa`: `wt session list`, `wt session revoke ID`, `wt session revoke-others`. `wt logout` forgets the local credential.
- `wt login` stores its token in `$WT_HOME/credentials.toml` (default `~/.wt`); the daemon uses the same credential to stage and fetch.

Use a scoped API token or service-account key with a TTL for CI and scripts instead of a session token.

## Service accounts

Non-human identities that belong to one tenant and act there with their own role (any role except `owner`), plus any grants made to them:

```bash
wt sa create acme ci --role developer --description "CI pipeline"
wt sa key-create acme ci --name github-actions --ttl-hours 720 --scope tree:read --scope ci:report
```

The principal name is `sa:acme/ci`. `wt sa update acme ci --disable` stops all its keys.

## Two-factor authentication and SSO

- **TOTP** (RFC 6238, 6 digits, 30 s): `wt mfa enable` shows a QR code, asks for a code and prints 10 single-use recovery codes. With MFA on, password login returns `{"mfa_required": true, "mfa_token": ...}` and `wt login` asks for a code (or reads `--mfa-code` / `WT_MFA_CODE`). Policies can require it with `require_mfa`.
- **SSO** (OpenID Connect with PKCE, state and nonce, RS256/ES256 ID tokens) is configured by a server admin with `wt sso set` or `PUT /api/v1/admin/sso`; the login page then offers the provider. Linking first-time identities to existing accounts by email (`--link-by-email true`) is off by default because local emails are not verified.

See [Security](/docs/security) for hashing, lockouts and token handling, and the [`wt` access commands](/docs/cli/iam) for every flag.
