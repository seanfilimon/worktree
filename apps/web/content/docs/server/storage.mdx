All server state lives in one data directory, set with `--data` / `WT_DATA` (default `./wt-data`, created with mode 0750). There is no external database.

## Layout

```text
wt-data/
  meta.db                 bbolt database: all metadata
  objects/
    af/
      1349b9f5f9a1a6a0404dea36dcc9499bcb25c9adc112b7cc9a93cae41f3262
    4f/
      ...
```

### `meta.db`

An embedded [bbolt](https://github.com/etcd-io/bbolt) database holding every record except file content: tenants, accounts (argon2id password hashes), memberships, token hashes, trees, branches and their tips, snapshots, tags, staged snapshots, branch protections, license rules, merge requests, the audit log, and the IAM data (teams, custom roles, policies, grants, service accounts, MFA state, invitations, SSO configuration). Primary buckets hold JSON values keyed by id, with `idx_*` buckets for lookups.

A `docs` bucket holds the document collections added with reviews, CI, releases and operations:

| Collection | Holds |
|---|---|
| `todos`, `todo_sources` | TODOs created from snapshot dependencies |
| `releases` | Releases (assets are referenced by hash) |
| `ci_status`, `mr_comments`, `linked_groups`, `tag_protections` | CI checks, review comments, linked merge groups, tag protections |
| `signing_keys`, `signing_key_index` | Registered Ed25519 signing keys |
| `access_docs` | Last applied declarative access documents |
| `gc_marks`, `gc_runs`, `tenant_usage` | GC bookkeeping, the last 20 GC reports, tenant storage usage |
| `webhooks`, `webhook_deliveries` | [Webhooks](/docs/server/webhooks) (with their secrets) and their delivery logs |
| `policy_versions` | [Policy history](/docs/server/policy-history) |
| `code_index_meta` | Metadata of the in-memory [code search](/docs/server/code-search) index, one document per indexed tree |

The file is opened exclusively with a 5 second lock timeout, so a second server on the same data directory fails to start. Every write is one bbolt transaction. A schema version is stored, and the server refuses to open a database written by a newer schema.

### `objects/`

A content-addressed store of:

- **blobs**: raw file bytes, or one chunk of a large file;
- **manifests**: the encoded file list of one snapshot;
- **chunk lists**: the ordered chunks of a file larger than 8 MiB (see [Large files](/docs/protocol/large-files)).

Each object is named by the 64-character lowercase hex BLAKE3-256 hash of its content, split into a two-character fan-out directory and the remaining 62 characters. Objects are at most 64 MiB each. A file holds either the raw content or, since v0.6, the magic `WTZ1` followed by a zstd frame of it: objects of at least 512 bytes are compressed when that saves at least 10 % (`--compress-objects`, default on). The hash is always over the uncompressed content, so files written before v0.6 need no migration. See [Object compression](/docs/server/operations#object-compression).

Objects are shared and deduplicated across all trees and tenants. Which tenant may read which object is decided by the metadata: an object is readable only through a tree whose branches, tags or staged snapshots reach it, and object downloads are scoped to one tree. See the [object model](/docs/protocol/object-model). Release assets are stored as blobs too.

## Integrity and immutability

- **Verified writes.** The server hashes every uploaded object and rejects it if the bytes do not match. Manifests and chunk lists must also decode and validate.
- **Verified store.** `wt admin fsck` re-hashes every stored object and checks that every reachable snapshot is complete. See [Integrity checks](/docs/server/operations#integrity-checks).
- **Idempotent, atomic writes.** Writing an existing object is a no-op. Objects are written to a temporary file, fsynced and renamed into place, so a crash never leaves a partial object under its final name.
- **Immutable snapshots.** A stored snapshot never changes; storing the same id with different content is rejected.
- **Append-only history.** Branch tips only move forward, with compare-and-swap. There is no force push.
- **Append-only audit log**, pruned only by the optional `--audit-retention`.

<Callout type="info" title="Windows">
  On Windows, renaming a temporary file over an object that already exists can fail with "Access is denied", for example when two uploads of the same object race. Such failures are retried with backoff, and because objects are content-addressed, a target that already has the right bytes counts as success.
</Callout>

## Garbage collection

Deleting a tree removes its metadata in one transaction and publishes `tree.deleted`; deleting a server branch removes the ref. Objects are never deleted directly. The garbage collector marks everything reachable from branch tips, tags, staged snapshots, merge requests and releases, and deletes unreachable objects after a grace period (`--gc-grace`, default 30 days). It also applies staged-snapshot and audit retention. See [Garbage collection](/docs/server/operations#garbage-collection).

## Quotas

Per-tenant storage usage is tracked in the `tenant_usage` document and increased by the new objects of each accepted push. It is enforced by the `max_storage_bytes` quota. See [Quotas](/docs/server/operations#quotas).

## Backup

The simplest consistent backup is to stop the server, copy the whole data directory, and start it again.

<Tabs items={['bash', 'PowerShell']}>
<Tab value="bash">

```bash
sudo systemctl stop worktree-server
tar -czf /backups/wt-data-$(date +%F).tar.gz -C /var/lib/worktree data
sudo systemctl start worktree-server
```

</Tab>
<Tab value="PowerShell">

```powershell
Stop-Service worktree-server
Compress-Archive -Path D:\worktree\data -DestinationPath "D:\backups\wt-data-$(Get-Date -Format yyyy-MM-dd).zip"
Start-Service worktree-server
```

</Tab>
</Tabs>

To keep the downtime short, use the fact that object files are immutable:

1. While the server runs, copy `objects/` to the backup location (for example with `rsync -a`).
2. Stop the server.
3. Copy `meta.db`, and run the `objects/` copy again to pick up objects written since step 1.
4. Start the server.

Do not copy `meta.db` while the server is running: a copy taken during a write can be inconsistent. A filesystem-level atomic snapshot (LVM, ZFS, Btrfs, or a VSS snapshot on Windows) of the whole data directory is also consistent. Always back up `meta.db` and `objects/` together. Because garbage collection deletes objects, take the `objects/` copy after (or together with) `meta.db`, never long before it, or pause GC (`--gc-interval 0`) while the backup runs.

## Restore

1. Stop the server.
2. Replace the data directory with the backup (both `meta.db` and `objects/`).
3. Start the server with `--data` pointing at it.

Clients whose local history is ahead of the restored server can push again: their snapshots descend from the restored tips.

## Moving the data directory

Stop the server, move the directory, and start the server with the new `--data` path. Paths inside the directory are relative, so no other changes are needed.

<Callout type="info">
  Encryption at rest, pluggable storage backends (S3, external databases) and replication are not built yet (see the [roadmap](/roadmap)). Use full-disk or volume encryption if you need data encrypted at rest. See the [Storage specification](https://github.com/seanfilimon/worktree/blob/main/crates/worktree-protocol/specs/storage/Storage.md).
</Callout>
