W0rkTree stores file content in a **content-addressed object store** and records history as **snapshots** that point at a manifest object. The client and server use the same bytes and the same hashes, so moving objects between them is a byte copy. The normative description is the [Storage specification](https://github.com/seanfilimon/worktree/blob/main/crates/worktree-protocol/specs/storage/Storage.md).

## Hashes

- An object's hash is **BLAKE3-256 of its exact (uncompressed) bytes**. There is no header, type prefix, or compression in the hashed data; on-disk compression (below) does not change it.
- On the wire, `ContentHash.value` is the **32 raw bytes** of the hash.
- In JSON (local snapshot records, REST responses) and in file paths, a hash is written as **64 lowercase hex characters**.
- In Rust the type is `worktree_sdk::ObjectHash` (a re-export of `worktree_protocol::core::hash::ContentHash`); `worktree_sdk::store::hash_bytes(data)` computes it. The Go server uses an equivalent 32-byte type, so hashes round-trip without re-encoding.

The server verifies `BLAKE3(data) == hash` for every uploaded object and rejects mismatches. The client re-hashes every object it reads and verifies downloads before storing them (`ObjectStore::put_with_hash` fails with `CorruptObject` on a mismatch).

## Objects

There are three kinds of object (`ObjectKind` on the wire):

| Kind | Content | Hash |
|---|---|---|
| `BLOB` | The raw bytes of one file, or one chunk of a large file, uncompressed. | BLAKE3 of the bytes. Identical content shares one blob. |
| `MANIFEST` | A protobuf-encoded `ManifestRecord`: the complete file listing of one snapshot of one tree. | BLAKE3 of the encoded `ManifestRecord`. |
| `CHUNK_LIST` | A protobuf-encoded `ChunkList` for a file larger than 8 MiB: the file size and its chunks in order. | BLAKE3 of the encoded `ChunkList`. |

Snapshots, branches, tags and releases are **not** objects; they are records that refer to objects by hash. Release assets are stored as blobs.

### Manifests

```text
ManifestRecord { entries: repeated ManifestEntry }
ManifestEntry  { path: string, blob_hash: ContentHash, size: uint64, executable: bool, chunked: bool }
```

Rules for a valid manifest:

- `path` is relative to the tree root and uses `/` as the separator on every platform (also on Windows). Paths are clean: no leading `/`, no `\`, NUL or `..` components, and no `.wt` or `.wt-tree` component.
- Entries are **sorted** lexicographically by path and paths are **unique**.
- The manifest lists every tracked file of the tree. It excludes ignored paths and paths that belong to nested trees. A manifest is flat: directories are implied by paths.
- `size` is the file size in bytes; `executable` records the executable bit.
- `chunked = true` means `blob_hash` names a `CHUNK_LIST` object instead of a blob.

Because the encoding is canonical (`Manifest::to_bytes`), two identical file listings always produce the same manifest hash. `Manifest::from_entries` sorts and dedups entries (last wins) so callers cannot produce a non-canonical manifest.

### Chunk lists

```text
ChunkList { size: uint64, chunks: repeated Chunk }
Chunk     { hash: ContentHash, size: uint64 }
```

The file is the concatenation of its chunks in order, and the chunk sizes must sum to `size` (both sides validate this). Chunks are produced by FastCDC (minimum 256 KiB, average 1 MiB, maximum 4 MiB), so unchanged regions of a large file keep their chunks across versions. See [Large files and shallow sync](/docs/protocol/large-files#chunked-large-files).

## Snapshots

A snapshot is an immutable point-in-time record of one tree. On the wire it is a `SnapshotRecord`; locally it is the JSON form of `worktree_sdk::Snapshot` in `.wt/snapshots/<id>.json`.

| `SnapshotRecord` field | Rust `Snapshot` field | Meaning |
|---|---|---|
| `id` | `id` | Snapshot id, a **UUID v4** string. |
| `tree_id` | `tree_id` | Stable tree id (UUID); the server's tree id once the tree is linked to a remote. |
| `branch_name` | `branch` | Branch the snapshot was created on. |
| `parents` | `parents` | Parent snapshot ids: none for the first snapshot, one normally, two for a merge (`[ours, theirs]`). |
| `manifest_hash` | `manifest` | Hash of the `MANIFEST` object. |
| `author` | `author` | `"Name <email>"` from `[user]`, else the OS user. |
| `message` | `message` | Snapshot message. |
| `created_at` | `created_at` | Creation time (`google.protobuf.Timestamp` / RFC 3339 UTC). |
| `auto_generated` | `auto_generated` | `true` for daemon auto-snapshots. |
| `dependencies` | `dependencies` | Declared dependencies on other trees (`wt snapshot --depend`); they become TODOs on push. |
| `reverts` | `reverts` | Set on a revert snapshot: the id of the snapshot whose changes it undoes. |
| `signature`, `signing_key_id` | `signature` (`SnapshotSignature{key_id, signature}`) | Optional Ed25519 signature (64 bytes) and the id of the key that made it. Empty means unsigned. |

A `Dependency` carries `tenant_slug` (empty = the same tenant), `tree`, `branch` (empty = the target's default branch), `title`, `details`, `priority` (`low`, `medium`, `high`, `critical`), `blocking` and `linked`. See [Dependencies, TODOs and releases](/docs/cli/dependencies).

A signature covers `SignedSnapshotPayload { record }`: the `SnapshotRecord` with `signature`, `signing_key_id`, `tree_id` and `branch_name` cleared, so it stays valid when the record is re-homed under the server's tree id. See [Snapshot signing](/docs/cli/signing).

Snapshot ids are random UUIDs, not content hashes; two snapshots with identical content are distinct records that share one manifest. The integrity of a snapshot's content comes from its `manifest_hash`, which pins every file through its blob or chunk-list hash. The first 8 characters of an id are its short form (`Snapshot::short_id`), and any unique prefix of at least 4 characters is accepted as a revision.

Snapshots form a DAG through `parents`. A push sends parents before children, and the server stores records immutably: once a snapshot id exists on the server it never changes. The server additionally records `pushed_by`, `pushed_at` and `verified` (the signature checked out against a registered key).

## Branch tips

A branch is a named pointer to its newest snapshot (its **tip**), or to nothing for an empty branch.

- Locally, `.wt/trees/<tree>/refs/branches/<branch>` contains the tip's snapshot id (or is empty), and `refs/remotes/<remote>/<branch>` records the last known server tip.
- On the server, a branch is `(tree, name) → tip`, plus a `protected` flag and timestamps. A tip only moves forward to a descendant snapshot, by compare-and-swap, during `Push` or a fast-forward merge-request merge.
- Locally archived (soft-deleted) branches keep their tip, so their history stays reachable. Deleting a server branch (`wt trees branch-delete`) removes the pointer; objects no longer reachable from any branch, tag, staged snapshot, merge request or release are removed by server [garbage collection](/docs/server/operations#garbage-collection) after a grace period.

## Tags

A tag names one snapshot: `TagRecord{name, target, message?, tagger, created_at}` on the wire, `worktree_sdk::TagInfo` locally (`.wt/trees/<tree>/refs/tags/<tag>.json`). Tags are per tree. `PushTag` never moves an existing server tag (pushing an existing name is refused), tag protections can forbid moving or deleting tags at all, and the server records the authenticated user as `tagger`. Releases are metadata attached to a server tag. See [Tags and releases](/guides/tags-and-releases) and [`wt release`](/docs/cli/dependencies#wt-release).

## Where objects live

| Location | Path |
|---|---|
| Local worktree | `.wt/objects/<hh>/<62 hex>`: the first two hex characters of the hash form the directory, the remaining 62 the file name. Objects are deleted only by [`wt gc`](/docs/cli/maintenance#wt-gc), when nothing references them. |
| Server | `<data>/objects/<hh>/<62 hex>` in the server's data directory (default `./wt-data`), shared and deduplicated across tenants. Metadata, including snapshot records and branch tips, lives in `<data>/meta.db` (bbolt). See [Storage](/docs/server/storage). |

A stored file is either the raw content or, since v0.6, the 4-byte magic `WTZ1` followed by one zstd frame of the content. Writers compress objects of at least 512 bytes when that saves at least 10 % (content that itself starts with `WTZ1` is always stored compressed, so the magic is unambiguous); readers accept both forms and verify the decoded content against the hash. Writes go to a temporary file followed by a rename, so concurrent writers are safe; if the rename target already exists, it decodes to the same content. See [Storage maintenance](/docs/cli/maintenance#compressed-objects).

<Callout type="info" title="Not built yet">
  Pack files, delta compression and per-directory tree objects are not part of the format (see the [roadmap](/roadmap)). Objects are stored and transferred whole; transfers are gzip-compressed per gRPC message.
</Callout>
